A field guide to Kubernetes

You can run a container. This is the rest: the reconciliation model, the object graph, how a packet reaches a Pod, scheduling, storage, RBAC, and the 2026 shifts — Gateway API, native sidecars, in-place resize. No hand-waving.

01

Orientation

Kubernetes is a control loop over declared desired state. You describe what you want; the cluster continuously works to make reality match.

At its core Kubernetes is not "a thing that runs containers" — it's a reconciliation engine. You submit objects describing desired state ("I want 3 replicas of this image, reachable on port 80"), and a set of controllers watch the cluster and take action to drive actual state toward that desired state, forever. If a Pod dies, a controller notices the gap and creates a new one. You almost never issue imperative "do X now" commands in production; you change the declared state and let the loop converge.

◆ mental model

Imperative ops (SSH in, start a process, restart on failure) is you being the control loop. Kubernetes is the control loop. You move from "run this" to "this should be true", and the system holds it true across node failures, deploys, and scaling. Everything below — Pods, Services, Deployments — is just a kind of desired-state object plus a controller that reconciles it.

What it gives you

  • Self-healing. Crashed containers restart, dead Pods get rescheduled, unhealthy ones leave rotation — without a human.
  • Declarative rollouts. Change the image; the Deployment controller rolls Pods one batch at a time and can roll back.
  • Horizontal scaling. Bump replica count or let an autoscaler do it from metrics.
  • Service discovery & load balancing. A stable virtual IP and DNS name fronts a churning set of Pods.
  • Portability. The same manifests run on any conformant cluster — laptop, on-prem, or any cloud's managed offering.

What it costs you

  • Operational complexity. Networking, storage, RBAC, upgrades, and a sprawling object model. The learning curve is the product's main downside.
  • It's not a PaaS. Out of the box it gives primitives, not a polished developer experience — you assemble CI/CD, secrets, observability, and policy yourself (or buy a platform on top).
  • Overkill for small/simple. One container on one box, or a handful of stateless services with no scaling needs, is often better served by a managed container runner or a VM.
◆ when to reach for it

Kubernetes pays off when you have many services, need self-healing and rolling deploys, want to bin-pack workloads densely across a fleet, or require multi-cloud portability. If you're running three stateless apps that never scale, the complexity tax probably isn't worth it. The honest 2026 take: most teams consume Kubernetes through a managed control plane (EKS/GKE/AKS) and a platform layer, rarely operating raw clusters themselves.

02

Architecture

A cluster splits into a control plane (the brain) and worker nodes (the muscle). Everything routes through one API server.

Control plane components

ComponentJob
kube-apiserverThe front door. The only component that talks to etcd. Validates and serves the REST API; every read/write — from kubectl, controllers, kubelets — goes through it.
etcdThe cluster's database: a consistent, distributed key-value store holding all object state. The source of truth. Lose it and you lose the cluster's memory.
kube-schedulerWatches for Pods with no node assigned and picks the best node for each (based on resources, affinity, taints).
kube-controller-managerRuns the built-in controllers — the reconciliation loops (Deployment, ReplicaSet, Node, Job, etc.) bundled into one process.
cloud-controller-managerBridges to the cloud provider: provisions load balancers, attaches volumes, manages node lifecycle.

Node components

ComponentJob
kubeletThe node agent. Watches the API server for Pods assigned to its node and makes them run, reporting status back. Talks to the container runtime via the CRI.
container runtimeActually runs containers — containerd or CRI-O via the Container Runtime Interface. (The Docker shim was removed in 1.24; Docker-built images still run fine — they're just OCI images.)
kube-proxyPrograms node networking (iptables/IPVS, or replaced by a CNI's eBPF dataplane) so Service virtual IPs route to backing Pods.
◆ how a deploy actually flows

kubectl apply → API server validates and writes the object to etcd → the Deployment controller sees a new Deployment, creates a ReplicaSet → the ReplicaSet controller creates Pod objects (still unscheduled) → the scheduler assigns each Pod to a node → that node's kubelet sees the assignment and tells the runtime to pull the image and start containers → kubelet reports status back to the API server. Notice: components don't call each other directly. They watch the API server and react. That watch-and-reconcile pattern is the whole architecture.

◆ why the API-server-centric design matters

Because every component is a client of one API and persists nothing locally, the system is uniformly observable, extensible, and recoverable. Custom controllers and operators (§13) plug in the same way the built-ins do — they watch objects and reconcile. There's no privileged backchannel. This is why "everything is an object in etcd, reconciled by a loop" is the one sentence that explains Kubernetes.

03

Objects & manifests

Every Kubernetes object shares the same four-part shape. Learn it once and every manifest reads the same.

anatomy.yamlyaml
apiVersion: apps/v1          # which API group + version defines this kind
kind: Deployment             # the type of object
metadata:
  name: web                  # unique within its namespace
  namespace: shop            # the virtual cluster partition (default: "default")
  labels:
    app: web                 # key/value tags — the glue for selection
spec:                        # DESIRED state — what you declare
  replicas: 3
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:
        - name: web
          image: nginx:1.27
status:                      # ACTUAL state — written by the controller, not you
  readyReplicas: 3
the four top-level keys, on every object
apiVersionThe API group and version (apps/v1, v1, networking.k8s.io/v1). Groups namespace the API and let features evolve. Using a removed version is the #1 cause of failed upgrades.
kindThe object type — Pod, Deployment, Service. apiVersion + kind together identify the schema.
metadataIdentity: name, namespace, labels, annotations, uid. Labels are for selection; annotations are for non-identifying data (tooling hints).
specYou write this. The desired state.
statusThe controller writes this. Observed actual state. The gap between spec and status is what every controller works to close.

Labels & selectors — the glue

Kubernetes has almost no hard references between objects. A Deployment doesn't "contain" Pods; it owns Pods whose labels match its selector. A Service doesn't list endpoints; it routes to Pods matching its selector. This loose coupling via labels is how everything connects.

▲ gotcha — a Deployment's selector is immutable

Once set, spec.selector can't be changed (you'd orphan the existing Pods). And if a Service's selector matches the wrong labels — or none — it silently routes to nothing and you get connection refused with no error in the manifest. When traffic mysteriously goes nowhere, check that selectors and Pod labels actually match.

Declarative vs imperative

apply, don't runbash
kubectl apply -f deploy.yaml     # declarative: reconcile cluster to this file (idempotent)
kubectl diff -f deploy.yaml      # preview what apply would change
kubectl create deploy web --image=nginx   # imperative: fine for scratch work, not prod
◆ why declarative wins

apply is idempotent and diff-able: the same file run twice is a no-op, and your manifests live in Git as the reviewed source of truth (the basis of GitOps, §13). Imperative kubectl create/edit/scale mutate the cluster out of band, so your repo no longer describes reality. Use imperative commands to explore; commit declarative YAML to ship.

04

Pods

The Pod is the atom of scheduling — one or more containers that share a network namespace and storage, always co-located on one node.

A Pod is not a container; it's a group of containers that live and die together, share one IP and localhost, and can share volumes. Usually it's one app container plus optional helpers. You rarely create Pods directly — a controller (§05) does — but the Pod spec is embedded everywhere, so it's the spec to know cold.

pod.yaml — the fields that matteryaml
apiVersion: v1
kind: Pod
metadata: { name: web, labels: { app: web } }
spec:
  initContainers:                       # run to completion BEFORE app containers start
    - name: migrate
      image: myapp:1.4
      command: ["./migrate"]
  containers:
    - name: app
      image: myapp:1.4
      ports: [{ containerPort: 8080 }]
      env:
        - name: LOG_LEVEL
          value: "info"
      resources:
        requests: { cpu: "250m", memory: "256Mi" }   # scheduler reserves this
        limits:   { cpu: "500m", memory: "512Mi" }   # hard ceiling; OOM-killed if exceeded
      livenessProbe:                    # restart the container if this fails
        httpGet: { path: /healthz, port: 8080 }
        initialDelaySeconds: 5
        periodSeconds: 10
      readinessProbe:                   # remove from Service endpoints if this fails
        httpGet: { path: /ready, port: 8080 }
    - name: log-shipper                 # a SIDECAR
      image: fluent-bit:3
      restartPolicy: Always             # <-- this makes it a native sidecar (stable 1.33)
  restartPolicy: Always
the high-value fields
requests / limitsrequests = what the scheduler reserves (and uses to place the Pod). limits = the hard cap; exceed memory and the container is OOM-killed, exceed CPU and it's throttled. These two numbers drive scheduling, density, and stability.
livenessProbe"Is it alive?" Fails → kubelet restarts the container. Misconfigured liveness probes cause restart loops — a classic outage.
readinessProbe"Can it serve traffic?" Fails → Pod is pulled from Service endpoints but not restarted. This is how rolling deploys avoid sending traffic to a not-yet-warm Pod.
startupProbeFor slow starters: holds off liveness/readiness until the app has booted, so a long warmup isn't mistaken for a hang.
initContainersRun sequentially to completion before app containers — migrations, waiting on a dependency, fetching config.
sidecar (restartPolicy: Always on a container)A long-running helper (proxy, log shipper) that K8s now manages natively: started before the app, kept alive alongside it, terminated after it. Stable since 1.33.
◆ QoS classes — derived from requests/limits

The values you set silently assign a Quality-of-Service class that decides eviction order under node pressure: Guaranteed (limits == requests for all resources) is evicted last; Burstable (requests < limits) is in the middle; BestEffort (nothing set) is killed first. Setting requests==limits on critical Pods is how you make them sticky under memory pressure.

▲ gotcha — Pods are cattle, not pets

A Pod has no durability guarantee. Its name and IP are ephemeral; reschedule it and both change. Never point a client at a Pod IP, never store durable data in a Pod's writable layer, and don't expect a Pod to come back — expect a new one. Stable identity and storage come from higher-level objects (Services, StatefulSets, PVCs), not Pods.

05

Workload controllers

You don't run bare Pods. You declare a controller that owns Pods and keeps the right number of the right ones running.

ControllerUse forKey property
DeploymentStateless appsRolling updates + rollback, manages a ReplicaSet
ReplicaSet(low-level)Keeps N identical Pods; you rarely touch it directly
StatefulSetDatabases, clustered stateful appsStable network IDs + per-Pod persistent storage, ordered rollout
DaemonSetNode agents (logging, CNI, monitoring)Exactly one Pod per (matching) node
JobRun-to-completion batchRuns Pods until N successes, then stops
CronJobScheduled batchCreates Jobs on a cron schedule

Deployment — the workhorse

A Deployment manages a ReplicaSet, which manages Pods. Change the Pod template (e.g. a new image) and the Deployment performs a controlled rolling update: spin up new Pods, wait for them to pass readiness, then retire old ones, bounded by maxSurge/maxUnavailable.

rollout controlbash
kubectl set image deploy/web app=myapp:1.5   # triggers a rolling update
kubectl rollout status deploy/web            # watch it converge
kubectl rollout undo deploy/web              # roll back to the previous ReplicaSet
kubectl rollout history deploy/web
◆ why the ReplicaSet layer exists

Each Deployment revision is a separate ReplicaSet. During a rollout, the new RS scales up while the old scales down; on rollback, the old RS scales back up. Keeping old ReplicaSets around (at scale 0) is what makes instant rollback possible — there's no rebuild, just a re-scale of a Pod template that already worked.

StatefulSet — when identity matters

For databases and anything that can't treat its replicas as interchangeable, a StatefulSet gives each Pod a stable, ordinal name (db-0, db-1), a stable DNS hostname, and its own persistent volume that follows it across reschedules. Pods are created/updated/deleted in order.

▲ gotcha — StatefulSet ≠ free distributed database

It gives stable identity and storage, not replication, leader election, or consensus. Your app still has to handle clustering. And scaling down doesn't delete the PersistentVolumeClaims by default — data persists, which is usually what you want, but it surprises people when storage costs don't drop after a scale-down.

06

Services & DNS

Pods are ephemeral with changing IPs. A Service is the stable address in front of a churning set of them.

The cluster networking model is flat: every Pod gets its own routable IP, and any Pod can reach any other Pod's IP directly, no NAT, across nodes (the CNI plugin makes this true). But Pod IPs change constantly, so you don't target them — you target a Service, which gives a stable virtual IP and DNS name and load-balances across the Pods matching its selector.

Service typeWhat it does
ClusterIPDefault. A stable in-cluster virtual IP. Only reachable inside the cluster. Most Services are this.
NodePortOpens the same high port on every node, forwarding to the Service. Crude external access; mostly a building block.
LoadBalancerProvisions a cloud load balancer (via the cloud-controller-manager) with an external IP. The standard way to expose a single service externally.
headless (clusterIP: None)No virtual IP — DNS returns the Pod IPs directly. Used by StatefulSets so clients can address individual Pods.
service.yamlyaml
apiVersion: v1
kind: Service
metadata: { name: web, namespace: shop }
spec:
  selector: { app: web }     # routes to Pods with label app=web (the loose coupling again)
  ports:
    - port: 80               # the Service's port
      targetPort: 8080       # the container's port
  type: ClusterIP
◆ how a Service IP actually works — and DNS

A Service's ClusterIP is virtual — nothing listens on it. kube-proxy (or a CNI's eBPF dataplane) programs each node so traffic to that IP is load-balanced to a healthy backing Pod, tracked via EndpointSlices (the readiness-gated list of Pod IPs). Cluster DNS (CoreDNS) gives every Service a name: web.shop.svc.cluster.local, usually shortened to web within the same namespace. So apps connect to http://web and never see a Pod IP.

▲ gotcha — only Ready Pods receive traffic

A Pod joins its Service's EndpointSlice only when its readiness probe passes. No readiness probe means a Pod is "ready" the instant its process starts — so traffic can hit it before it's warm. Conversely a failing readiness probe quietly removes a Pod from rotation with no restart, which can look like "my Service is dropping requests" when it's actually doing its job. Always define readiness probes for anything that serves traffic.

07

Ingress & Gateway API

North-south traffic: getting HTTP from the outside world to the right Service by host and path. This is where 2026 looks different.

Ingress — the incumbent

An Ingress object declares HTTP routing rules (host + path → Service), and an ingress controller (NGINX, Traefik, a cloud LB) watches those objects and configures the actual proxy. One external load balancer can fan out to many Services by hostname/path, with TLS termination.

▲ gotcha — Ingress is frozen, and Ingress-NGINX is retiring

The Ingress API is feature-frozen — anything beyond basic host/path routing (rewrites, auth, canary) lives in controller-specific annotations, which are non-portable and a known source of pain. More urgently: the upstream Ingress-NGINX controller is being retired in 2026 (no further releases). If you depend on it, plan a migration — there's no drop-in replacement.

Gateway API — the successor

Gateway API is the modern, role-oriented replacement (Standard channel GA, v1.5 in 2026). It splits the one overloaded Ingress object into typed, layered resources owned by different roles — infrastructure vs. app teams — and moves routing features into the spec instead of annotations.

ResourceOwned byDeclares
GatewayClassInfra providerWhich implementation backs Gateways (like a StorageClass for ingress)
GatewayCluster/infra teamAn actual listener: ports, protocols, TLS, hostnames
HTTPRouteApp teamRouting rules: match host/path/header → backend Service. Also GRPCRoute, TCPRoute
httproute.yamlyaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: web }
spec:
  parentRefs: [{ name: prod-gateway }]    # attach to a Gateway listener
  hostnames: ["shop.example.com"]
  rules:
    - matches: [{ path: { type: PathPrefix, value: /api } }]
      backendRefs: [{ name: api, port: 80 }]      # canary/splitting via weights here
    - matches: [{ path: { type: PathPrefix, value: / } }]
      backendRefs: [{ name: web, port: 80 }]
◆ why Gateway API, and what to choose now

Three wins over Ingress: portability (header matching, traffic splitting, redirects are first-class fields, not vendor annotations), role separation (platform owns Gateways, app teams own their HTTPRoutes without touching shared infra), and protocol breadth (HTTP, gRPC, TCP, TLS). For new clusters, start with Gateway API. For existing Ingress, it works alongside — migrate incrementally, prioritizing anything on the retiring Ingress-NGINX.

Config & secrets

Keep configuration out of the image. ConfigMaps for plain config, Secrets for sensitive values — injected as env vars or mounted files.

configmap + secret + consumptionyaml
apiVersion: v1
kind: ConfigMap
metadata: { name: web-config }
data:
  LOG_LEVEL: "info"
  config.yaml: |                 # whole files live here too
    feature_x: true
---
apiVersion: v1
kind: Secret
metadata: { name: web-secret }
type: Opaque
data:
  DB_PASSWORD: c3VwZXJzZWNyZXQ=  # base64 — NOT encryption (see gotcha)
---
# in the Pod spec:
#   envFrom: [{ configMapRef: { name: web-config } }]
#   env:
#     - name: DB_PASSWORD
#       valueFrom: { secretKeyRef: { name: web-secret, key: DB_PASSWORD } }
#   volumeMounts: [{ name: cfg, mountPath: /etc/app }]
# volumes: [{ name: cfg, configMap: { name: web-config } }]
▲ gotcha — Secrets are base64, not encrypted

A Secret's data is base64-encoded, which is encoding, not security — anyone with read access decodes it instantly. Real protection requires three things you must turn on: encryption at rest for etcd (so the API server encrypts Secret data before storing it), RBAC restricting who can read Secrets (§12), and ideally an external secrets manager (Vault, cloud KMS, External Secrets Operator) so the real secret never lives in Git or plain etcd. Treating base64 as a security boundary is a classic, dangerous mistake.

env vars vs mounted files

MethodBehavior
env / envFromInjected at container start. Does not update if the ConfigMap/Secret changes — the Pod must restart to pick up new values.
volume mountMounted as files; updates in place (eventually) when the source changes — though your app has to re-read the file to notice.
◆ immutable ConfigMaps & the rollout trick

Mark a ConfigMap/Secret immutable: true to prevent edits and cut API-server load (the kubelet stops watching it). But then how do you change config? You create a new versioned object (web-config-v2) and update the Pod template to reference it — which changes the template hash and triggers a clean rolling deploy. This "config change = new immutable object = rollout" pattern gives you the same rollback story as code, and avoids the silent-staleness of edited env-injected ConfigMaps.

09

Storage

Container filesystems are ephemeral. Durable data needs Volumes — and for real persistence, the PV/PVC/StorageClass triad.

A container's writable layer vanishes when it restarts. Volumes outlive the container (but most are tied to the Pod). For data that must survive Pod deletion and rescheduling, Kubernetes separates what the app asks for from what the cluster provides:

ObjectRoleAnalogy
PersistentVolumeClaim (PVC)The app's request: "I need 10Gi, ReadWriteOnce". Written by the app team.A request for storage
PersistentVolume (PV)An actual piece of storage (a cloud disk, NFS share). Bound to a PVC.The fulfilled storage
StorageClassA template for dynamically provisioning PVs on demand (disk type, IOPS, the CSI driver to use).The "menu" of storage tiers
pvc.yaml — dynamic provisioningyaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: data }
spec:
  accessModes: ["ReadWriteOnce"]      # one node mounts it read-write
  storageClassName: fast-ssd          # which StorageClass provisions the PV
  resources:
    requests: { storage: 10Gi }
# A StorageClass + CSI driver auto-creates a matching PV and binds it.
# In the Pod:  volumes: [{ name: data, persistentVolumeClaim: { claimName: data } }]
◆ access modes & the CSI

RWO (ReadWriteOnce) = one node at a time — block storage (most cloud disks). RWX (ReadWriteMany) = many nodes simultaneously — requires a network filesystem (NFS, CephFS); most block disks cannot do RWX. The CSI (Container Storage Interface) is the plugin standard: every storage backend ships a CSI driver, so Kubernetes core has no vendor storage code. Choosing RWX when your backend only supports RWO is a common reason multi-replica Pods fail to schedule.

▲ gotcha — reclaim policy & StatefulSet volumes

A StorageClass's reclaimPolicy decides what happens to the PV when its PVC is deleted: Delete (the default for dynamic provisioning) destroys the underlying disk — fine for caches, catastrophic for a database if you delete the PVC by accident. Use Retain for anything precious. And StatefulSet Pods get their storage from volumeClaimTemplates (one PVC per Pod, e.g. data-db-0); deleting the StatefulSet leaves those PVCs behind on purpose, so the data survives — clean them up explicitly when you really mean to.

10

Scheduling

How a Pod gets matched to a node. The scheduler filters, then scores — and you steer it with requests, affinity, and taints.

For each unscheduled Pod the scheduler runs two phases: filtering (which nodes can run it — enough free resources, satisfies affinity, tolerates taints) then scoring (rank the survivors and pick the best). The single most important input is the Pod's resource requests: a node must have that much unreserved capacity, and over-requesting wastes the cluster while under-requesting risks contention.

MechanismWhat it controls
nodeSelectorSimplest: only nodes with these labels (e.g. disktype: ssd).
node affinityRicher node selection — required ("must") or preferred ("nice to have"), with expressions.
pod (anti-)affinityPlace Pods near (affinity) or apart from (anti-affinity) other Pods — e.g. spread replicas across nodes, or co-locate with a cache.
taints & tolerationsA taint repels Pods from a node unless the Pod has a matching toleration. The inverse of selection: nodes opt out by default.
topologySpreadConstraintsEvenly distribute Pods across failure domains (zones, nodes) to survive a zone loss.
priorityClassHigher-priority Pods can preempt (evict) lower-priority ones when the cluster is full.
◆ taints vs affinity — the direction differs

Easy to confuse. Node affinity is the Pod saying "I want to run on nodes like this." A taint is the node saying "keep Pods off me unless they explicitly tolerate this." Control-plane nodes are tainted so normal workloads don't land on them; GPU nodes are tainted so only GPU Pods (with the toleration) use the expensive hardware. Use affinity to attract, taints to repel.

▲ gotcha — "Pending" almost always means unschedulable

A Pod stuck in Pending usually can't be placed: not enough CPU/memory anywhere, a PVC that won't bind, an affinity rule nothing satisfies, or a taint with no toleration. kubectl describe pod <name> spells out exactly which filter failed in the Events section. Don't guess — read the events.

Scaling

Three axes: more Pods (horizontal), bigger Pods (vertical), and more nodes (cluster). Each has its own controller.

AutoscalerAdjustsBased on
HPA (Horizontal Pod Autoscaler)Replica count of a DeploymentCPU/memory or custom/external metrics
VPA (Vertical Pod Autoscaler)A Pod's requests/limitsObserved usage over time
in-place resizeA running Pod's CPU/memoryManual or VPA — no restart (stable 1.35)
Cluster Autoscaler / KarpenterNumber of nodesPending Pods that don't fit
hpa.yamlyaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: web }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: web }
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 70 }   # scale to hold ~70% CPU
◆ how the layers cooperate — and clash

The healthy chain: HPA adds Pods when load rises → if Pods can't be placed, the Cluster Autoscaler / Karpenter adds nodes → when load falls, both scale back. HPA needs the metrics-server installed, and only works well when requests are set sanely (utilization is measured against the request). Don't run HPA and VPA on the same metric (e.g. both on CPU) — they fight: VPA shrinks the Pod, which spikes utilization, which makes HPA add Pods, and round it goes. In-place resize now lets VPA adjust a Pod without the disruptive restart it used to require.

▲ gotcha — no requests, no HPA

CPU-based HPA computes utilization as usage ÷ request. If a Pod has no CPU request, there's nothing to divide by and the HPA can't compute a target — it just won't scale. Resource requests aren't optional bookkeeping; they're the foundation scheduling, QoS, and autoscaling all stand on.

12

Security & RBAC

Who can do what (RBAC), what a Pod is allowed to be (Pod Security), and who can talk to whom (NetworkPolicy).

RBAC — authorization

Role-Based Access Control governs every API call. A Role (namespaced) or ClusterRole (cluster-wide) lists allowed verbs on resources; a RoleBinding/ClusterRoleBinding grants that Role to a subject — a user, group, or ServiceAccount (the identity Pods run as).

rbac.yaml — least privilegeyaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { namespace: shop, name: pod-reader }
rules:
  - apiGroups: [""]                 # "" = the core API group
    resources: ["pods"]
    verbs: ["get", "list", "watch"] # read-only, pods only, this namespace only
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata: { namespace: shop, name: read-pods }
subjects:
  - kind: ServiceAccount
    name: web
roleRef: { kind: Role, name: pod-reader, apiGroup: rbac.authorization.k8s.io }
▲ gotcha — the default ServiceAccount & over-broad roles

Every Pod runs as a ServiceAccount (the namespace's default if you don't specify one), and its token is mounted into the Pod. If that account has broad permissions, a compromised container inherits them. Give each workload its own narrowly-scoped ServiceAccount, and disable token automounting where the Pod doesn't call the API. Never bind cluster-admin to anything you don't have to — RBAC is allow-list, so start from nothing and add.

Pod Security Admission & Standards

PodSecurityPolicy was removed; the replacement is Pod Security Admission — a built-in admission controller that enforces the Pod Security Standards per namespace via labels. Three levels:

LevelMeans
privilegedNo restrictions. For trusted infra workloads only.
baselineBlocks known privilege escalations (host namespaces, privileged containers).
restrictedHardened best practice: non-root, no privilege escalation, dropped capabilities, seccomp. The target for app namespaces.
enforce on a namespace + container hardeningyaml
# label the namespace to enforce a standard:
#   pod-security.kubernetes.io/enforce: restricted
securityContext:                 # per-container hardening that "restricted" expects
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities: { drop: ["ALL"] }
  seccompProfile: { type: RuntimeDefault }

NetworkPolicy — segmentation

◆ why you need NetworkPolicy

By default the flat Pod network means any Pod can talk to any Pod — a single compromised container can reach your database. A NetworkPolicy is a per-namespace allow-list of ingress/egress by Pod label, namespace, or IP block. Once any policy selects a Pod, everything not explicitly allowed is denied. It requires a CNI that enforces policy (Calico, Cilium); a policy with no enforcing CNI does nothing — a silent false sense of security. Default-deny plus explicit allows is the baseline for a real zero-trust posture inside the cluster.

Ops & ecosystem

Raw YAML doesn't scale to many apps and environments. This is the layer teams actually operate with: packaging, GitOps, debugging, and extending the API.

GitOps

◆ why GitOps is the 2026 default

Instead of running kubectl apply from a laptop or CI, an in-cluster agent (Argo CD or Flux) continuously watches a Git repo and reconciles the cluster to match it — the same desired-state loop as Kubernetes itself, extended to your manifests. Git becomes the single source of truth: every change is a reviewed, audited, revertible commit, and the cluster self-corrects drift. It composes naturally with Helm/Kustomize, which render the manifests the agent applies.

Extending the API: CRDs & Operators

A CustomResourceDefinition adds your own object kind to the API server, served and stored like any built-in. An Operator is a custom controller that reconciles those resources — encoding operational knowledge ("how to run Postgres") as the same watch-and-reconcile loop the built-ins use. This is how databases, message queues, and cert managers ship as first-class Kubernetes objects.

triage toolkitbash

kubectl debug <pod> -it --image=busybox   # ephemeral debug container (no shell in image)

◆ reading a Pod's state

Pending = not scheduled (resources/affinity/PVC — see §10). CrashLoopBackOff = the container starts then exits repeatedly; logs --previous shows why, and the back-off is K8s slowing the restarts, not the bug. ImagePullBackOff = can't fetch the image (typo, private registry, missing pull secret). OOMKilled in describe = exceeded its memory limit. Ninety percent of triage is describe + logs + events.

The seven things people get wrong

  1. No resource requests → broken scheduling, QoS, and autoscaling all at once.
  2. No readiness probe → traffic hits cold or dead Pods.
  3. Treating base64 Secrets as encryption → secrets effectively in plaintext.
  4. Pointing clients at Pod IPs instead of Services → breaks on every reschedule.
  5. Mismatched Service/Pod selector labels → traffic silently goes nowhere.
  6. Over-broad RBAC on the default ServiceAccount → a container breakout owns the cluster.
  7. Liveness probe too aggressive → healthy Pods restart-loop themselves into an outage.
