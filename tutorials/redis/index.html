Orientation

Redis is a data-structure server

Not "a cache." A single-threaded, in-memory engine that exposes data structures — strings, hashes, lists, sets, sorted sets, streams, bitmaps, HyperLogLog, geo — behind atomic commands. Every design decision (speed, atomicity, the pitfalls) falls out of those two words: in-memory and single-threaded.

One thread, executing commands one-at-a-time over in-memory structures — atomicity is free. Persistence (AOF/RDB) and replicas are bolted on around that core.

Five facts that explain everything else

  1. In-memory → sub-millisecond ops, but your dataset must fit in RAM (per shard), and memory is the scaling ceiling, not CPU or disk.
  2. Single-threaded command execution → each command is atomic with no locking, but one slow command (KEYS, a big SMEMBERS, a heavy Lua script) blocks every other client. Latency discipline is the whole game.
  3. Data structures, not rows → you pick the structure that makes your access pattern O(1) or O(log n). Modeling Redis = "which structure answers this read cheapest?"
  4. Derived/ephemeral by default → replication is asynchronous, so a failover can lose the last few writes. Redis is a brilliant cache/index/serving layer, a risky system-of-record for money.
  5. Keys are flat & global → no nesting of keys; structure lives inside a value. Your key naming scheme (user:123:cart) is your schema.
How to read this book

Foundations = the model, protocol, and memory. Data structures = every type, its internals, Big-O, and what it's for. Access & patterns = pagination, filtering, indexing, locks, queues. Operating at scale = persistence, eviction, replication, Cluster, pitfalls. Each structure page ends with an ASK-ME block — the cross-questions an interviewer fires, pre-answered, so you don't stutter.

Foundations · 01

The single thread, RESP & pipelining

Redis serves enormous throughput from one command thread. Understanding why — and where the other threads are — is the difference between "Redis is fast" hand-waving and an answer that survives probing.

Why one thread is fast, not slow

In-memory operations are nanoseconds; the bottleneck is the network and syscalls, not CPU. A single thread driving an epoll/kqueue event loop avoids lock contention, context switches, and cache-coherency traffic that would dog a multi-threaded design. The result: a commodity box does 100k–1M+ ops/sec on simple commands. CPU is rarely the limit; memory bandwidth and network are.

What actually is multi-threaded

The command execution is single-threaded, but Redis offloads side work to background threads: I/O threads (since 6.0) parallelize reading/writing socket buffers (parsing the request, sending the reply) while execution stays serial; lazy-free / UNLINK reclaims big objects on a background thread so deletion doesn't stall the loop; RDB/AOF persistence forks a child process. So "single-threaded" precisely means: the logical command runs serially against the keyspace.

The blocking trap

Because execution is serial, an O(N) command on a huge key freezes the whole server for its duration. KEYS *, SMEMBERS on a million-element set, HGETALL on a giant hash, FLUSHALL (sync), or a slow Lua script will spike p99 for every client. Prefer the SCAN family, bounded ranges, and UNLINK over DEL for big keys.

RESP — the wire protocol

Clients speak RESP (REdis Serialization Protocol): a simple, line-based, binary-safe format. First byte signals type — + simple string, - error, : integer, $ bulk string, * array (RESP3 adds maps, sets, doubles, push). It's human-readable and cheap to parse, which is part of why latency is low.

Pipelining vs round-trips

Each command normally costs one network round-trip (RTT). Pipelining sends N commands without waiting for replies, then reads N replies — turning N×RTT into ~1×RTT plus server processing. This is the single biggest client-side throughput win and is independent of MULTI (pipelining is about batching the network; MULTI is about atomicity).

# 1000 SETs, one round-trip instead of 1000
SET k:1 v1
SET k:2 v2
... (buffered, flushed together) ...
SCAN cursor [MATCH p] [COUNT n] [TYPE t]O(1) per call
Cursor-based, non-blocking iteration of the keyspace. Returns a slice + next cursor; guarantees every key present for the whole scan is returned at least once (may return duplicates, may miss keys added/removed mid-scan). The only safe way to walk keys in production. Siblings: HSCAN, SSCAN, ZSCAN for fields inside one key. COUNT is a hint, not a page size.
Ask me

If it's single-threaded, how does it do a million ops/sec?

In-memory ops are nanoseconds; the work is network + parsing, which I/O threads parallelize while execution stays serial. No locks, no context switches. CPU isn't the bottleneck — memory bandwidth and NIC are.

So one bad query takes everyone down?

Latency-wise, yes — a long O(N) command blocks the loop and spikes everyone's p99. That's why KEYS is banned in prod, big deletes use UNLINK, and iteration uses SCAN.

Difference between pipelining and MULTI?

Pipelining batches the network (fewer round-trips, no atomicity guarantee). MULTI/EXEC batches for atomicity (no other command interleaves). You often pipeline a MULTI block to get both.

Foundations · 02

Memory, encodings & key design

RAM is the budget you spend. Redis quietly switches each structure between a compact and a full encoding based on size — knowing the thresholds is how you keep a 100M-key dataset affordable.

Dual encodings: compact below a threshold, full above

Small collections use cache-friendly contiguous encodings; once they cross a configured limit they convert (one-way) to the full structure. Check with OBJECT ENCODING key.

The lesson: many small structures are cheaper than few huge ones, and huge ones are cheaper kept under the listpack threshold. A hash of 100 fields in listpack form can be an order of magnitude more memory-efficient than 100 separate keys (each key carries dict + expire + object overhead, ~tens of bytes).

The "hash-bucketing" memory trick

Instagram's classic optimization: instead of user:1000000 → id as a million top-level keys, bucket them into hashes of ~1000 fields — users:1000 → {000..999: id}. The hashes stay in listpack encoding, slashing per-key overhead. Same lookup, a fraction of the RAM. This is "bucketing" for memory (distinct from time-bucketing for hot keys, covered later).

Key design = your schema

  • Namespacing: colon-delimited, coarse→fine: app:entity:id:attr e.g. order:9f2:items. Consistent prefixes make SCAN MATCH and eviction reasoning sane.
  • Keep keys short but readable — every key string lives in RAM, but clarity usually wins over saving 4 bytes.
  • One structure per access pattern — like Cassandra, you may store the same data twice under two keys if two reads need two shapes.
  • Hash tags {…} force keys onto the same Cluster slot so multi-key ops work (see Cluster page): cart:{user42}:items, cart:{user42}:total.
Big keys & the 5 % rule

A single key holding millions of elements (a giant set/zset/hash) is a latency bomb: O(N) commands on it block the loop, it can't be split across the cluster, and deleting it stalls everything. Keep collections bounded (thousands, not millions); shard a logical big collection across many keys by bucket. Watch memory with redis-cli --bigkeys and MEMORY USAGE key.

The modeling reflex

"What's the cheapest read?" → need ranking or range-by-score or pagination? sorted set. Membership / set algebra? set. A record I patch field-by-field? hash. FIFO/LIFO or recent-N? list. Ad-hoc queries across keys (no SELECT … WHERE over the keyspace — that's SCAN or a manual index), joins, secondary-attribute filtering without a built index, anything bigger than RAM, and being a durable ledger. Data structures · 01

Strings, counters, bitmaps & HyperLogLog

The string is the atom — but Redis overloads it into atomic counters, bit-addressable flags, and probabilistic cardinality. These power rate limiting, presence, and "how many uniques" at scale.

Strings & atomic counters

SET key val [EX s|PX ms] [NX|XX] [GET]O(1)
The workhorse. NX = set only if absent (the basis of locks & idempotency keys), XX = only if present, EX/PX = TTL set atomically with the value. GET returns the old value in the same atomic op.
INCR / INCRBY / DECR / INCRBYFLOAT keyO(1)
Atomic counters with no read-modify-write race — the single thread guarantees it. Page views, stock decrements, ID generation, sliding counters. INCRBYFLOAT for fractional.
Flash-sale / oversell guard

Preload stock as an integer, then gate each buy with an atomic decrement that refuses to go negative — a tiny Lua script: if DECR ≥ 0 then ok else INCR (undo) end. Single-threaded execution means no two buyers can both pass the last unit. Reconcile to the durable order store async. This is the canonical hot-key counter pattern.

Rate limiting

  • Fixed window: INCR rate:user:{id}:{minute} with EXPIRE 60s; reject when > limit. Cheap, but allows 2× burst at window edges.
  • Sliding window / token bucket: a Lua script over a small sorted set (timestamps) or counters refilled by elapsed time — smooth, accurate, atomic.

Bitmaps — one bit per entity

A bitmap is just a string addressed at the bit level. 1 bit per user × millions of users = a few hundred KB. Perfect for daily-active flags, feature cohorts, attendance.

SETBIT key offset 0|1 · GETBIT · BITCOUNT · BITOPSET/GET O(1), COUNT O(N)
SETBIT active:2026-06-20 {userId} 1 marks a user active today. BITCOUNT = today's DAU. BITOP AND dst day1 day2 = users active both days (retention). BITOP OR over 7 daily keys = weekly actives.

HyperLogLog — count uniques in ~12 KB

When you need "how many distinct X" at billions scale and can tolerate ~0.81 % error, HLL stores a probabilistic sketch in a fixed ~12 KB regardless of cardinality — versus a set that would need gigabytes.

PFADD key elem… · PFCOUNT key… · PFMERGE dst src…O(1) add, O(1) count
Unique visitors per page/day, distinct search terms, dedup-counting at scale. PFMERGE unions sketches (weekly uniques from 7 daily HLLs). You get the count, never the members — that's the trade for the tiny footprint.
Ask me

Counter is one hot key — doesn't that bottleneck?

On one node, atomic INCR handles ~100k+/s — usually fine. If truly extreme, shard the counter into N sub-keys (cnt:{id}:0..N), increment a random one, sum on read — trading read cost for write spread.

Why HLL over a set for unique counts?

A set is exact but grows with cardinality (GBs for billions). HLL is fixed ~12 KB with ~0.81 % error and O(1) ops. Use a set only when you must enumerate members or need exactness.

Fixed vs sliding window rate limiting?

Fixed window is one INCR+TTL — cheap but allows edge bursts (2× at the boundary). Sliding window (zset of timestamps or token bucket in Lua) is accurate and smooth at slightly more cost.

Data structures · 02

Hashes, lists & sets

The everyday three: a hash is a record, a list is a sequence/queue, a set is membership and algebra. Each has one or two "don't do that" edges worth knowing.

Hash — the record type

A field→value map under one key. Use it for an object you update field-by-field (a user profile, a cart line, a config blob) instead of serializing JSON into a string and rewriting the whole thing on every change.

HSET · HGET · HMGET · HINCRBY · HDEL · HGETALLfield ops O(1) · HGETALL O(N)
HSET user:42 name Abhi tier gold; HINCRBY user:42 visits 1 patches one counter atomically. Avoid HGETALL on large hashes (O(N) blocks); use HMGET for known fields or HSCAN to iterate. Per-field TTL exists in Redis 7.4+ (HEXPIRE).

List — ordered sequence & queues

A linked list (quicklist of listpacks). Pushes/pops at either end are O(1); indexing into the middle is O(N). It's a FIFO/LIFO, a capped "recent N" buffer, or a simple job queue.

LPUSH/RPUSH · LPOP/RPOP · LRANGE · LTRIM · BLPOP/BRPOP · LMOVEend ops O(1) · LRANGE/LINDEX O(N)
Queue: producers LPUSH, workers BRPOP (blocking pop — no busy-poll). Recent-N: LPUSH then LTRIM list 0 99 keeps only the latest 100. Reliable queue: LMOVE src dst (atomic move to a processing list so a crashed worker's item isn't lost). For real durability/acks, prefer Streams.

Set — membership & relationships

Unordered collection of unique members. O(1) add and membership test; set algebra (union/intersect/diff) is its superpower — think tags, unique visitors, "users who did X", common-friends.

SADD · SISMEMBER · SMISMEMBER · SCARD · SINTER · SUNION · SDIFF · SRANDMEMBER · SPOPSADD/SISMEMBER O(1) · set ops O(N)
SADD post:9:likes {userId}; SCARD = like count; SISMEMBER = "did I like it?". Common friends: SINTER friends:A friends:B. Dedup: SADD returns 1 only if new. Use SMISMEMBER (batch) and avoid SMEMBERS on big sets — use SSCAN.
The O(N) edges to never cross

HGETALL / SMEMBERS / LRANGE 0 -1 on a large key all return everything and block the loop. The fixes are uniform: bound the request (known fields, a range, a limit) or iterate with the SCAN family. "Is it O(N) on a key the user controls the size of?" is the question to ask of every command.

Ask me

Hash vs storing JSON in a string?

Hash lets you read/patch single fields O(1) without rewriting the whole blob, and small hashes are memory-efficient in listpack form. JSON-in-string is fine when you always read/write the whole object and don't need field-level ops (or use RedisJSON for nested querying).

List vs Stream for a queue?

List is simplest (LPUSH/BRPOP) but has no acks, no consumer groups, no replay — a crashed worker loses its in-flight item unless you use LMOVE. Streams add durability, consumer groups, acknowledgements, and replay. Pick Stream when at-least-once delivery matters.

Data structures · 03 · the important one

Sorted sets — the ranking engine

The structure interviews circle back to. A sorted set holds unique members each with a float score, kept in score order. It is simultaneously a leaderboard, a time-ordered index, a priority queue, a rate limiter, and a pagination cursor — because all of those are "ordered by a number."

Internals: skiplist + hashtable

A full zset is two structures kept in sync: a hashtable (member → score, for O(1) score lookup and dedup) and a skiplist (a probabilistic multi-level linked list giving O(log N) ordered insert, delete, and rank/range queries). Small zsets collapse to a single listpack until they cross the threshold. This dual structure is why ZSCORE is O(1) but ZRANGE is O(log N + M).

Express lanes (upper levels) let a search skip most nodes — O(log N) to locate, then a linear walk of M results. A parallel hashtable gives O(1) member→score and rank lookups.

The command surface (this is the page to memorize)

ZADD key [GT|LT|NX|XX] score member …O(log N) per member
Insert/update. GT only raises the score (perfect for "max score wins" leaderboards), LT only lowers, NX only adds new, XX only updates existing. ZADD GT board 5000 player7.
ZRANGE key start stop [BYSCORE|BYLEX] [REV] [LIMIT off cnt] [WITHSCORES]O(log N + M)
The unified range command (7.0+ folded in ZREVRANGE, ZRANGEBYSCORE, ZRANGEBYLEX). By rank: ZRANGE board 0 9 REV = top 10. By score: ZRANGE board (1000 5000 BYSCORE. LIMIT = offset/count for pagination.
ZRANK / ZREVRANK key member [WITHSCORE]O(log N)
A player's own rank — the thing a relational ORDER BY can't do cheaply. ZREVRANK board player7 → "you're #42". This is the killer feature: rank is maintained, not computed by counting.
ZSCORE · ZINCRBY · ZCARD · ZCOUNT · ZREM · ZPOPMIN/MAX · BZPOPMIN/MAXmostly O(1)–O(log N)
ZINCRBY board 10 p7 adds to a score atomically. ZPOPMIN = pop lowest (priority queue). BZPOPMIN = blocking variant (priority job queue). ZCOUNT board 1000 2000 = members in a score band.
ZRANGEBYLEX / ZLEXCOUNT (all scores equal)O(log N + M)
When every member shares one score, the set sorts lexicographically — turning a zset into an ordered string index for autocomplete/prefix search: ZRANGEBYLEX names [ab [ac finds members between two prefixes.

What you build with it

  • Leaderboard: ZADD GT on score; ZRANGE … REV LIMIT for top-N; ZREVRANK for a user's rank; ZINCRBY for deltas. O(log N) everywhere — the textbook fit.
  • Time-ordered index / feed: score = timestamp (or a Snowflake-style id). Range by score = "items between t1 and t2"; this is also your cursor pagination (next page).
  • Priority queue: score = priority/deadline; BZPOPMIN pulls the most urgent.
  • Sliding-window rate limit: ZADD a timestamp per request, ZREMRANGEBYSCORE to drop the old window, ZCARD to count — all in one Lua block.
  • Delayed/scheduled jobs: score = run-at epoch; a poller does ZRANGEBYSCORE … 0 now to claim due jobs.
Ask me

Why a zset for a leaderboard instead of SQL ORDER BY?

Top-N is fine in SQL, but a specific player's rank means counting everyone above them — O(N) without extra structure. A zset maintains rank inside the skiplist, so ZREVRANK is O(log N). And updates are O(log N), in-memory, sub-ms.

How do you paginate a zset?

Keyset/cursor pagination by score: fetch ZRANGE (lastScore +inf BYSCORE LIMIT 0 N, carry the last score+member as the cursor. Stable under inserts, unlike offset pagination. (Full page on this next.)

Two players tie on score — ordering?

Ties break by member lexicographic order. If you need a stable tiebreak (e.g. who reached the score first), encode it into the score: score = points * 1e7 + (1e7 - timestamp_bucket), so earlier achievers rank higher within the same points.

Millions of players in one zset — problem?

Memory and big-key risk. Ops stay O(log N), but one giant key can't shard across the cluster and blocks on O(N) ops. Bucket by league/region into many zsets, or cap to top-K and recompute the long tail offline.

Data structures · 04

Streams, Pub/Sub & messaging

Redis has three messaging primitives at different durability tiers: fire-and-forget Pub/Sub, simple list queues, and the durable, replayable Stream with consumer groups — a mini-Kafka inside Redis.

Streams — append-only log with consumer groups

A Stream is an append-only log of entries, each with an auto monotonic ID (<ms>-<seq>) and a set of field/value pairs. Unlike Pub/Sub, entries persist and can be re-read; unlike a list, multiple consumers can cooperate via consumer groups with per-message acknowledgement and redelivery.

XADD key [MAXLEN ~ N] * field val …O(1) (+O(log) trim)
Append an event; * auto-assigns the time-ordered ID. MAXLEN ~ 100000 caps the log (approximate trim is cheaper). The ID is your cursor and is globally ordered.
XREADGROUP GROUP g consumer … COUNT n BLOCK ms STREAMS key >O(N) read
> = "new messages never delivered to this group". Each message goes to exactly one consumer in the group (work sharing). Delivered-but-unacked entries sit in that consumer's PEL (Pending Entries List).
XACK · XPENDING · XCLAIM / XAUTOCLAIMO(1)–O(N)
XACK marks done (removes from PEL). XPENDING inspects stuck messages; XAUTOCLAIM lets a healthy consumer steal messages a crashed one never acked — that's your at-least-once redelivery and crash recovery.
A Stream fans work across a consumer group with acks and redelivery — durable, replayable, ordered. For a single broadcast with no persistence, Pub/Sub is lighter.

Pub/Sub — fire-and-forget broadcast

PUBLISH channel msg → all current SUBSCRIBErs receive it. No persistence, no replay, no acks: a subscriber that's offline or slow simply misses messages. Great for live notifications, cache-invalidation fan-out, presence — bad for anything that must not be lost. PSUBSCRIBE matches channel patterns; keyspace notifications publish events when keys change/expire.

Streams are not Kafka

Streams give you durable, grouped, replayable messaging — but the whole stream lives in one node's RAM (one key, not partitioned across the cluster), retention is memory-bound, and durability inherits Redis's async-replication tail-loss. For high-throughput, long-retention, partitioned event backbones, Kafka still wins. Redis Streams shine for in-process, low-latency work queues and moderate event fan-out.

Access & patterns · 01

Pagination, the right way

Redis has no OFFSET/LIMIT over the keyspace, and offset pagination is a trap even where it exists. The correct primitive is cursor (keyset) pagination — and the sorted set was built for it.

Two cursors: keyspace vs within-a-key

Across keys → SCAN (and HSCAN/SSCAN/ZSCAN within a key). These return an opaque cursor; you keep calling until it returns 0. They're non-blocking and bounded — the only safe iteration. They guarantee every element present throughout the scan is returned at least once (duplicates possible, so dedupe client-side if needed).

Ordered data → keyset pagination on a sorted set by score, which is what you want for feeds, leaderboards, and time-ranges.

Keyset pagination on a sorted set

Score-ordered data paginates by carrying the last score seen as the cursor, not a numeric offset. Each page is an O(log N + page) range starting just past the cursor.

# page 1 — newest first (score = timestamp)
ZRANGE feed:42 +inf -inf BYSCORE REV LIMIT 0 20 WITHSCORES
# cursor = score of the 20th item, say 1718900000
# page 2 — strictly older than the cursor
ZRANGE feed:42 (1718900000 -inf BYSCORE REV LIMIT 0 20

The ( makes the bound exclusive, so you never re-show the boundary item. If scores can tie (two items same timestamp), make the cursor a (score, member) pair and filter the equal-score boundary in the app, or bake a tiebreaker into the score so it's unique.

Why keyset beats offset

Offset pagination (LIMIT 1000, 20) must walk and discard 1000 elements — O(offset), and it skips or repeats items when the set changes between pages (someone posts, everything shifts by one). Keyset pagination is O(log N + page) regardless of depth and is stable under concurrent inserts because the cursor is anchored to a value, not a position. This is exactly the "Twitter timeline deep-scroll" pattern: the score/ID is the cursor.

The connection to durable stores

Same idea extends past Redis: when deep-scroll falls through the bounded Redis timeline to the durable store, you paginate there by a time-ordered ID (WHERE id < cursor ORDER BY id DESC LIMIT N). Cursor pagination isn't a Redis feature — it's a property of having an ordered key. Redis's zset just makes the ordered key in-memory and O(log N).

Ask me

Why not KEYS pattern to list keys for a page?

KEYS is O(N) over the entire keyspace and blocks the single thread — it can freeze a busy server for seconds. SCAN is the non-blocking, cursor-based, production-safe replacement.

User posts mid-scroll — does the cursor break?

No. Keyset pagination anchors to a score/value, so new inserts above the cursor don't shift the page boundary. You might miss the brand-new item until a refresh, but you never duplicate or skip existing ones — the correct trade.

How do you do "jump to page 50"?

You generally can't cheaply with keyset — that's offset's one advantage. If random-page access is a hard requirement, store an offset index or accept O(offset). Most feeds only need next/prev, so keyset wins.

Access & patterns · 02

Filtering & secondary indexes

Redis can't WHERE attr = x across keys — there's no query planner over the keyspace. You either build the index by hand with sets/zsets, or bring in RediSearch for real inverted-index queries.

Hand-rolled indexes (the idiomatic way)

An "index" in plain Redis is just another key whose members are the IDs matching a property. You maintain it on write; you intersect it on read.

  • Equality / tag index → set: SADD idx:status:active 42 99. Query "active users": SMEMBERS idx:status:active (or SSCAN).
  • Range / numeric index → sorted set: ZADD idx:price 19.99 sku123. Query "price 10–50": ZRANGEBYSCORE idx:price 10 50.
  • Compound filter → set algebra: "active AND tier=gold AND price<50" = ZINTERSTORE/SINTER across the per-property indexes (zsets and sets can be combined, weighting scores).
  • Sorted result → keep the sort key as the zset score so the intersection comes back already ordered.
# maintained on every write:
SADD idx:tag:gold user:42
ZADD idx:lastSeen 1718900000 user:42
# query: gold users, most-recent first, page 1
ZINTERSTORE tmp 2 idx:lastSeen idx:tag:gold WEIGHTS 1 0
ZRANGE tmp +inf -inf BYSCORE REV LIMIT 0 20
You own consistency now

Hand-built indexes must be updated atomically with the data (a MULTI or Lua block writing both the record and every index it belongs to), or they drift. Every new filterable attribute is another index to maintain on create/update/delete. This is the cost that pushes teams toward RediSearch or a real database once filters multiply.

RediSearch — actual queries

The RediSearch module adds a true inverted index over hash/JSON fields: full-text (tokenization, stemming, fuzzy), numeric & geo filters, tags, sorting, and aggregations — without you hand-maintaining sets. You FT.CREATE an index schema, write normal hashes, and FT.SEARCH/FT.AGGREGATE.

FT.CREATE idx:products ON HASH PREFIX 1 product: SCHEMA
  name TEXT price NUMERIC SORTABLE tags TAG
FT.SEARCH idx:products "@tags:{gold} @price:[10 50] running" SORTBY price LIMIT 0 20

This is the bridge between "Redis as cache" and "Redis as a queryable store" — but it's a module (Redis Stack / Redis Enterprise), it builds and holds the index in memory, and it's still not a replacement for a full-text engine at search-engine scale. For tweet-style keyword search at billions of docs, Elasticsearch is the right tool; RediSearch fits moderate, latency-critical filtered lookups on hot data.

Ask me

How do you query "users where city=NYC and age>30" in plain Redis?

Maintain a set idx:city:NYC and a zset idx:age; intersect SINTER/ZRANGEBYSCORE results. Each filterable attribute is a pre-built index updated on write. If filters get rich, switch to RediSearch.

RediSearch vs Elasticsearch?

RediSearch is in-memory, sub-ms, great for filtered lookups on hot data and tight latency budgets. ES is disk-based, scales to billions of docs, richer relevance/analyzers. Use ES for large-corpus keyword search; RediSearch for fast filters on a working set.

Access & patterns · 03

Atomicity: transactions, Lua & locks

Single-command atomicity is free. For multi-step atomicity you have three tools — MULTI/EXEC, WATCH (optimistic concurrency), and Lua scripts — plus the much-debated distributed lock.

MULTI / EXEC — queued, not isolated-by-default

MULTI queues commands; EXEC runs them atomically and in order with nothing interleaving. But there's no rollback — if a command errors at runtime, the others still run (it's not SQL transactions). It's "all run together," not "all-or-nothing."

WATCH — optimistic locking (CAS)

WATCH key before MULTI; if that key changes before EXEC, the whole transaction aborts and you retry. This is compare-and-swap for "read, compute, conditionally write" without holding a lock — e.g. decrement stock only if still positive.

WATCH stock:sku9
val = GET stock:sku9
if val > 0:
  MULTI; DECR stock:sku9; EXEC   # aborts & retries if stock changed

Lua scripts & Functions — atomic compound logic

A script runs atomically on the single thread — nothing else executes mid-script. This is the cleanest way to do read-modify-write logic server-side in one round-trip: rate limiters, conditional decrements, dequeue-and-mark, multi-key invariants. EVAL/EVALSHA for scripts; Functions (7.0+) register reusable libraries.

Scripts block the loop

Because a script runs to completion atomically, a slow or looping script freezes the entire server. Keep scripts short and O(small); never do unbounded loops or O(N) work over huge keys inside one. Atomicity and blocking are the same coin.

Distributed locks — handle with care

SET lock:resource token NX PX 30000 = acquire a lock only if absent, auto-expiring so a dead holder doesn't deadlock. Release with a Lua script that deletes only if the token matches (so you don't release someone else's re-acquired lock).

# acquire
SET lock:job123 $uuid NX PX 30000
# release (atomic check-and-del)
EVAL "if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end" 1 lock:job123 $uuid
The Redlock caveat to cite

Single-node lock = simple but not fault-tolerant (lose the node mid-lock, lose mutual exclusion). Redlock spreads the lock across N independent masters for safety, but Martin Kleppmann's well-known critique argues it's unsafe under GC pauses / clock skew for correctness-critical mutual exclusion. The honest take: Redis locks are great for efficiency (avoid duplicate work) and best-effort coordination; for correctness mutual exclusion (money, exactly-once), use a fencing token or a strongly-consistent coordinator (ZooKeeper/etcd) or push the invariant into your ACID store.

Ask me

MULTI vs Lua?

Both atomic. MULTI is a static queued batch; Lua can branch/compute between reads and writes in one atomic pass (true conditional logic). Lua is usually cleaner for read-modify-write; WATCH+MULTI is optimistic CAS without server-side scripting.

Is a Redis lock safe for exactly-once payment processing?

No — async replication + GC/clock issues mean a lock can be held by two clients across a failover. For correctness, use a fencing token or put the idempotency key as a unique constraint in the ACID store holding the payment. Redis locks are for efficiency, not correctness-critical mutual exclusion.

Access & patterns · 04

Bucketing, hot keys & sharding patterns

"Bucketing" means two different things in Redis, both essential: time-bucketing to bound key size and spread load, and hash-bucketing to cut memory. Plus the hot-key problem that bucketing exists to solve.

The hot-key problem

A single key that everything reads or writes — a global counter, a celebrity's follower set, "today's trending" — concentrates load on the one node owning that key's slot. The cluster can't help: a key lives on exactly one shard. Symptoms: one node CPU-pinned while others idle, p99 spikes on that key's slot.

Time-bucketing — bound size & spread writes

Instead of one ever-growing key, key by a time window: views:page9:2026-06-20-14 (hourly), stream:orders:2026-06-20 (daily). Benefits: each key stays small (no big-key blocking), old buckets expire cleanly via TTL, and writes spread across many keys/slots over time. Reads that span windows union a handful of buckets.

# per-minute counter, auto-expiring, naturally sharded by time
INCR rate:user42:202606201432
EXPIRE rate:user42:202606201432 120
# DAU bitmap per day, OR 7 of them for weekly actives
SETBIT active:2026-06-20 42 1

Write-sharding a hot counter

If one counter is genuinely too hot, split it into N sub-counters and pick one at random per write; sum on read. You trade an O(N) read for an N× write spread.

# write: pick a random shard 0..9
INCR likes:post9:{rand(0,9)}
# read: sum the shards
MGET likes:post9:0 ... likes:post9:9   # → add up

Hash-bucketing — memory (recap with intent)

Group many tiny top-level keys into hashes of ~100–1000 fields kept under the listpack threshold (users:{id/1000} → {id%1000: value}). Same O(1) lookup, far less per-key overhead. This is the memory lever; time-bucketing is the load/size lever.

Hash tags — co-locating related keys

In Cluster, only the substring inside {…} is hashed to a slot. Wrap the shared entity so its keys land together and multi-key ops (MGET, MULTI, SINTER) work: cart:{u42}:items, cart:{u42}:total → same slot. But over-tagging recreates hot keys — don't force unrelated load onto one slot.

Ask me

A celebrity's follower set is one huge hot key — fix?

Don't store one giant set. Bucket followers across many keys (by id range or shard), and for the fan-out use the hybrid approach — don't materialize the celebrity into every follower's timeline. Hot read keys also get a local/replica read cache in front.

Time-bucket vs one big sorted set for a feed?

A bounded zset (capped to recent N) is usually right for a feed. Time-bucketing suits append-heavy counters/logs where you also want TTL-based expiry of old windows and write spread. Choose by whether you need ranked access (zset) or windowed counts/logs (buckets).

Access & patterns · 05

Caching patterns & their failure modes

Redis's most common job. The patterns are simple; the value is knowing the failure modes — stampede, penetration, avalanche — and the one-line fix for each.

The strategies

  • Cache-aside (lazy): app checks Redis; on miss, reads DB, writes back to Redis with TTL. Simplest, most common. Cache holds only what's been requested.
  • Read-through / write-through: the cache layer itself loads/persists (synchronous). Write-through keeps cache fresh but adds write latency.
  • Write-behind (write-back): write to cache, flush to DB async. Fast writes, risk of loss on crash — only for tolerant data.

The three failure modes (name them in the interview)

ProblemWhat happensFix
Stampede / dogpileA hot key expires; thousands of concurrent misses all hit the DB at onceLock/single-flight on rebuild (one loader, others wait); or probabilistic early refresh; or never-expire + async refresh
PenetrationQueries for keys that don't exist (often malicious) skip the cache and pound the DB every timeCache the negative result (short TTL) or a Bloom filter of valid keys to reject misses cheaply
AvalancheMany keys share an expiry instant; all expire together → mass DB load spikeJitter the TTLs (add random spread); stagger warming

Invalidation

The hard problem. Options: TTL (simple, accepts staleness window), write-through (update cache on write), explicit delete on write (delete the key so next read re-loads — beware races between the DB write and the delete), and CDC-driven (a change stream from the DB invalidates Redis — keeps the cache a true derived view). Pub/Sub or keyspace notifications can fan invalidation across app nodes.

Consistency framing

A cache is eventually consistent derived data. Accept a staleness window and design for it, or use write-through/CDC if you can't. The dangerous pattern is "delete cache then write DB" (or vice-versa) without ordering care — a concurrent reader can repopulate a stale value. Delete-after-commit + short TTL as a safety net is the pragmatic default.

Ask me

A viral key expires and the DB melts — what happened, how prevent?

Cache stampede: simultaneous misses dogpile the DB. Fix with single-flight (one rebuild, others wait on a lock), probabilistic early expiration, or serve-stale-while-revalidate.

How do you keep cache and DB consistent?

You don't get strong consistency cheaply — pick a staleness budget. TTL for simple cases; delete-on-write (after commit) + short TTL; CDC-driven invalidation when the cache must track the DB closely. Order the DB write and cache delete carefully to avoid repopulating stale data.

Operating at scale · 01

Persistence — RDB, AOF & what you can lose

"In-memory" doesn't mean "non-durable." Redis offers two persistence mechanisms with different recovery/loss profiles — and the precise durability guarantee is the cross-question that separates depth from buzzwords.

RDB — point-in-time snapshots

Periodically fork()s a child that writes the whole dataset to a compact binary .rdb file (copy-on-write means the parent keeps serving). Pros: tiny files, fast restart, great for backups. Con: you lose every write since the last snapshot if you crash between them. Triggered by save rules (e.g. "after 60s if ≥1000 keys changed") or BGSAVE.

AOF — append-only command journal

Logs every write command to a file, replayed on restart. Durability depends on the fsync policy:

appendfsyncDurabilityCost
alwaysfsync every write — lose ~nothingSlowest (disk per op)
everysec (default)fsync once/sec — lose ≤1s of writesGood balance
noOS decides — can lose a lotFastest

AOF grows, so Redis rewrites it (compacts to the minimal command set) in a background fork. Modern Redis supports a hybrid: AOF rewrite emits an RDB preamble + recent AOF tail — fast load and small loss window.

The durability sentence to say out loud

"Default Redis (everysec AOF + async replication) guarantees at most ~1 second of write loss on a single-node crash, and can lose recently-acknowledged writes on a failover because replication is asynchronous — so it's excellent as a cache/index/derived store, and unsafe as the sole system of record for money. WAIT can block until N replicas ack, raising durability at a latency cost, but it's not full synchronous replication."

Persistence ≠ the data is safe

A snapshot/AOF on the same box doesn't survive disk loss; ship backups off-box. And persistence interacts with memory: the fork() for BGSAVE/AOF-rewrite can briefly double memory under heavy writes (copy-on-write page divergence) — size headroom accordingly.

Ask me

If Redis is in-memory, what happens on crash?

Depends on config. RDB: lose everything since the last snapshot. AOF everysec: lose ≤1s. AOF always: lose ~nothing but slow. On a replica failover, async replication can drop the last writes regardless. State the exact knob, don't hand-wave "it's durable."

RDB or AOF — which?

Run both: RDB for fast restart + backups, AOF for the small-loss window. Hybrid persistence gives RDB-speed loads with an AOF tail. Pure RDB only if you can tolerate snapshot-interval loss.

Operating at scale · 02

Expiry, eviction & the memory ceiling

When RAM fills, Redis's behavior is entirely determined by two things: how TTLs are reclaimed, and which maxmemory-policy you chose. Getting this wrong turns a cache into an outage.

How TTLs actually expire

Two mechanisms together: lazy (a key is checked for expiry when accessed, and dropped if dead) and active (a background cycle samples random keys with TTLs and evicts expired ones). The implication: an expired key still occupies memory until it's sampled or touched — so you can't assume memory frees the instant a TTL passes.

Eviction policies — what dies when full

maxmemory-policyBehaviorUse when
noevictionWrites error once full; reads okRedis is a store, not a cache — never silently drop data
allkeys-lruEvict least-recently-used across all keysPure cache; hot set should survive
allkeys-lfuEvict least-frequently-usedCache with stable hot keys (better than LRU for skewed access)
volatile-lru/lfu/ttlEvict only keys that have a TTLMixed: persistent keys (no TTL) protected, cache keys (with TTL) evictable
allkeys-random / volatile-randomEvict at randomRarely — when access is uniform

Redis's LRU/LFU are approximate (sampled, not a global ordering) — cheaper and good enough. LFU adds a decaying counter so a once-popular-now-cold key eventually loses out.

Cache vs store, decided here

The single most consequential choice: noeviction says "this data matters, error rather than lose it" (Redis-as-store); allkeys-lfu/lru says "this is a cache, shed the cold tail under pressure." The volatile-* family lets one instance be both — TTL'd cache entries are evictable, permanent keys are safe. Pick deliberately; the default behavior under memory pressure is what bites teams.

Ask me

TTL passed but memory didn't drop — why?

Expiry is lazy + sampled-active, not instantaneous. A dead key holds memory until it's accessed or the active cycle samples it. Under heavy churn this lag is normal; eviction policy handles true pressure.

Redis as primary store — which eviction policy?

noeviction — so a full instance errors on write rather than silently dropping your data. Then alert on memory and scale out. allkeys-lru/lfu is for caches where losing cold keys is fine.

Operating at scale · 03

Replication, Sentinel & failover

One node is a single point of failure. Replication + Sentinel gives high availability — but the async nature of replication is exactly why Redis can lose acknowledged writes, the caveat you must surface.

Primary → replica (asynchronous)

A replica connects, gets an initial snapshot, then streams the primary's write commands. Replication is asynchronous: the primary acks the client before the replica confirms. So a primary that crashes after acking but before the replica caught up loses those writes on failover. Replicas scale reads (route read-only traffic to them) at the cost of replica-lag staleness.

Sentinel — automatic failover

Sentinel is a separate monitoring process (run ≥3 for quorum). Sentinels watch the primary, agree via quorum that it's down, elect a replica, promote it, and reconfigure clients (via pub/sub). It provides HA for a non-sharded setup. Clients ask Sentinel "who's the primary?" rather than hardcoding an address.

Sentinels reach quorum on failure and promote a replica. Because replication is async, writes acked by the old primary but not yet replicated are lost on promotion — the durability caveat.
Ask me

Can Redis lose data even with replicas?

Yes. Replication is asynchronous — the primary acks before replicas confirm, so a crash-then-failover can drop the last writes. WAIT n ms blocks until n replicas ack (stronger, slower) but it's not full sync replication. This is why Redis isn't a money-grade SoR.

Sentinel vs Cluster?

Sentinel = HA/failover for a single (non-sharded) dataset. Cluster = sharding the keyspace across many primaries for horizontal scale (and each shard has its own replicas/failover). You pick Sentinel when data fits one node but you need failover; Cluster when you must shard.

Operating at scale · 04

Redis Cluster — sharding the keyspace

When the dataset outgrows one node's RAM (or one node's throughput), Cluster shards keys across many primaries using 16384 hash slots. The mechanics — slot mapping, hash tags, redirects, resharding — and the multi-key constraint are core interview ground.

16384 slots, CRC16, no central router

Every key maps to a slot: slot = CRC16(key) mod 16384. Slots are divided among primaries (e.g. 3 shards ≈ 5461 slots each). There's no proxy in the data path — clients learn the slot→node map and talk to the right node directly. Add a node → move some slots to it (online resharding); the ~1/N data movement keeps rebalancing cheap.

Keys are deterministically placed by slot; clients route directly and self-correct on MOVED (slot permanently moved) / ASK (slot migrating right now).

The multi-key constraint & hash tags

A command touching multiple keys (MGET, SINTER, MULTI, Lua with multiple keys) requires all keys on the same slot — otherwise CROSSSLOT error. Hash tags force co-location: only the part inside {…} is hashed, so {user42}:cart and {user42}:wishlist share a slot and can be operated on together. Design related keys with a common tag from the start.

Cluster trade-offs to state

No cross-slot transactions/Lua without hash tags; multi-key ops are constrained; a hot key still pins one shard (sharding spreads keys, not load on a single key); and async replication means clustered Redis can still lose acked writes on failover. Cluster buys capacity and parallelism, not stronger consistency.

Ask me

Why 16384 slots, not more?

It's a fixed bitmap each node gossips about cluster state; 16384 bits ≈ 2 KB per heartbeat — small enough to exchange cheaply while giving fine-enough granularity for clusters up to ~1000 nodes. A pragmatic constant, not a deep law.

How do you keep a user's keys operable together in a cluster?

Hash tags: wrap the shared entity in braces — cart:{u42}:items, cart:{u42}:total — so they hash to one slot and multi-key ops work. Don't over-tag, or you recreate hot slots.

Does Cluster fix hot keys?

No — it shards keys across nodes, but any single key still lives on one shard. A hot key needs write-sharding (sub-keys), a read cache/replica, or a redesign (e.g. hybrid fan-out), not cluster.

Pitfalls, latency sources & when not to use Redis

The senior move is knowing where Redis hurts. Most production Redis pain is one of a handful of issues — and the honest "don't use Redis here" answer scores more than forcing it everywhere.

When Redis is the wrong tool

  • Sole system of record for money / anything that can't lose a write — async replication + memory-first means use an ACID store as the source of truth.
  • Dataset much larger than RAM (× shards) — RAM is the ceiling and it's expensive; a disk-based store (or Redis-on-flash tiers) fits cold data better.
  • Ad-hoc analytical queries / joins / arbitrary GROUP BY — that's a relational/columnar engine; Redis answers known access patterns, not exploration.
  • Large-corpus full-text search — Elasticsearch; RediSearch only for hot, moderate-size filtered lookups.
  • Durable, partitioned, long-retention event log at high throughput — Kafka; Streams for in-process queues and moderate fan-out.
The one-paragraph summary to land

"Redis is an in-memory, single-threaded data-structure server. Use it as the hot, derived layer — cache, ranked index, counter, queue, session, geo, dedup — chosen by picking the structure that makes your access pattern O(1)/O(log N). Respect the single thread (no O(N) on big keys), keep keys bounded and named as a schema, and treat it as eventually-consistent derived state behind an authoritative store. Its limits — RAM ceiling, async-replication loss, no ad-hoc queries — are exactly where you reach for a real database, search engine, or Kafka instead."
