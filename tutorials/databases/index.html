Internals · 01

Storage engines, pages & the write-ahead log

How bytes actually land on disk decides a database's whole performance personality. Two families dominate: B-tree (update-in-place) and LSM-tree (append + merge). Both rely on a WAL to survive crashes.

The page & the heap

Disk is read/written in fixed pages (Postgres 8 KB, InnoDB 16 KB). Rows live in a heap (unordered) or are stored inside the primary index (a clustered / index-organized table). A page holds a header, row pointers, and rows growing from opposite ends. The buffer pool caches hot pages in RAM; dirty pages are flushed lazily.

B-tree vs LSM-tree

B-tree pays on writes (random in-place I/O) and wins on reads. LSM pays on reads (multi-level lookups, compaction) and wins on write throughput.
TraitB-treeLSM-tree
WritesIn-place, random I/OAppend, sequential — much faster
ReadsOne tree walkCheck memtable + every SSTable level (Bloom filters prune)
SpaceFragmentation / partial pagesWrite amplification + compaction churn
EnginesInnoDB, Postgres, SQLite, BoltDBRocksDB, LevelDB, Cassandra, HBase, ScyllaDB

Write-Ahead Log (WAL)

The durability trick: before a change touches the data pages, append it to a sequential on-disk log and fsync it. If the process crashes, replay the WAL to recover committed work and roll back the rest. This turns slow random page writes into a fast sequential append, then flushes data pages later (group commit, checkpointing).

Recovery = redo + undo

On restart the engine replays log records after the last checkpoint (redo) and reverts uncommitted transactions (undo). A checkpoint periodically flushes dirty pages and records a safe restart point so the log doesn't grow unbounded.

Indexes — trading write cost for read speed

An index is a secondary data structure that turns an O(n) scan into an O(log n) or O(1) lookup. Every index you add speeds some reads and slows every write (it must be maintained too).

Clustered vs secondary

A clustered index stores the actual rows in index order — InnoDB's primary key is the table. A secondary index stores the key plus a pointer back (InnoDB stores the PK; Postgres stores a physical ctid tuple id). That's why InnoDB secondary lookups do two hops, and why a fat primary key bloats every secondary index.

Covering & composite

A covering index includes every column a query needs, so the engine answers from the index alone (index-only scan). A composite index on (a,b,c) serves prefixes a and a,b — leftmost-prefix rule — but not b alone.

The write tax

Indexes are not free reads — they are deferred writes. Each INSERT updates every index on the table. Write-heavy tables want few, narrow indexes; LSM engines amortize this via batched compaction.

Internals · 03

Replication — copies for durability, reads & locality

Replication keeps the same data on multiple nodes so you survive failures, scale reads, and serve users from a nearby region. The hard part is keeping copies in agreement.

Single-leader is simple and consistent but the leader is a write bottleneck. Multi-leader enables local writes but creates conflicts. Leaderless trades a coordinator for quorums.

Synchronous vs asynchronous

Sync replication waits for a follower to acknowledge before the write commits — no data loss on leader failure, but higher latency and a stall if the follower is slow. Async commits immediately and ships later — fast, but a leader crash can lose the un-shipped tail (and followers serve stale data: replication lag). Most systems use semi-sync: wait for one of N followers.

Quorums (R + W > N)

In leaderless systems you write to W replicas and read from R of N. If R + W > N, the read and write sets overlap on at least one node holding the latest value — strong-ish consistency without a leader. Cassandra/Dynamo expose this per query (ONE / QUORUM / ALL).

Internals · 04

Partitioning & sharding — splitting data to scale out

Replication makes copies of the same data. Partitioning (sharding) splits different data across nodes so the dataset and write throughput exceed one machine. The two combine: each partition is itself replicated.

Hash partitioning

Key → hash → node. Spreads load evenly and kills hotspots, but range scans must hit every shard, and naïve hash % N reshuffles almost everything when N changes.

Range partitioning

Contiguous key ranges per node. Great for range scans and time-series, but prone to hotspots (all "today" writes hit one shard). Bigtable/HBase split ranges dynamically.

Consistent hashing

Map both nodes and keys onto a hash ring; a key belongs to the next node clockwise. Adding/removing a node only moves the keys between two adjacent points — ~1/N of keys instead of nearly all. Virtual nodes (each physical node owns many ring points) smooth out the distribution.

Consistent hashing minimizes data movement on membership change — the backbone of Dynamo-style stores.

Secondary indexes when sharded

Local (document-partitioned): each shard indexes its own rows — cheap writes, but a query by the indexed field must scatter-gather across all shards. Global (term-partitioned): the index itself is partitioned by term — fast reads, but writes touch multiple shards. Elasticsearch uses local; DynamoDB GSIs are global-ish.

Internals · 05

Consistency models & client guarantees

"Consistency" means two different things. In CAP it's about replica agreement; in ACID it's about invariants. Here we map the spectrum from strongest to weakest, plus the per-client guarantees that matter in practice.

The strength ladder

ModelGuaranteeCostExample
Linearizable (strong)Every read sees the latest committed write; one global order, real-timeCoordination / consensus per opSpanner, etcd, ZooKeeper
SequentialOne global order, but not tied to wall-clockCheaper than linearizableSome RAFT reads
CausalCausally-related ops seen in order; concurrent ops may differTrack dependenciesMongoDB causal sessions, COPS

Client-centric guarantees (the "read-your-writes" family)

Even on an eventually-consistent store, these per-session promises remove the worst surprises:

  • Read-your-writes: after you write, you can read it back (route your reads to the leader/quorum, or to a replica caught up past your write).
  • Monotonic reads: you never see time go backward — once you read value v, you won't later read an older one (pin the session to one replica).
  • Monotonic writes: your writes apply in the order you issued them.
  • Consistent prefix: readers see writes in a causally valid order — never the reply before the question.
CAP / PACELC recap

During a Partition you must drop A or C. PACELC adds: Else (normal operation) you trade Latency vs Consistency. PA/EL = Cassandra, Dynamo. PC/EC = Spanner, HBase. PA/EC = MongoDB.

MVCC — isolation without read locks

Multi-Version Concurrency Control keeps multiple versions of each row. Readers see a consistent snapshot (the versions visible as of their start), writers create new versions — so readers never block writers and writers never block readers. The cost is garbage: dead versions must be reclaimed.

A transaction's visibility is decided by comparing its snapshot to each version's create/delete transaction ids.

Internals · 07

Distributed atomicity — 2PC, Saga & outbox

A single-node transaction is atomic via the WAL. Across nodes/services you need an agreement protocol so a transaction either commits everywhere or nowhere.

Two-Phase Commit (2PC)

2PC gives atomicity but is blocking: if the coordinator dies after PREPARE, participants hold locks indefinitely. It also kills availability — one slow node stalls everyone.

3PC adds a pre-commit phase to reduce blocking but assumes bounded delays (fails under real partitions). Production systems usually avoid bare 2PC and pick one of:

Saga

Break the distributed txn into local txns, each with a compensating action. On failure, run compensations in reverse (refund, cancel). Eventually consistent, no global locks. Choreographed (events) or orchestrated (a coordinator).

Transactional outbox

Write the business row and an "event" row in one local txn; a relay/CDC publishes the event to Kafka. Solves the dual-write problem (DB + queue) without 2PC. Your Mercari outbox notes live here.

Percolator (Spanner/TiDB style)

2PC layered on a versioned KV store: a client-driven protocol with a primary lock row that makes commit atomic, using snapshot timestamps. This is how TiDB and Spanner do cross-shard transactions — 2PC on top of a consensus-replicated store.

Internals · 08

Consensus — Paxos, Raft & ZAB

Consensus lets a cluster agree on a single value (or an ordered log of values) despite crashes and message loss, as long as a majority is alive. It's the engine under leader election, replicated logs, and linearizable reads.

Paxos

The original, provably-correct protocol. A proposer runs a two-phase ballot: Prepare(n) to a majority of acceptors (learning any already-accepted value), then Accept(n, v). Higher ballot numbers override lower ones. Correct but famously hard to implement; real systems use Multi-Paxos (elect a stable leader once, then skip Phase 1 for a stream of entries).

Raft — Paxos made understandable

Raft decomposes consensus into leader election (randomized timeouts), log replication (leader appends, commits at majority), and safety (a candidate can't win without the most up-to-date log).

Each entry is committed once a majority has it; the leader then advances the commit index. Terms (monotonic election epochs) prevent split-brain. ZAB (ZooKeeper) is a close cousin built around atomic broadcast.

Why majorities

A quorum of ⌊N/2⌋+1 guarantees any two quorums overlap, so a new leader always learns the latest committed entry. This is why consensus clusters are odd-sized (3, 5) and tolerate ⌊N/2⌋ failures — but throughput is bounded by the round trip, so they store small, critical data.

Internals · 09

Conflict resolution in leaderless / multi-leader systems

When writes can happen on multiple replicas, two updates to the same key can be concurrent. The system needs a rule to detect and reconcile divergence.

Detecting concurrency: versioning

Last-Write-Wins (LWW)

Attach a timestamp; the highest wins. Simple and used by Cassandra, but silently drops the loser's write and depends on clock sync — dangerous for counters or sets.

Vector clocks

A per-replica counter map. Comparing two vectors tells you if A happened-before B, B-before-A, or they're concurrent (genuine conflict to resolve). Used by Dynamo/Riak; lets the app or a CRDT merge.

CRDTs — merge without coordination

Conflict-free Replicated Data Types are structured so concurrent updates always merge deterministically regardless of order: G-Counters (grow-only), PN-Counters, OR-Sets, LWW-registers. Replicas converge with no consensus — the basis of Riak data types, Redis CRDTs (Active-Active), and collaborative editors.

Background repair

  • Read repair: on a quorum read, if replicas disagree, push the newest value to the stale ones inline.
  • Anti-entropy + Merkle trees: replicas periodically exchange a hash tree of their data; mismatched branches pinpoint exactly which ranges differ, so only those are synced (Cassandra nodetool repair, Dynamo).
  • Hinted handoff: if a target replica is down, a healthy node stores a "hint" and replays the write when it returns — preserving availability during brief outages.

Internals · 10

Fault tolerance, failure detection & clocks

Distributed databases assume nodes crash, networks drop messages, and clocks drift. Surviving that needs detection, recovery, and a notion of time that doesn't lie.

Detecting failure

You can't distinguish a dead node from a slow one — only suspect it. Heartbeats + timeouts are the baseline; phi-accrual detectors (Cassandra) output a suspicion level instead of a boolean. Gossip protocols spread membership and state epidemically: each node periodically exchanges what it knows with a few random peers, so the whole cluster converges on who's alive in O(log N) rounds without a central registry.

Recovery mechanisms

  • Replication + failover: promote a follower (consensus-elected leader) when the leader dies.
  • Checkpoints + WAL replay: restart a crashed node from its last checkpoint forward.
  • Snapshots / backups: point-in-time recovery (PITR) = full snapshot + WAL/binlog replay up to a chosen instant.
  • Hinted handoff / read repair: heal divergence after transient partitions (prev page).

TrueTime's trick

Spanner's API returns an interval [earliest, latest] for "now". To guarantee external consistency it waits out the uncertainty (a few ms) before committing, so no later transaction can get an earlier timestamp. Hardware (atomic clocks) shrinks the wait — buying linearizability across continents.

Internals that define it

MVCC via tuple versioning

Every row update writes a new tuple rather than overwriting; visibility is decided by xmin/xmax (the creating/deleting transaction ids) against the reader's snapshot. Readers and writers never block each other. The trade-off: dead tuples accumulate and must be reclaimed by VACUUM (and autovacuum), and high-update tables can suffer bloat and transaction-id wraparound if vacuuming falls behind.

WAL = durability + replication + PITR

All changes hit the Write-Ahead Log first. The same WAL stream powers crash recovery, streaming replication (followers replay it), and point-in-time recovery (restore base backup + replay WAL to a chosen instant). Logical decoding turns WAL into a change stream for CDC.

Heap + visibility map

Tables are unordered heaps; all indexes are secondary and point at physical tuple ids (ctid). An index-only scan is possible when the visibility map confirms a page is all-visible. HOT updates avoid touching indexes when no indexed column changed.

-- JSONB + GIN: relational and document in one engine
CREATE INDEX idx_meta ON events USING gin (meta);
SELECT * FROM events WHERE meta @> '{"type":"signup"}';
Reach for it when

You want a correct, flexible source of truth with room to grow — extensions (PostGIS, pgvector, TimescaleDB, Citus) let one engine cover geo, embeddings, time-series and sharding without switching databases.

Databases · Relational

MySQL / InnoDB

The web's workhorse RDBMS. InnoDB (the default engine) gives ACID transactions, row-level locking, and a clustered-index storage layout. Two logs — redo and binlog — do very different jobs.

Internals that define it

Clustered primary index

In InnoDB the table is the primary-key B+tree — rows live in the leaf pages in PK order. Secondary indexes store the primary key as the row pointer, so a secondary lookup does two B+tree walks, and a large PK inflates every secondary index. Pick a small, monotonic PK (auto-increment) to keep inserts sequential.

Two logs: redo vs binlog

The redo log (physical, circular) restores InnoDB pages after a crash. The binlog (logical, server-level) is the replication + PITR + Debezium-CDC stream. Undo logs hold old row versions for MVCC and rollback.

MVCC via undo logs

Unlike Postgres's in-table version chain, InnoDB keeps old versions in the undo log (rollback segment). Readers reconstruct their snapshot by walking undo records back; purge threads clean them once no transaction needs them. Default isolation is Repeatable Read, with next-key (gap) locking to block phantoms.

Reach for it when

High-read web workloads, huge install base and tooling, or when a managed offering (RDS/Aurora MySQL, PlanetScale via Vitess) fits. Vitess shards MySQL transparently behind a SQL proxy.

Persistence

Despite being in-memory, Redis is durable-ish: RDB takes periodic point-in-time snapshots (fast restart, can lose recent writes); AOF appends every write command and replays on restart (more durable, larger, fsync-tunable). Many deployments run both.

Internals that define it

Replica sets & the oplog

A replica set has one primary (takes writes) and secondaries that tail the primary's oplog (a capped operation log, like a logical WAL). On primary failure, a Raft-like election promotes a secondary. Default reads go to the primary → strongly consistent; readPreference and readConcern/writeConcern tune the consistency/latency trade (this is why it's PA/EC).

Sharding

Collections shard on a shard key (hashed or ranged); mongos routers direct queries, config servers hold metadata, and the balancer migrates chunks. A poor shard key (low cardinality or monotonic) creates hotspots — the single most important design decision.

// aggregation: documents in, reshaped out
db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: { _id: "$userId", total: { $sum: "$amount" } } }
])
Reach for it when

Your data is naturally document-shaped (catalogs, profiles, content), the schema evolves fast, and you read/write whole aggregates together. Multi-document ACID transactions exist but cost more than in an RDBMS — model to avoid needing them.

Databases · Wide-column

Apache Cassandra

A masterless, linearly-scalable wide-column store built for relentless write throughput and zero downtime. Every node is equal; there is no single point of failure.

Wide-column (partition → rows)

The write path (why it's so fast)

Append-only writes = no read-before-write, no locks. Deletes are tombstones; data converges via compaction.

Availability machinery

Data is placed by consistent hashing with a replication factor; gossip spreads membership; hinted handoff covers brief outages; read repair and Merkle-tree anti-entropy (nodetool repair) heal divergence. Consistency is per-query: R + W > RF gives strong reads on demand. Lightweight transactions (LWT) use Paxos for the rare compare-and-set.

Design query-first

No joins, no ad-hoc filtering. You model one table per access pattern, choosing a partition key (locates data, must avoid hotspots) and clustering columns (sort within partition). Denormalization is expected.

Databases · Managed KV / wide

Amazon DynamoDB

The serverless descendant of the Dynamo paper. Single-digit-millisecond latency at any scale, fully managed, with no servers to tune — if you design around its key model.

How it works

Items are spread across partitions by a hash of the partition key; each partition is replicated across 3 AZs with a quorum. Reads are eventually consistent by default (cheaper, may lag) or strongly consistent on request (single region only). Global tables replicate multi-region as active-active with last-write-wins — eventually consistent across regions.

Single-table design

The idiomatic pattern packs multiple entity types into one table, overloading the partition/sort keys so related items sit together and one query fetches an aggregate — avoiding joins DynamoDB doesn't have. GSIs add alternate access paths (eventually consistent, async-maintained). DynamoDB Streams emit a change log for CDC / fan-out.

The partition-key trap

A hot partition key throttles throughput even if the table is under-utilized overall. Choose high-cardinality keys; add write sharding (suffixes) for hot aggregates. Capacity is provisioned or on-demand; design access patterns before the schema.

Reach for it when

Access patterns are known and key-based, scale is large/spiky, and you want zero ops. Carts, sessions, user profiles, event stores. Pair with DAX (in-memory cache) for read-heavy hot keys.

Databases · Distributed SQL

Google Spanner

The system that "shouldn't exist": globally distributed, horizontally scalable, and externally consistent (linearizable) SQL. Its secret is special hardware — TrueTime.

Architecture: 2PC over Paxos

Each data split is a Paxos-replicated group (so each shard survives node loss with strong consistency). A transaction spanning splits runs 2PC across the Paxos leaders — durable participants, no blocking-on-crash problem.

TrueTime → external consistency

Spanner assigns every transaction a commit timestamp and must guarantee timestamps respect real-world order globally. TrueTime exposes time as a bounded interval [earliest, latest] sourced from GPS + atomic clocks in every datacenter. At commit, Spanner performs a commit-wait: it waits until latest has passed before releasing locks, ensuring no later transaction can receive an earlier timestamp. Result: linearizable transactions across continents, with read-only transactions served lock-free at a snapshot timestamp.

The CAP nuance to quote

Strictly, Spanner is CP — on partition it favors consistency. But Google's network + TrueTime deliver ~5 nines, so in practice it behaves like the "impossible" highly-available strongly-consistent system. CockroachDB/YugabyteDB are open-source takes on the same idea (using HLC instead of atomic clocks).

Databases · Distributed SQL

CockroachDB

Open-source distributed SQL inspired by Spanner — but without atomic clocks. It reaches serializable isolation and survives node/region loss using Raft and Hybrid Logical Clocks, behind a PostgreSQL-compatible wire protocol.

Internals

Ranges + Raft

The keyspace is sorted and chopped into ranges; each range is a Raft group replicated (default 3×). Ranges split/merge and rebalance automatically as data grows. A range leader (leaseholder) serves reads locally; writes go through Raft to a majority.

Transactions without TrueTime

Instead of waiting out clock error, CockroachDB uses HLC timestamps plus a configured max clock offset. When a read might overlap that uncertainty window, it performs an uncertainty restart at a higher timestamp. Cross-range transactions use a Spanner-style protocol (parallel commits + 2PC over the Raft groups) to stay atomic.

Reach for it when

You want Postgres-compatible SQL and transactions but need to scale horizontally and survive whole-region failures, without running Google's hardware. Multi-region tables let you pin data near users for locality + low latency.

Databases · Wide-column & Search

Bigtable / HBase & Elasticsearch

Two specialist families: range-partitioned wide-column stores for petabyte-scale sequential workloads, and inverted-index engines for full-text and analytics.

Rows are sorted by key and split into regions/tablets; exactly one region server owns each range, giving strong single-row consistency. Writes hit a WAL + memstore, flush to immutable files, and compact — the classic LSM path. Row-key design is everything: it controls locality and hotspots (salt or hash time-prefixes to avoid a single region taking all "now" writes). Documents are tokenized into an inverted index (term → posting list of doc ids), enabling fast full-text, relevance scoring (BM25), facets and aggregations. Lucene writes immutable segments that are periodically merged; a refresh (default 1s) makes new docs searchable — hence "near-real-time," not instantly consistent. Indices are sharded (each shard a Lucene index) and replicated. It's a secondary store: feed it from your system of record via CDC; it's rebuildable and not the authoritative copy.

Your domain

The OpenSearch shard-tuning and 241M-doc index work maps directly here: shard count = parallelism but also overhead; oversharding wastes heap, undersharding limits throughput and makes rebalancing painful. Vector (HNSW) fields now bring semantic search into the same engine.

Databases · Log & Coordination

Kafka, etcd & ZooKeeper

Not "databases" in the query sense, but they're load-bearing in almost every distributed system design — the durable backbone and the source of truth for cluster state.

Apache Kafka — the distributed log

Model
Partitioned append-only log
Ordering
Total order within a partition
Durability
Replicated; ISR + acks=all
Retention
Time/size based or compacted

A topic is split into partitions; each is an ordered, immutable, replicated log. Producers append; consumers track their own offset and replay at will. Replication uses an in-sync replica (ISR) set — with acks=all a write is durable once all ISRs have it. This makes Kafka the spine for event sourcing, CDC (Debezium → Kafka → derived stores), the transactional outbox relay, and fan-out — exactly the read-path/outbox patterns in distributed system design. (Newer Kafka replaces ZooKeeper with built-in KRaft consensus.)

etcd & ZooKeeper — coordination

Model
Small linearizable KV + watches
Consensus
Raft (etcd) / ZAB (ZooKeeper)
Used for
Config, leader election, locks, discovery
Backs
etcd→Kubernetes; ZK→HBase/Kafka(old)

These are strongly-consistent metadata stores. Their consensus core makes them safe for leader election and distributed locks (via ephemeral keys/sessions + watches), but throughput is bounded by the consensus round trip — keep the dataset tiny (kilobytes of cluster state, not user data). etcd's linearizable reads and watch streams are why Kubernetes stores its entire desired state there.

Design heuristic

If a component needs "exactly one leader" or "everyone agrees on this config," that's a coordination store — don't reinvent it in your application DB. If you need a durable, replayable event stream that decouples producers from consumers, that's a log.

The order to reason in

  1. Shape of the data & queries — relational with joins? document aggregates? key lookups? full-text? time-series? graph? This narrows the family before anything else.
  2. Consistency vs availability — what breaks if a read is stale? Money → strong (Postgres/Spanner). Feeds/carts → eventual is fine (Cassandra/Dynamo).
  3. Scale & write pattern — fits one primary + replicas, or must shard? Write-heavy favors LSM/leaderless; read-heavy relational favors replicas + cache.
  4. Latency & geography — single region or global? Local reads needed? → distributed SQL or multi-region replication.
  5. Operational reality — managed service available? team expertise? Default to the boring, well-understood option and add specialist stores (cache, search, OLAP) around it.
The senior signal

Name a polystore, not one database: e.g. "Postgres as the system of record, Redis for the session/cart cache, Elasticsearch for search fed by CDC, S3 for media, Kafka to glue them." Derive each choice from a requirement you stated — don't reverse-engineer requirements to fit a database you already liked.
