A field guide to GraphQL

You know REST and JSON. This goes to the execution model: the type system, the resolver tree, null propagation, N+1, cursor pagination, and runnable servers in Node, Python, and Go. No hand-waving.

01

Orientation

GraphQL is a query language and an execution engine for a typed graph of data. One endpoint; the client decides the response shape.

A GraphQL service is three things working together: a type system (the schema) that publishes exactly what data exists, a query language the client uses to ask for precisely the fields it wants, and an execution engine that walks the request against the schema and returns a JSON response in the same shape as the query. It is transport-agnostic by design — almost always served over HTTP, but the spec does not mandate that.

◆ mental model

REST: the server decides each endpoint's response shape; the client takes the whole payload (over-fetching) or makes several calls (under-fetching). GraphQL: there is one endpoint, and the client specifies field-by-field what it needs in a single request. The response mirrors the query tree exactly. You're not calling URLs — you're describing a sub-selection of a typed graph.

What it buys you

  • No over/under-fetching. A mobile screen asks for 5 fields and gets 5; a desktop view asks for 40 in the same round trip. The server doesn't ship versioned endpoints per client.
  • One round trip across resources. Fetch a user, their last orders, and each order's line items in a single nested query instead of N REST calls.
  • A strongly typed contract. The schema is introspectable, so tooling gives autocomplete, validation before execution, and codegen of typed clients.
  • Schema evolution without versioning. Add fields freely; deprecate old ones with @deprecated. Clients only break if you remove something they request.
  • A natural backend-for-frontend. In 2026 the dominant pattern is GraphQL as an aggregation layer over REST/gRPC microservices, often federated into one supergraph.

Where it costs you

  • HTTP caching is gone by default. Everything is a POST to one URL, so CDNs and browser caches can't help without extra work (persisted queries — §07/§12).
  • Performance footguns are built in. The resolver model invites the N+1 problem (§05); a malicious nested query can be a DoS without depth/complexity limits (§12).
  • It's not free real-time. Subscriptions need a stateful transport and pub/sub infrastructure (§07).
  • Overkill for one stable client over one service. A single internal microservice talking to one consumer is simpler as REST or gRPC.
◆ the honest 2026 take

GraphQL didn't replace REST. It won a specific niche: a backend-for-frontend when you have many clients consuming one backend and can't predict which fields each needs. A common production shape is REST/gRPC internally, GraphQL at the edge, federated across teams. Reach for it when client diversity and graph complexity are the problem — not for raw throughput on a hot internal path.

02

The schema (SDL)

The Schema Definition Language is the contract. Every type, every field, every modifier is meaningful — here it all is, annotated.

schema.graphqlgraphql
scalar DateTime

"A registered user."                       # description (shows in introspection/docs)
type User {
  id: ID!                                  # ID, non-null
  email: String!
  fullName: String
  role: Role!                              # enum
  posts(first: Int = 10): [Post!]!         # field with an argument + default
  createdAt: DateTime                      # custom scalar
}

type Post {
  id: ID!
  title: String!
  author: User!                            # object reference -> graph edge
}

enum Role { MEMBER ADMIN }

input CreateUserInput {                    # input type: used only as an argument
  email: String!
  fullName: String
}

interface Node { id: ID! }                 # shared field contract
union SearchResult = User | Post           # value is exactly one of these

type Query {                               # the read entry points
  user(id: ID!): User
  search(term: String!): [SearchResult!]!
}

type Mutation {                            # the write entry points
  createUser(input: CreateUserInput!): User!
}

type Subscription {                        # the real-time entry points
  postAdded: Post!
}
the type kinds
typeObject type — a node with fields. The backbone of the graph. Fields that return object types are edges to other nodes.
scalarA leaf value. Built-ins: Int, Float, String, Boolean, ID. Define custom ones (DateTime, JSON) with their own serialize/parse logic.
enumA fixed set of named values. Serialized as the name string, not an integer.
inputAn object used only as an argument. Separate from type because inputs can't have circular edges or resolvers — they're plain data in.
interfaceA field contract multiple object types implement. Lets a field return "any Node" while guaranteeing shared fields.
union"Exactly one of these object types" with no required shared fields. Resolve which one at runtime.
Query / Mutation / SubscriptionThe three root operation types — the only entry points a client can start from. Read / write / stream.

Type modifiers — the two symbols that matter most

NotationMeans
StringNullable string — may be the value or null
String!! = non-null. The server guarantees a value; never null
[String]Nullable list of nullable strings
[String!]Nullable list, but no null elements
[String!]!Non-null list of non-null strings — the list always exists and every element is present
▲ gotcha — non-null is a runtime contract, and it propagates

The ! isn't just documentation. If a resolver for a non-null field returns null (or throws), GraphQL can't satisfy the guarantee, so the null bubbles up to the nearest nullable parent — potentially nulling a whole branch of your response. Mark a field non-null only when the server can truly always produce it. Over-using ! turns one failed leaf into a collapsed subtree. This is the single most surprising behavior in GraphQL; §04 shows it in action.

Directives

Directives are @-prefixed annotations that modify execution or schema behavior. Built-in schema directive @deprecated; built-in execution directives @skip/@include (§03). You can define custom ones for auth, rate limits, caching hints, etc.

directives in SDLgraphql
type User {
  fullName: String
  name: String @deprecated(reason: "Use fullName")   # schema directive
  ssn: String @auth(requires: ADMIN)                  # a custom directive
}
◆ code-first vs schema-first

Two ways to author a schema. Schema-first: write the SDL above by hand, then attach resolvers (Apollo, gqlgen). Code-first: write typed code in your language and the SDL is generated from it (Strawberry, Graphene, Nexus). Code-first keeps types and resolvers in one place and avoids drift; schema-first keeps the contract front-and-center and language-agnostic. Both produce the same wire behavior — pick per ecosystem (§08–10 show both).

03

Operations & the query language

What the client sends. A document contains one or more operations and any reusable fragments.

a query with everythinggraphql
query GetUser($id: ID!, $withPosts: Boolean!) {   # operation type + name + variables
  user(id: $id) {                                 # field with an argument
    id
    handle: email                                 # alias: rename in the response
    ...UserFields                                 # fragment spread (reuse)
    posts @include(if: $withPosts) {              # directive: conditionally fetch
      title
    }
  }
}

fragment UserFields on User {                     # named, reusable selection
  fullName
  role
}
every token explained
queryThe operation type: query (read), mutation (write), or subscription (stream). query is the default if omitted.
GetUserOperation name. Optional but always name them — needed for caching, logging, persisted queries, and multi-operation documents.
$id: ID!A variable declaration. $-prefixed, typed. Values are sent separately as JSON, never string-interpolated into the query — this is what keeps GraphQL injection-safe and queries cacheable.
user(id: $id)A field with an argument, bound to the variable.
handle: emailAn alias. Returns the email field under the key handle. Required to request the same field twice with different args.
...UserFieldsA fragment spread — inserts a named, reusable selection set. The unit of query composition.
@include(if:)An execution directive. @include(if: false) omits the field; @skip(if: true) is the inverse.
on UserThe type condition — a fragment applies to a specific type. Inline form: ... on Admin { ... } for narrowing interfaces/unions.

Request and response shape

Over HTTP a request is JSON with query, optional operationName, and variables. The response is JSON with data and/or errors — and the data tree mirrors the query exactly.

request → responsejson
// POST /graphql  body:
{ "query": "query GetUser($id:ID!){ user(id:$id){ id email } }",
  "operationName": "GetUser",
  "variables": { "id": "42" } }

// response:
{ "data": { "user": { "id": "42", "email": "al@acme.dev" } } }

Mutations & subscriptions

mutation + subscriptiongraphql
mutation CreateUser($input: CreateUserInput!) {
  createUser(input: $input) {   # mutations return data too — request the new state back
    id
    email
  }
}

subscription OnPostAdded {
  postAdded { id title }        # server pushes a payload per event over a live connection
}
◆ why mutations still have a selection set

A mutation is a write, but it returns an object like any field — so you select what you want back (the created row, an updated count, a payload wrapper). Convention: return the affected entity so the client can update its cache without a follow-up query. Top-level Mutation fields execute serially (left to right); Query fields may execute in parallel. That serial guarantee is the only ordering GraphQL gives you.

04

Execution & resolvers

How a query becomes data. The engine walks the query tree and calls a resolver for each field. Understanding this is understanding GraphQL.

Execution is a depth-first walk of the selection set. For each field, the engine calls its resolver — a function that returns that field's value. A field returning an object type resolves to a parent value that's passed down to resolve its children. Leaves (scalars) end the recursion. Resolvers run concurrently among sibling fields where possible.

resolver signature (JS reference impl)javascript
function resolve(parent, args, context, info) { /* return the field's value */ }
the four resolver arguments
parentThe value returned by the parent field's resolver (a.k.a. root/source/obj). For User.posts, parent is the resolved User. Top-level fields get the root value.
argsThe arguments passed to this field in the query, already validated and coerced against the schema (e.g. { id: "42" }).
contextA per-request object shared by every resolver: auth/user, DB connections, DataLoaders, request headers. The standard place to put dependencies. Built once per request.
infoThe execution AST — field name, path, the sub-selection requested, schema. Used for advanced tricks (look-ahead to fetch only requested columns, tracing).
◆ default resolvers — why you write fewer than you think

If you don't define a resolver for a field, the engine uses the default: read a property of the same name off parent (e.g. parent.email), and call it if it's a function. So when your DB row already has the right shape, most scalar fields need no resolver at all — you only write resolvers for entry points and for edges that require a fetch.

The data / errors envelope

GraphQL doesn't fail a whole request when one field fails. The response carries data (partial allowed) and an errors array. A field that errors becomes null in data, and an entry with a path appears in errors.

partial successjson
{
  "data": { "user": { "id": "42", "fullName": null } },
  "errors": [
    { "message": "name service timeout",
      "path": ["user", "fullName"],
      "extensions": { "code": "UPSTREAM_TIMEOUT" } }
  ]
}
▲ gotcha — null propagation through non-null fields

Recall the ! from §02. If fullName were typed String! and its resolver returned null or threw, GraphQL can't put null there — so it nulls the nearest nullable ancestor instead. If user is nullable, the whole user becomes null; if user is also non-null, the null climbs further, potentially to the root data. One overly-strict ! deep in a tree can wipe out an entire response branch. Type leaves nullable unless the server can truly always supply them.

◆ error conventions in 2026

Two error classes: execution errors (a resolver threw — goes in the top-level errors array) and expected business errors (validation failures, "email taken"). The mature pattern is to model expected failures in the schema as union result types (e.g. createUser: CreateUserResult = User | EmailTakenError) so clients handle them with types instead of string-matching the errors array. Reserve errors[] for the genuinely exceptional. Put machine-readable codes in extensions.code.

05

The N+1 problem & DataLoader

The performance trap every GraphQL backend hits. The resolver model that makes nested queries elegant also makes them accidentally quadratic.

Consider query { posts { author { name } } } over 50 posts. The posts resolver runs one query (the "1"). Then the engine resolves author per post — 50 separate lookups (the "N"). One list query explodes into 51 database round trips. Nest deeper and it compounds.

the naive resolver — one query per postjavascript
const resolvers = {
  Query: { posts: () => db.posts.findAll() },          // 1 query
  Post:  { author: (post) => db.users.findById(post.authorId) }, // N queries (!)
};

DataLoader — batch + cache per request

A DataLoader sits between resolvers and your data source. Instead of querying immediately, each author resolver calls load(id), which collects all the IDs requested in the same tick of the event loop, then fires one batched query (WHERE id IN (...)). It also caches within the request so the same ID isn't fetched twice.

batched with DataLoaderjavascript
import DataLoader from "dataloader";

// the batch function receives ALL ids collected this tick; return values in id order
const makeUserLoader = () => new DataLoader(async (ids) => {
  const users = await db.users.findByIds(ids);        // ONE query: WHERE id IN (...)
  const byId = new Map(users.map((u) => [u.id, u]));
  return ids.map((id) => byId.get(id) ?? null);       // MUST align with input order
});

// build a fresh loader per request and put it on context (never share across requests)
const context = () => ({ loaders: { user: makeUserLoader() } });

const resolvers = {
  Query: { posts: () => db.posts.findAll() },
  Post:  { author: (post, _args, ctx) => ctx.loaders.user.load(post.authorId) },
};
▲ gotcha — a new loader every request, results in input order

Two rules people break. (1) Create loaders per request (on context), never as a singleton — the per-request cache must not leak data between users. (2) The batch function must return an array the same length and order as the input keys, with null for misses. Return them out of order and you'll hand the wrong user to the wrong post — a silent, dangerous bug.

◆ why this is the canonical answer

DataLoader is in every ecosystem (built into Strawberry, idiomatic in gqlgen, standard with Apollo). It solves N+1 without changing your schema or coupling resolvers together. The alternatives — preloading via info look-ahead, or a query planner — are heavier. If an interviewer asks "how does GraphQL avoid N+1", the answer is per-request batching, and DataLoader is the reference implementation.

06

Pagination

GraphQL has no built-in pagination, but the ecosystem standardized on cursor-based connections. Know why offset loses.

Offset vs cursor

Offset (limit/offset, "page 3") is simple but breaks under writes: insert a row while a user pages and everything shifts, so they see duplicates or skip items. It also gets slow at high offsets (the DB still scans skipped rows). Cursor pagination passes an opaque pointer to "the item after this one", which is stable under inserts and indexes well.

The Relay Connection spec

The community convention (the "Connection" pattern, from Relay) wraps a list in a structure of edges and pageInfo. It's verbose but ubiquitous — tools, clients, and federation assume it.

connection schema + querygraphql
type Query {
  posts(first: Int!, after: String): PostConnection!   # forward pagination
}

type PostConnection {
  edges: [PostEdge!]!
  pageInfo: PageInfo!
  totalCount: Int                                       # optional, often expensive
}
type PostEdge {
  node: Post!          # the actual item
  cursor: String!      # opaque pointer to THIS item
}
type PageInfo {
  hasNextPage: Boolean!
  hasPreviousPage: Boolean!
  startCursor: String
  endCursor: String
}

# client pages like:
# query { posts(first: 10, after: "Y3Vyc29yOjEw") {
#   edges { node { title } cursor } pageInfo { hasNextPage endCursor } } }
what each piece is for
edges + nodeThe extra edge wrapper exists so you can attach data about the relationship (e.g. addedAt on a membership) alongside the node, without polluting the node itself.
cursorAn opaque, base64-ish token the server understands — usually encodes a stable sort key (id, timestamp). Clients must treat it as a black box and just echo it back in after.
pageInfoNavigation metadata: whether more pages exist and the boundary cursors to continue from. first/after page forward; last/before page backward.
◆ when to skip the ceremony

Connections are the right default for public/federated APIs and infinite-scroll feeds. For a small bounded internal list, a plain [Post!]! is fine — don't cargo-cult edges/pageInfo onto a dropdown of 12 categories. Match the pattern to the access pattern.

07

Transport & subscriptions

The spec deliberately doesn't define a transport. In practice it's HTTP for queries/mutations and a streaming protocol for subscriptions. The GraphQL-over-HTTP spec nails down the conventions.

GraphQL over HTTP

  • POST + JSON is the workhorse: body { query, operationName, variables }, response { data, errors }.
  • GET is allowed for queries only (params in the query string) — mutations over GET must be rejected with 405, since GET should be side-effect-free and cacheable.
  • Content types: the modern application/graphql-response+json lets the server return real HTTP status codes (4xx/5xx) for protocol/validation failures, instead of the legacy habit of always returning 200 with an errors array.
▲ gotcha — "200 OK" with errors inside

Classic GraphQL returns 200 even when the query failed validation, with the problem buried in errors[]. That defeats HTTP-level monitoring and client retry logic. Under the GraphQL-over-HTTP conventions plus the newer content type, transport/validation failures map to proper status codes while field-level resolver errors still ride in the errors array of a 200. Know which layer an error lives at.

Caching — the thing REST got for free

Because every operation is a POST to one URL, HTTP/CDN caching doesn't apply out of the box. The standard fix is persisted queries (a.k.a. trusted documents): register the query text server-side, and the client sends only a hash. Now requests are tiny, can travel as cacheable GETs (/graphql?id=abc), and the server can reject any query not on the allow-list — caching and security in one move. See §12.

Subscriptions — real-time transport

Queries and mutations are request/response; subscriptions are a long-lived stream where the server pushes a payload per event. They need a stateful transport. Current options:

TransportLibraryNotes
WebSocketgraphql-wsThe recommended default. Bidirectional, widely supported
Server-Sent Eventsgraphql-sseOne-way, simpler, survives corporate proxies, no custom protocol
Multipart HTTP(built into clients)Chunked responses; also powers @defer/@stream
subscriptions-transport-ws(legacy)Unmaintained — do not use for new work
▲ gotcha — the graphql-ws naming trap

The maintained library is called graphql-ws, but its WebSocket subprotocol is named graphql-transport-ws. The old, unmaintained library subscriptions-transport-ws used a subprotocol confusingly named graphql-ws. They're wire-incompatible. The subprotocol string must match exactly across server, client, and any tooling (GraphiQL/Sandbox) — a mismatch fails silently with a dead connection. Use the graphql-ws library + graphql-transport-ws subprotocol end to end.

Incremental delivery — @defer / @stream

An emerging feature: mark a slow fragment @defer or a list field @stream, and the server sends the fast parts first, then streams the rest as additional payloads (with hasNext, pending, incremental, completed markers over multipart HTTP). It improves perceived latency without splitting into multiple round trips.

◆ status as of 2026

@defer/@stream are still working through the spec process (multiple competing execution RFCs) and ship as experimental in graphql-js and some servers/clients. Great for a known-slow field behind a feature flag; don't build core architecture on the exact payload shape yet, since it's still moving. Confirm support across your server and client before adopting.

08

Node — Apollo Server / Yoga

The reference ecosystem. Schema-first SDL plus a resolver map. Apollo Server 5 is the default; GraphQL Yoga is the lean, edge-friendly alternative.

installbash
npm install @apollo/server graphql dataloader
# edge/lean alternative: npm install graphql-yoga graphql
server.js — Apollo Server 5javascript
import { ApolloServer } from "@apollo/server";
import { startStandaloneServer } from "@apollo/server/standalone";
import DataLoader from "dataloader";

const typeDefs = `#graphql
  type User { id: ID!, email: String!, posts: [Post!]! }
  type Post { id: ID!, title: String!, author: User! }
  type Query { user(id: ID!): User }
`;

const resolvers = {
  Query: {
    user: (_parent, { id }) => db.users.findById(id),     // entry point
  },
  Post: {
    author: (post, _args, ctx) => ctx.loaders.user.load(post.authorId), // batched
  },
  // User.email/id need no resolver — defaults read them off the parent row
};

const server = new ApolloServer({ typeDefs, resolvers });

const { url } = await startStandaloneServer(server, {
  listen: { port: 4000 },
  // context runs ONCE per request: fresh loaders, auth, db handles
  context: async ({ req }) => ({
    user: await authenticate(req.headers.authorization),
    loaders: {
      user: new DataLoader(async (ids) => {
        const rows = await db.users.findByIds(ids);
        const byId = new Map(rows.map((r) => [r.id, r]));
        return ids.map((id) => byId.get(id) ?? null);
      }),
    },
  }),
});
console.log(`ready at ${url}`);
◆ Apollo Server 5 vs GraphQL Yoga

Both are production-ready and speak standard GraphQL-over-HTTP. Apollo Server 5 brings the largest commercial ecosystem — Studio, the Rust-based Router, first-class Federation v2. Yoga has a tiny footprint and runs on edge runtimes (Cloudflare Workers, Deno, Bun) where Apollo is too heavy, and ships SSE subscriptions out of the box. Vanilla Node service → Apollo 5. Edge/serverless → Yoga.

▲ gotcha — the #graphql comment isn't decoration

That leading #graphql in the template literal triggers SDL syntax highlighting and tooling in editors. Harmless if omitted, but standard. Also: pin Apollo Server's version (avoid ^ ranges) during a build-out — minor releases occasionally adjust plugin signatures.

Python — Strawberry

Code-first: you write typed Python and the SDL is generated from your type hints. Async-native, dataclass-based. (Ariadne is the schema-first alternative; Graphene the older option.)

installbash
pip install 'strawberry-graphql[fastapi]'   # Python >=3.10; ASGI server integration
schema.pypython
import strawberry
from strawberry.dataloader import DataLoader

@strawberry.type
class Post:
    id: strawberry.ID
    title: str

@strawberry.type
class User:
    id: strawberry.ID
    email: str

    @strawberry.field                       # a resolver = a method on the type
    async def posts(self, info: strawberry.Info) -> list[Post]:
        return await info.context["db"].posts_for(self.id)

@strawberry.type
class Query:
    @strawberry.field
    async def user(self, id: strawberry.ID, info: strawberry.Info) -> User | None:
        return await info.context["loaders"]["user"].load(id)   # batched

schema = strawberry.Schema(query=Query)     # SDL is derived from the types above
app.py — serve over FastAPI, build per-request contextpython
from fastapi import FastAPI
from strawberry.fastapi import GraphQLRouter
from strawberry.dataloader import DataLoader
from schema import schema

async def load_users(ids: list[str]) -> list[User | None]:
    rows = await db.users.find_by_ids(ids)          # ONE query
    by_id = {r.id: r for r in rows}
    return [by_id.get(i) for i in ids]              # aligned with input order

async def get_context():                            # runs per request
    return {"db": db, "loaders": {"user": DataLoader(load_fn=load_users)}}

app = FastAPI()
app.include_router(GraphQLRouter(schema, context_getter=get_context), prefix="/graphql")
◆ why code-first fits Python

Strawberry reuses type hints you'd write anyway: id: strawberry.ID, -> User | None, list[Post] become the schema's ID!, nullable User, and [Post!]!. The contract can't drift from the code because it is the code, and mypy checks resolver return types against the schema. The trade-off vs schema-first: your .graphql file is generated, not hand-authored — export it (strawberry export-schema) for review and client codegen.

Go — gqlgen

Schema-first with code generation: write SDL, generate typed Go interfaces, implement the resolver stubs. Type-safe end to end, no reflection at request time.

scaffold + generatebash
go mod init acme/gql
go get github.com/99designs/gqlgen           # requires Go 1.21+
go run github.com/99designs/gqlgen init       # creates schema.graphqls, gqlgen.yml, server.go
# edit schema.graphqls, then regenerate types + resolver stubs:
go run github.com/99designs/gqlgen generate
what gqlgen generates
generated.goThe execution engine wiring — routing, argument coercion, the runtime. Don't edit.
models_gen.goGo structs matching your SDL types (or map to your own models via gqlgen.yml).
schema.resolvers.goResolver method stubs you fill in. Regen adds new stubs for new schema fields without clobbering your code.
schema.graphqlsgraphql
type User { id: ID!  email: String!  posts: [Post!]! }
type Post { id: ID!  title: String!  author: User! }
type Query { user(id: ID!): User }
schema.resolvers.go — implement the stubsgo
// User returns the user for the given id. (a Query resolver stub, filled in)
func (r *queryResolver) User(ctx context.Context, id string) (*model.User, error) {
    return r.DB.UserByID(ctx, id)
}

// Author resolves Post.author — the N+1 edge; batch via a loader from ctx.
func (r *postResolver) Author(ctx context.Context, obj *model.Post) (*model.User, error) {
    return loadersFrom(ctx).User.Load(ctx, obj.AuthorID)
}

func main() {
    srv := handler.New(generated.NewExecutableSchema(generated.Config{
        Resolvers: &Resolver{DB: db},
    }))
    srv.AddTransport(transport.POST{})
    http.Handle("/query", loaderMiddleware(db, srv)) // inject per-request loaders
    log.Fatal(http.ListenAndServe(":8080", nil))
}
◆ why codegen suits Go

Go has no decorators or runtime type hints, so the schema-first + codegen path gives you compile-time-checked resolvers: implement the wrong signature and it won't build. The generated queryResolver/postResolver interfaces are your contract. Loaders typically come from github.com/vikstrous/dataloadgen (a generics-based DataLoader) wired in via middleware so each request gets its own — same per-request rule as everywhere else.

Clients

From the consumer side. The floor is a fetch; the ceiling is a normalized cache with typed, codegen'd operations.

the zero-dependency baselinejavascript
const res = await fetch("/graphql", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({
    query: `query U($id:ID!){ user(id:$id){ id email } }`,
    variables: { id: "42" },         // variables stay separate from the query text
  }),
});
const { data, errors } = await res.json();

When to graduate to a client library

LibraryStrength
Apollo ClientNormalized cache, React hooks, large ecosystem, optimistic updates. The heavyweight default.
urqlLighter, composable "exchanges", document caching by default — graphs to normalized when you add it.
RelayStrictest and most powerful: compiler-enforced fragment colocation, demands the Connection spec. Best at very large scale.
graphql-codegenNot a runtime — generates typed hooks/operations from your schema + query documents. Pair with any of the above.
◆ the two ideas worth taking from client land

Normalized caching: a smart client stores entities by __typename:id, so updating a User in one query updates it everywhere it appears — no manual cache busting. This is the main reason to adopt Apollo/Relay over raw fetch. Fragment colocation: each UI component declares its own data needs as a fragment, and the page query is composed from them — so a component and its data requirements live and change together. Combined with graphql-codegen, you get end-to-end types from schema to React prop.

12

Production concerns

A single flexible endpoint is a security and caching liability unless you constrain it. This is what separates a demo from a deployed service.

Security — the flexible endpoint is the attack surface

The same field-level freedom that helps clients lets attackers craft expensive queries. A handful of controls are non-negotiable:

  • Depth limiting. Cap nesting depth. Without it, a cyclic schema (user → posts → author → posts → …) lets one request fan out into millions of resolver calls — a trivial DoS.
  • Cost / complexity analysis. Assign each field a cost and reject queries over a budget before executing. More robust than depth alone because a wide-but-shallow query is also expensive.
  • Persisted queries / trusted documents. Only allow pre-registered operations (client sends a hash). Eliminates arbitrary query execution entirely and shrinks requests — caching and security together.
  • Disable introspection in production (or gate it) so the full schema isn't a public map for attackers. Pair with disabling field suggestions in errors.
  • Pagination caps & timeouts. Enforce a max first:, set per-resolver and per-request timeouts.
▲ gotcha — auth belongs in resolvers/context, not the gateway

You can't authorize by URL or HTTP verb here — every operation hits one endpoint with one method. Authorization is per-field/per-object, enforced in resolvers using the authenticated principal on context (or via schema directives / a policy layer). A request that's allowed to call user may not be allowed to read user.ssn — that's a field-level decision the transport can't make for you.

Caching

No HTTP caching by default (everything's a POST). Three levers: persisted-query GETs for CDN/browser caching of whole responses; a server-side response cache keyed by query+variables with per-type/field TTLs (Apollo's @cacheControl, Yoga's response-cache plugin); and the client normalized cache (§11) for entity-level reuse on the frontend. DataLoader's per-request cache (§05) is a fourth, narrower layer.

Federation & the backend-for-frontend

At scale, one monolithic schema owned by one team doesn't fit a large org. Federation (Apollo Federation v2, plus alternatives like Cosmo/Hive) lets independent teams own subgraphs — each a normal GraphQL service that declares which types it contributes and how they join on shared keys. A router/gateway (Apollo's is written in Rust) composes them into one supergraph and plans each query across subgraphs. This is the dominant enterprise pattern: GraphQL as a composition layer over REST/gRPC services owned by separate teams.

Observability & errors

Instrument with OpenTelemetry — trace each operation and ideally each resolver to find the slow field and spot N+1 you missed. Log by operation name (another reason to always name operations). For errors, keep the discipline from §04: expected business failures modeled as schema result unions, unexpected failures in errors[] with a stable extensions.code, and never leak internal messages/stack traces to clients in production.

◆ the production checklist

Before going live: depth + complexity limits on, introspection gated, persisted/trusted documents enforced, per-request DataLoaders, response timeouts, query-cost metrics and per-operation tracing, and field-level authorization. Missing any one of the first three has put real GraphQL endpoints down — the famous case being teams who simply disabled GraphQL in production rather than secure it.

The five things people get wrong

  1. No DataLoader → N+1 storms on every nested query.
  2. Over-using ! → one failed leaf nulls a whole response branch.
  3. Sharing a DataLoader across requests → cross-user data leaks.
  4. Shipping with introspection on and no depth/complexity limits → DoS surface.
  5. Mismatched subscription subprotocol (graphql-ws lib vs graphql-transport-ws wire name) → silent dead connection.
