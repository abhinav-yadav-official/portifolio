01Why Go (and what it deliberately isn't)

Go was built at Google by people who were tired of slow builds, dependency hell, and concurrency that needed a PhD. Every design decision optimises for one thing: large teams shipping reliable services for a decade. Understanding that goal explains every "weird" choice you're about to meet.

The pitch in one paragraph

Go is a statically typed, compiled, garbage-collected language with a runtime that schedules lightweight goroutines across OS threads. It compiles to a single static binary with no external runtime — you scp one file and it runs. It has a famously small spec (you can hold the whole language in your head), a formatter everyone uses without arguing, and a standard library good enough to build a production HTTP server with zero dependencies.

Why this matters for you

Coming from Python/Django, the mental shift is: the compiler and the runtime do work that you used to do at runtime or in review. Types catch shape errors before deploy; the race detector catches concurrency bugs in CI; go vet and gofmt end style debates. You trade some expressiveness for the machine carrying more of the correctness burden.

What Go deliberately leaves out

  • No exceptions. Errors are ordinary values you return and check. This is the single biggest cultural difference — and the source of the if err != nil meme.
  • No classes or inheritance. You get structs, methods, and interfaces satisfied implicitly. Composition over inheritance isn't a guideline here; it's the only option.
  • No constructors, no overloading, no default args, no ternary. One obvious way to do things, even when it's more typing.
  • Generics arrived late (1.18, 2022) and are intentionally limited. The community still prefers concrete code where it reads more clearly.
Internals · the value proposition under the hood

A goroutine starts with an ~8 KB growable stack (vs ~1–8 MB for an OS thread), so you can run hundreds of thousands of them. The runtime multiplexes them onto a small pool of OS threads using an M:N scheduler (the GMP model — §11). That's why "just spawn a goroutine per request" is sane in Go and "spawn a thread per request" is not in most languages.

When not to reach for Go

Heavy numerical/ML work (Python's ecosystem wins), hard-real-time systems (GC pauses, though sub-millisecond now), or anything needing a rich expressive type system (Rust/Haskell). Go's sweet spot is networked services, CLIs, infrastructure tooling, and anything where operational simplicity beats cleverness. Kubernetes, Docker, Terraform, Prometheus, and etcd are all Go — that's not a coincidence.

02The toolchain & modules

There is exactly one toolchain, it ships with the language, and you'll use a handful of commands daily. No pip vs poetry vs uv debates — just go.

Installing & the one-command tour

terminalbash

go mod init github.com/abhinav/api   # create a module (run once per project)

Convention · gofmt is law

There is no style guide argument in Go because gofmt ends it. Tabs for indentation, specific brace placement, sorted imports — all enforced. Configure your editor to run gofmt (or goimports, which also fixes import lines) on save. A diff that only contains formatting changes signals someone forgot to.

Modules: how dependencies actually work

A module is a tree of packages versioned together, defined by a go.mod file at its root. The module path (e.g. github.com/abhinav/api) is both its identity and the import prefix for its packages.

Go fetches the exact source for a version, hashes it, and refuses to build if it doesn't match go.sum — defending against a dependency being re-tagged or tampered with after you vetted it. internal/ is enforced by the compiler, not convention. Any package under an internal/ directory can only be imported by code rooted at the directory's parent. Put domain logic there and outsiders physically cannot import it — perfect for keeping your public API surface tiny.

03Syntax, types & the zero value

Go's syntax is C-family but reads "backwards" in places (type after name) for good reasons. Let's decode every symbol you'll see.

Your first program, annotated

main.gogo
package main          // every file belongs to a package; "main" = an executable

import "fmt"          // pull in the standard formatting package

func main() {         // main() in package main is the program entrypoint
    msg := "hello"    // := declares AND infers type (string) in one step
    fmt.Println(msg)  // exported (capitalised) identifier from fmt
}
SymbolMeaning
packageThe compilation unit. Files in the same directory must share one package name. main is special: it builds an executable with an entry func main().
:=Short variable declaration. Declares a new variable and infers its type from the right-hand side. Usable only inside functions.
=Plain assignment to an already-declared variable.
var x intExplicit declaration. Required at package scope (where := is illegal). Initialises to the zero value.
Capital letterVisibility is encoded in case. Println is exported (public); println would be package-private. No public/private keywords exist.
Why is the type after the name?

var x int not int x. Go's declaration syntax reads left-to-right like English ("x is an int") and stays readable for complex types: var f func(int) (string, error) reads cleanly, whereas C's char (*(*x[3])())[5] famously does not. Same reason := exists — to make the common case (declare+assign) a single, scannable line.

The zero value: Go has no null surprises (mostly)

Every type has a zero value that a variable takes if you don't initialise it. There is no "uninitialised garbage" and no separate "undefined."

zero valuesgo
var i int        // 0
var f float64    // 0.0
var b bool       // false
var s string     // ""  (empty, never nil — strings can't be nil)
var p *int       // nil (pointer)
var sl []int     // nil (but usable! len/append work on a nil slice)
var m map[string]int  // nil (reads ok, WRITES PANIC — see §7)
var err error    // nil
Convention · make the zero value useful

Idiomatic Go designs structs so the zero value already works. sync.Mutex{} is a ready-to-use unlocked mutex; bytes.Buffer{} is a ready-to-use empty buffer — no constructor needed. When you design a type, ask: "does var t MyType do something sensible?"

Gotcha · no implicit numeric conversion

Go will not auto-convert between numeric types. var i int = 3; var f float64 = i is a compile error. You must write float64(i). Annoying at first, but it eliminates a whole class of silent precision/overflow bugs. The same rule means int32 and int are distinct types even on a 32-bit machine.

Constants & iota

Internals · untyped constants

const Pi = 3.14159 has no type until used. Constants live with arbitrary precision at compile time, so const Big = 1 << 62 is fine even though it'd overflow in some contexts — the type is assigned (and overflow checked) only at the point of use. This is why you can write var x float64 = Pi and var y float32 = Pi from the same constant.

04Control flow & loops

One loop keyword. A switch that does more than C's. And an if that can scope a variable to the branch. Small surface, lots of leverage.

for is the only loop

loops.gogo
// classic three-clause
for i := 0; i < 10; i++ { }

// while-style (no "while" keyword)
for n > 1 { n /= 2 }

// infinite loop
for { /* break out when done */ }

// range over slice: index, value
for i, v := range nums { fmt.Println(i, v) }

// range over map: key, value (ORDER IS RANDOMISED — see gotcha)
for k, v := range m { }

// range over channel: receive until closed
for msg := range ch { }

// Go 1.22+: range over an integer
for i := range 5 { fmt.Println(i) }   // 0,1,2,3,4

// Go 1.23+: range over a function (iterators)
for v := range myIterator { }
Gotcha · map iteration order is intentionally random

Go randomises map iteration order on every run — by design, to stop you accidentally depending on it. If you need deterministic order, collect keys into a slice and sort them. Tests that iterate a map and assert order will flake.

Gotcha (historical) · the loop variable trap — fixed in Go 1.22

Before Go 1.22, the loop variable was shared across iterations. for _, v := range items { go func(){ use(v) }() } would print the last item N times because every goroutine closed over the same v. Go 1.22 changed the semantics so each iteration gets a fresh variable. If you read older code or run with an older go directive, the old behaviour applies — this is the single most famous Go footgun, now mostly defused.

if with an init statement

if-initgo
// the workhorse error pattern: scope err to just this if
if v, err := strconv.Atoi(s); err != nil {
    return fmt.Errorf("parsing %q: %w", s, err)
} else {
    use(v)  // v and err only exist inside this if/else
}

// guard clause style (preferred — flat, not nested)
v, err := strconv.Atoi(s)
if err != nil {
    return err
}
use(v)
Convention · return early, keep the happy path un-indented

Idiomatic Go handles errors with guard clauses and returns immediately, so the "success" code marches down the left margin with no nesting. If you find yourself writing } else { after a block that returns, delete the else — the linter golangci-lint will flag it.

switch — no fallthrough, no break needed

switch.gogo
switch day {
case Saturday, Sunday:        // multiple values per case
    return "weekend"
case Monday:
    return "ugh"
default:
    return "weekday"
}                              // cases do NOT fall through by default

// expression-less switch = clean if/else-if ladder
switch {
case score >= 90: grade = "A"
case score >= 80: grade = "B"
default:          grade = "F"
}

// type switch (covered fully in §9)
switch x := any.(type) {
case int:    fmt.Println("int", x)
case string: fmt.Println("string", x)
}
Why no automatic fallthrough?

In C, forgetting break is a classic bug. Go inverts the default: each case breaks automatically. If you genuinely want C-style fallthrough, you opt in with the explicit fallthrough keyword — making the rare case visible and the common case safe.

05Functions, multiple returns & defer

Functions are first-class values. Multiple return values are everywhere (it's how errors travel). And defer is Go's answer to "make sure cleanup happens."

Signatures & multiple returns

functions.gogo
// (T1, T2) return — the idiomatic (value, error) pair
func divide(a, b float64) (float64, error) {
    if b == 0 {
        return 0, errors.New("divide by zero")
    }
    return a / b, nil
}

// named return values — declared in the signature, returned by bare "return"
func split(sum int) (x, y int) {
    x = sum * 4 / 9
    y = sum - x
    return            // "naked return" returns the named x, y
}

// variadic parameters: zero or more ints
func sum(nums ...int) int {
    total := 0
    for _, n := range nums { total += n }
    return total
}
sum(1, 2, 3)          // call with args
sum(slice...)         // spread a slice with ...
Gotcha · naked returns hurt readability

Named returns are handy with defer (you can mutate the result in a deferred func), but naked returns in long functions make it hard to see what's actually returned. Convention: use named returns for documentation and defer-mutation, but still write explicit return x, y in anything longer than a few lines.

Functions as values & closures

closures.gogo
// a function type
type HandlerFunc func(w http.ResponseWriter, r *http.Request)

// closure: captures `count` by reference
func counter() func() int {
    count := 0
    return func() int {
        count++          // mutates the captured variable
        return count
    }
}
next := counter()
next(); next()           // 1, then 2 — state lives in the closure
Internals · closures cause heap escape

When a closure captures a local variable, that variable can no longer live on the stack (the stack frame disappears when the function returns, but the closure outlives it). Go's escape analysis detects this at compile time and silently allocates count on the heap. Run go build -gcflags='-m' to see escape decisions printed — useful when chasing allocations in hot paths (§8).

defer: cleanup that can't be forgotten

defer.gogo
func readFile(path string) ([]byte, error) {
    f, err := os.Open(path)
    if err != nil {
        return nil, err
    }
    defer f.Close()      // runs when readFile returns, no matter HOW it returns

    return io.ReadAll(f)
}

// multiple defers run LIFO (last-in, first-out)
func order() {
    defer fmt.Println("1")
    defer fmt.Println("2")
    defer fmt.Println("3")
}                        // prints 3, 2, 1
Why defer instead of try/finally?

You put the cleanup right next to the acquisition — os.Open then immediately defer f.Close() — so the reader sees the lifecycle in one place, and you can't forget to close on an early return. There's no separate finally block far below that someone might not update when adding a new exit path.

Gotcha · deferred arguments evaluate immediately

defer fmt.Println(i) captures i's value now, but the call runs later. So i := 1; defer fmt.Println(i); i = 2 prints 1. If you want the late value, defer a closure: defer func(){ fmt.Println(i) }(). Also: deferring inside a loop stacks up all the defers until the function returns — don't defer f.Close() inside a 10k-iteration loop or you'll hold 10k files open. Extract the body into its own function.

06Slices & arrays — the internals that bite

Slices are the Go data structure, and the place experienced engineers from other languages get tripped up. Understanding the three-word header explains every surprise.

Arrays vs slices

An array has a fixed length that's part of its type: [3]int and [4]int are different types, and arrays are value types — copying one copies all elements. You'll rarely use them directly. A slice is a flexible, growable view into an underlying array.

Internals · a slice is a 3-word header

A slice value is literally this struct (from the runtime):

type slice struct { ptr *T; len int; cap int }

ptr → start of the backing array, len → how many elements are visible, cap → how many fit before a reallocation. When you pass a slice to a function, you copy these three words — not the data. That's why the function sees the same backing array (and can mutate your elements) but can't make your slice longer.

slices.gogo
s := []int{2, 3, 5, 7}        // literal; len=4 cap=4
s = make([]int, 0, 10)        // make([]T, len, cap): empty but cap for 10

s = append(s, 11)             // append returns a (possibly new) slice — ALWAYS reassign
s = append(s, more...)        // spread another slice in

sub := s[1:3]                 // slicing: [low:high] → len=2, SHARES backing array
sub = s[1:3:3]                // three-index [low:high:max] caps the new slice

fmt.Println(len(s), cap(s))   // length and capacity
Gotcha · append can alias — or not — and that's the bug

append writes into the existing backing array if there's spare capacity; otherwise it allocates a new, bigger array and copies. So whether two slices sharing a backing array affect each other depends on cap at runtime — a Heisenbug. The fix: when you slice-then-append and need isolation, use the three-index slice s[a:b:b] (forces the next append to reallocate) or copy explicitly. Always reassign the result of append (s = append(s, x)) — ignoring the return is the #1 slice mistake.

The classic sharing bug, made concrete

aliasing.gogo
original := []int{1, 2, 3, 4, 5}
view := original[1:3]          // [2 3], but cap=4 (reaches to end of original)

view = append(view, 99)        // cap available! writes into original[3]
// original is now [1 2 3 99 5]  ← surprise! you mutated original

// SAFE: cut off the capacity
view := original[1:3:3]        // cap=2 now
view = append(view, 99)        // forced to allocate; original untouched
Internals · how append grows capacity

When capacity runs out, Go grows the backing array — historically "double until 1024 elements, then grow ~1.25×." The exact factor changed in Go 1.18 to a smoother curve, but the takeaway holds: growth is amortised O(1), and if you know the final size, make([]T, 0, n) avoids all the intermediate copies. In a hot loop that builds a big slice, pre-sizing is a real, measurable win.

Gotcha · the memory-leak slice

Slicing a huge slice down to a tiny view keeps the entire backing array alive — the GC can't free it while any slice references it. If you extract a 10-byte header from a 10 MB buffer and keep it around, you've pinned 10 MB. Fix: append([]byte(nil), small...) or bytes.Clone to copy just what you need.

copy & iterating

copy.gogo
dst := make([]int, len(src))
n := copy(dst, src)           // copies min(len(dst),len(src)) elements

// delete element i preserving order (the idiom)
s = append(s[:i], s[i+1:]...)
// Go 1.21+: cleaner with the slices package
s = slices.Delete(s, i, i+1)
slices.Sort(s)                // generic sort, no boilerplate
i, found := slices.BinarySearch(s, 7)

07Maps & structs

Maps: hash tables with sharp edges

maps.gogo
m := make(map[string]int)     // create (nil map can be READ but not written)
m["a"] = 1                    // set

v := m["a"]                   // get; MISSING KEY RETURNS ZERO VALUE, not an error
v, ok := m["x"]               // comma-ok: ok==false if key absent
delete(m, "a")                // remove
n := len(m)                   // size

// literal
prices := map[string]float64{"coffee": 3.5, "tea": 2.0}
Gotcha · writing to a nil map panics

var m map[string]int gives you a nil map. Reads return the zero value silently, but m["x"] = 1 panics at runtime. Always initialise with make or a literal before writing. This asymmetry catches everyone once.

Gotcha · you can't take the address of a map element

&m["k"] is a compile error, and you can't mutate a struct field in place: m["k"].Field = 1 won't compile. Reason: maps may rehash and move entries, so a pointer into one would dangle. Fix: read the value out, modify, write it back — or store map[K]*V (pointers to structs) when you need in-place mutation.

Internals · maps are not concurrency-safe

Concurrent map read+write triggers a deliberate runtime panic ("concurrent map writes") — the runtime detects it and crashes you rather than corrupting memory silently. For concurrent access use a sync.RWMutex around the map, or sync.Map for specific read-heavy patterns. The race detector (go test -race) will also flag it. Don't reach for sync.Map by default — a plain map + mutex is usually faster and clearer.

Structs: aggregate types

structs.gogo
type User struct {
    ID        int64
    Name      string
    Email     string    `json:"email"`        // struct tag (metadata, §18)
    CreatedAt time.Time `json:"created_at"`
    internal  bool      // lowercase = unexported field
}

u := User{ID: 1, Name: "Abhinav"}   // field-keyed literal (preferred)
u2 := User{1, "A", "a@x.com", time.Now(), false} // positional (fragile — avoid)

u.Name = "Updated"                  // dot access
p := &u                             // pointer to struct
p.Name = "Via pointer"              // Go auto-derefs: (*p).Name not needed

// anonymous struct — handy for one-off shapes (e.g. JSON responses)
resp := struct {
    OK   bool   `json:"ok"`
    Data string `json:"data"`
}{OK: true, Data: "hi"}
Internals · struct field ordering affects size

Structs are laid out in declaration order with alignment padding. struct{ a bool; b int64; c bool } can be 24 bytes (1+7pad+8+1+7pad) while struct{ b int64; a bool; c bool } is 16. For millions of structs this matters; tools like fieldalignment (in golang.org/x/tools) auto-detect and reorder. Don't micro-optimise prematurely, but know the lever exists.

Embedding: composition, not inheritance

embedding.gogo
type Base struct {
    ID        int64
    CreatedAt time.Time
}
func (b Base) Age() time.Duration { return time.Since(b.CreatedAt) }

type Article struct {
    Base               // embedded (no field name) — "promotes" its fields/methods
    Title string
}

a := Article{Base: Base{ID: 1, CreatedAt: time.Now()}, Title: "Hi"}
a.ID        // promoted field — reach in directly
a.Age()     // promoted method — Article "has" Base's behaviour
Why embedding instead of inheritance?

Embedding gives you method/field promotion (the convenience of inheritance) without the fragile base-class problem. Article doesn't extend Base — it contains one and forwards to it. There's no virtual dispatch surprise: if both Article and Base define Age(), the outer one wins and the inner is still reachable as a.Base.Age(). Explicit, no magic.

08Pointers, stack vs heap & escape analysis

Go has pointers but no pointer arithmetic. The interesting part isn't the syntax — it's that the compiler, not you, decides what lives on the stack vs the heap.

The two operators

pointers.gogo
x := 42
p := &x        // & "address of" → p is *int, points at x
fmt.Println(*p) // * "dereference" → reads through the pointer: 42
*p = 99        // writes through the pointer; x is now 99

// pointers let a function mutate its caller's value
func increment(n *int) { *n++ }
increment(&x)  // x becomes 100

// new(T) allocates a zeroed T and returns *T
ptr := new(int)  // *int pointing at a fresh 0
Why no pointer arithmetic?

You can't do p++ to walk memory. That removes an entire category of buffer-overrun and use-after-free bugs, and lets the garbage collector know exactly where every pointer is. unsafe.Pointer exists as an escape hatch for the 0.1% of cases (zero-copy conversions, syscalls), and the name is a warning label.

Value vs pointer: when to use which

Pass by valuePass by pointer
Small structs (a few words)Large structs (avoid copying)
You want immutability / a copyYou need to mutate the caller's value
time.Time, small value typesAnything with a sync.Mutex (must not be copied)
Slices/maps/channels (already reference-like)When "no value" is meaningful (nil pointer)
Gotcha · never copy a type containing a Mutex

Copying a struct that embeds sync.Mutex copies the lock's internal state — now two "different" locks guard the same data and neither protects anything. go vet catches this ("copies lock value"). Rule of thumb: types with a mutex are passed and stored by pointer, always.

Stack vs heap — decided by escape analysis

In C you choose malloc vs stack. In Go you don't — the compiler runs escape analysis: if a value's lifetime is provably bounded by the function, it goes on the (fast, auto-freed) stack; if it "escapes" (returned, captured by a closure, stored in something that outlives the call, or too large), it goes on the heap and the GC manages it.

escapebash
func stackAlloc() int {
    x := 42        // stays on stack — never escapes
    return x       // returns a COPY
}

func heapAlloc() *int {
    x := 42        // escapes! a pointer to x outlives the function
    return &x      // → compiler moves x to the heap
}
terminalbash
go build -gcflags='-m' ./...
# ./main.go:8:2: moved to heap: x        ← escape analysis report
# ./main.go:3:2: x does not escape
Internals · returning a pointer to a local is safe (and idiomatic)

In C, return &x for a local is a dangling-pointer bug. In Go it's fine and common — escape analysis guarantees x is heap-allocated when needed, so the pointer stays valid. This is why Go constructors return *T without ceremony. The cost is a heap allocation + GC pressure, which is why hot paths sometimes pass values or use sync.Pool to recycle objects.

Internals · the garbage collector

Go uses a concurrent, tri-color mark-and-sweep collector tuned for low latency over throughput. It runs alongside your program with sub-millisecond stop-the-world pauses, typically targeting <1 ms. You tune it with GOGC (default 100 = collect when heap doubles) or the newer GOMEMLIMIT (a soft memory ceiling — invaluable in containers to avoid OOM-kills). For latency-sensitive services, set GOMEMLIMIT to ~90% of the pod's memory limit and the GC will pace itself instead of being killed by the OOM killer.

09Methods & interfaces — Go's superpower

Interfaces are how Go does polymorphism, dependency injection, and testability. They're satisfied implicitly, which feels strange for a day and then feels like a gift.

Methods: functions with a receiver

methods.gogo
type Counter struct{ n int }

// value receiver — operates on a COPY, can't mutate the original
func (c Counter) Value() int { return c.n }

// pointer receiver — can mutate; required to change state
func (c *Counter) Inc() { c.n++ }

c := Counter{}
c.Inc()        // Go auto-takes &c → (&c).Inc()
c.Value()      // 1
Convention · pick one receiver type per type

If any method needs a pointer receiver (to mutate, or because the struct is large), make all methods pointer receivers for consistency. Mixing value and pointer receivers on one type leads to subtle method-set bugs (below). The community rule: "when in doubt, use a pointer receiver."

Interfaces: behaviour, satisfied implicitly

interfaces.gogo
// an interface is a set of method signatures
type Stringer interface {
    String() string
}

type Point struct{ X, Y int }

// Point satisfies Stringer just by HAVING the method —
// no "implements" keyword, no declaration of intent
func (p Point) String() string {
    return fmt.Sprintf("(%d, %d)", p.X, p.Y)
}

var s Stringer = Point{1, 2}   // works automatically
fmt.Println(s.String())        // (1, 2)
Why implicit satisfaction?

Because the consumer defines the interface it needs, not the producer. You can write an interface that os.File satisfies without modifying the os package. This decouples packages completely: your code depends on a tiny interface{ Read(p []byte) (int, error) }, and anything with a matching method fits — files, network connections, in-memory buffers, your test mock. It's structural typing with compile-time checking.

Convention · accept interfaces, return structs; keep them small

"The bigger the interface, the weaker the abstraction." The standard library's most-used interfaces have one method: io.Reader, io.Writer, fmt.Stringer, error. Define interfaces in the package that uses them, sized to exactly what that function needs — not a giant "Repository" interface with 30 methods.

The empty interface & any

any.gogo
var x any = 42        // any == interface{} (alias since Go 1.18); holds anything

// type assertion: pull the concrete type back out
n, ok := x.(int)      // ok==true, n==42 ; comma-ok form never panics
n := x.(int)          // panics if x isn't an int — use only when certain

// type switch: branch on dynamic type
switch v := x.(type) {
case int:    fmt.Println("int:", v)
case string: fmt.Println("string:", v)
case nil:    fmt.Println("nil")
default:     fmt.Printf("unknown: %T\n", v)
}
Internals · an interface value is two words (the iface)

An interface value is a pair: (type pointer, data pointer). The type pointer references an itab (interface table) holding the concrete type's info and a function pointer for each method — this is Go's vtable, built once per (interface, concrete-type) pair. Method calls through an interface are an indirect jump through that table, which is why interface dispatch is slightly slower than a direct call and can't be inlined. For empty interfaces, it's (type, data); for typed interfaces, (itab, data).

Gotcha · the typed-nil interface trap

An interface is nil only when both its type and data words are nil. If you store a nil pointer of a concrete type in an interface, the interface is not nil — its type word is set:

var p *MyError = nil; var err error = p; err != nil // TRUE!

This bites hard with error returns: returning a nil *MyError as an error makes if err != nil true even though "there's no error." Fix: return a literal nil, or check and return nil explicitly. This is one of the most infamous Go interview questions.

Method sets & the pointer-receiver subtlety

Internals · who satisfies the interface — T or *T?

If a method has a pointer receiver func (c *Counter) Inc(), then only *Counter satisfies an interface requiring Inc() — a plain Counter value does not. (A value's address isn't always available, e.g. a map element, so the language can't auto-take it for interface satisfaction.) Value-receiver methods are in the method set of both T and *T. Practical effect: var w io.Writer = myBuf may fail while var w io.Writer = &myBuf works. When an interface assignment mysteriously won't compile, this is almost always why.

10Generics (type parameters)

Added in Go 1.18 after a decade of debate. Use them for genuinely type-agnostic containers and algorithms — not as a hammer for everything.

generics.gogo
// [T any] declares a type parameter T constrained to "any type"
func Map[T, U any](s []T, f func(T) U) []U {
    out := make([]U, len(s))
    for i, v := range s {
        out[i] = f(v)
    }
    return out
}

doubled := Map([]int{1, 2, 3}, func(n int) int { return n * 2 })
// T and U inferred from the arguments — no explicit Map[int,int] needed

// constraints restrict what operations are allowed
type Number interface {
    ~int | ~int64 | ~float64    // | is a union ; ~ means "underlying type"
}
func Sum[T Number](nums []T) T {
    var total T
    for _, n := range nums { total += n }   // + is allowed because Number permits it
    return total
}

Why so cautious with generics?

Before 1.18, type-agnostic code meant interface{} + runtime assertions (unsafe) or code generation (clunky). Generics fix that for containers (slices, maps packages are now generic) and algorithms. But Go's philosophy is "a little copying is better than a little dependency" — if a concrete []string version reads more clearly than a generic one, write the concrete one. Generics are a tool for library authors more than application code.

Internals · GC-shape stenciling

Go doesn't fully monomorphise like C++ (which would bloat binaries) nor fully box like Java. It uses GC-shape stenciling: one compiled instance is shared across all types with the same memory layout/pointer-shape (e.g. all pointer types share one stencil), passing a hidden dictionary of type info at runtime. The upshot: small binary growth, but generic code over pointer types has a slight dictionary-lookup overhead vs hand-written concrete code. Rarely matters; occasionally does in tight loops.

Convention · the standard generic helpers

Reach for the stdlib first: slices.Sort, slices.Contains, slices.Index, maps.Keys, maps.Clone, cmp.Compare, and min/max (builtins since 1.21). These cover 90% of what people used to write generics for.

Part III · Concurrency

11Goroutines & the scheduler (GMP)

"Don't communicate by sharing memory; share memory by communicating." Concurrency is Go's headline feature, and the runtime scheduler is the machinery that makes "spawn a goroutine per request" actually work.

Spawning concurrency is one keyword

goroutines.gogo
go doWork()              // launch doWork concurrently; main does NOT wait
go func() {              // anonymous goroutine
    fmt.Println("hi")
}()

// the catch: main returning kills all goroutines instantly
func main() {
    go fmt.Println("might never print")
    // main exits → program exits → goroutine may not run
}
Gotcha · goroutines need a reason to be waited for

A bare go f() with nothing synchronising it is almost always a bug. When main returns, the process exits and every goroutine is killed mid-flight — no cleanup, no defers. You need a sync.WaitGroup, a channel, or errgroup to wait. time.Sleep "to let it finish" is the canonical beginner mistake and a flaky-test generator.

Concurrency ≠ parallelism

Concurrency is structuring a program as independently executing pieces. Parallelism is actually running them simultaneously on multiple cores. Go gives you concurrency as a language feature; the runtime delivers parallelism when cores are available. You write the same code either way.

Internals · the GMP scheduler

The runtime schedules goroutines onto OS threads with three entities:

  • G — a goroutine: its stack, instruction pointer, and state. Cheap (~2 KB start, grows/shrinks).
  • M — a machine: an actual OS thread that executes code.
  • P — a processor: a scheduling context holding a local run-queue of Gs. The number of P's = GOMAXPROCS (default = CPU cores).

An M must hold a P to run Go code. The scheduler is M:N — many goroutines multiplexed onto few threads. Each P has a local queue (lock-free fast path); when empty, it work-steals from other P's queues. A global queue and a netpoller (epoll/kqueue/IOCP) round it out.

Internals · why blocking I/O doesn't block your threads

This is the magic. When a goroutine does network I/O, the runtime parks it on the netpoller and frees the M to run other goroutines — the OS thread is never blocked waiting on a socket. When the I/O is ready, the netpoller wakes the goroutine. For a blocking syscall (e.g. file read), the runtime detaches the M+G from the P and spins up/reuses another M so the P keeps scheduling. Result: 100k goroutines doing network I/O cost a handful of threads, not 100k. This is why Go web servers handle massive concurrency without an explicit event loop — the runtime is the event loop.

Internals · preemption

Originally Go was cooperatively scheduled — a goroutine yielded only at function calls/allocations, so a tight loop with no calls could hog a P forever. Since Go 1.14 the scheduler is asynchronously preemptive: it sends a signal to interrupt long-running goroutines at safe points. This is why a CPU-bound goroutine no longer starves others. You rarely think about it, but it's why for {} won't wedge your whole program anymore.

Convention · GOMAXPROCS in containers

GOMAXPROCS defaults to the machine's core count, which in a CPU-limited container (e.g. a 0.5-CPU k8s pod on a 64-core node) means Go thinks it has 64 P's — causing excessive context-switching and GC threads. Set it to your CPU limit, or use go.uber.org/automaxprocs (a blank import that reads cgroup limits). Go 1.25+ is making this cgroup-aware by default; until you're on it, set it explicitly.

WaitGroup: wait for N goroutines

waitgroup.gogo
var wg sync.WaitGroup
for _, url := range urls {
    wg.Add(1)                // increment BEFORE starting the goroutine
    go func(u string) {
        defer wg.Done()      // decrement when this goroutine finishes
        fetch(u)
    }(url)                   // pass url as arg (pre-1.22 capture safety)
}
wg.Wait()                    // blocks until counter hits 0
Gotcha · Add inside the goroutine is a race

Call wg.Add(1) before go, on the parent goroutine. If you call it inside the new goroutine, wg.Wait() might run before the Add and return early. Also: a WaitGroup must not be copied after first use — pass it by pointer.

12Channels & select

Channels are typed pipes that also synchronise. They're how goroutines hand off data and coordinate without explicit locks.

channels.gogo
ch := make(chan int)        // unbuffered: send blocks until a receiver is ready
buf := make(chan int, 100)  // buffered: send blocks only when full

ch <- 42                    // send (arrow points INTO the channel)
v := <-ch                   // receive (arrow points OUT)
v, ok := <-ch               // ok==false if channel is closed AND drained

close(ch)                   // close: signals "no more values" (sender's job)
for v := range ch {         // range receives until the channel is closed
    use(v)
}
Direction / opMeaning
chan intBidirectional channel of ints.
chan<- intSend-only (used in function params to restrict usage).
<-chan intReceive-only.
unbufferedA send rendezvous: sender and receiver meet — a synchronisation point.
bufferedDecouples sender/receiver up to capacity; send blocks only when full.
Why channels instead of locks?

Locks protect state; channels transfer ownership. When you send a value on a channel, you're conceptually handing it off — only one goroutine "owns" it at a time, so there's no shared mutable state to race over. This makes data-flow pipelines (producer → worker → consumer) natural to express and reason about. That said, sometimes a plain mutex around a counter is the right tool — Go gives you both and the idiom is "use whichever is simpler for the problem."

select: wait on multiple channels

select.gogo
select {
case msg := <-ch1:
    handle(msg)
case ch2 <- value:           // a send can be a case too
    sent()
case <-time.After(2 * time.Second):
    return errors.New("timeout")     // timeout pattern
case <-ctx.Done():
    return ctx.Err()                 // cancellation pattern
default:
    // runs if NO case is ready — makes the select non-blocking
}
Internals · select is fair-random, not ordered

If multiple cases are ready simultaneously, select picks one uniformly at random — not top-to-bottom. This prevents starvation of later cases. A default case makes the whole select non-blocking (it's chosen only when nothing else is ready). Don't put a default in a loop that should block, or you'll busy-spin and burn a CPU.

Channel deadlocks & closing rules

Gotcha · the close rules that cause panics
  • Sending on a closed channel → panic.
  • Closing a closed channel → panic.
  • Closing a nil channel → panic.
  • Receiving from a closed channel → returns zero value immediately, ok=false (safe).
  • Send/receive on a nil channel → blocks forever (useful trick to disable a select case).

Rule: the sender closes, never the receiver, and only one goroutine should close. With multiple senders, coordinate close via a separate "done" channel or sync.Once — never let senders race to close.

Gotcha · "all goroutines are asleep — deadlock!"

An unbuffered ch <- 1 with no receiver, or <-ch with no sender, blocks forever. If every goroutine is blocked, the runtime detects it and panics with this message — a gift, because it surfaces the bug instead of hanging. (It can't detect partial deadlocks where some goroutines still run, e.g. a leaked goroutine waiting on a channel nobody will ever send to — those just leak silently. Watch your goroutine count in metrics.)

13sync, context & the patterns that matter

The sync toolbox

sync.gogo
var mu sync.Mutex            // mutual exclusion
mu.Lock(); count++; mu.Unlock()

var rw sync.RWMutex          // many readers OR one writer
rw.RLock(); _ = data; rw.RUnlock()   // concurrent reads allowed

var once sync.Once           // run exactly once (lazy init, singletons)
once.Do(func() { initExpensiveThing() })

// sync.Pool — recycle allocations to cut GC pressure in hot paths
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}
b := bufPool.Get().(*bytes.Buffer)
defer func() { b.Reset(); bufPool.Put(b) }()

// atomic — lock-free counters
var n atomic.Int64
n.Add(1); n.Load()
Convention · guard the lock with defer, scope it tight

Pattern: mu.Lock(); defer mu.Unlock() at the top of a critical section so the unlock can't be skipped on an early return or panic. But keep critical sections short — never do I/O or call out to unknown code while holding a lock, or you'll serialise your whole service behind one slow call.

context: cancellation, deadlines & request scope

Every Go web service is built around context.Context. It carries deadlines, cancellation signals, and request-scoped values across API boundaries and goroutines. The HTTP server gives you one per request; you thread it down to the database, the cache, the gRPC call.

context.gogo
// derive a context with a 5s deadline
ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
defer cancel()               // ALWAYS call cancel to release resources

// pass ctx as the FIRST argument, by convention
rows, err := db.QueryContext(ctx, "SELECT ...")

// inside a long operation, watch for cancellation
select {
case <-ctx.Done():
    return ctx.Err()         // context.Canceled or context.DeadlineExceeded
case result := <-work:
    return result
}

// request-scoped values (use sparingly — for request IDs, auth, not config)
ctx = context.WithValue(ctx, userKey{}, user)
u, _ := ctx.Value(userKey{}).(*User)
Why thread context everywhere?

When a client disconnects or a request times out, you want the cancellation to propagate — the DB query should stop, the downstream HTTP call should abort, goroutines should wind down. Context is the wire that carries "stop now" through every layer. A service that ignores context keeps doing expensive work for requests nobody is waiting for anymore — a classic cause of cascading overload.

Gotcha · context anti-patterns vet/linters flag
  • Don't store a Context in a struct field — pass it as the first argument.
  • Don't pass nil Context — use context.TODO() if you genuinely don't have one yet.
  • Don't use context.WithValue for optional function params — it's untyped and invisible. Reserve it for request-scoped cross-cutting data (trace IDs, auth principal).
  • Always defer cancel() — leaking a cancel func leaks a goroutine and a timer.

errgroup: the modern fan-out pattern

errgroup.gogo
import "golang.org/x/sync/errgroup"

// run N tasks concurrently, cancel all if any fails, collect first error
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(8)                       // bound concurrency (worker-pool-ish)
for _, id := range ids {
    g.Go(func() error {             // Go 1.22+: id captured safely
        return process(ctx, id)
    })
}
if err := g.Wait(); err != nil {    // waits for all; returns first error
    return err
}
Convention · prefer errgroup over raw WaitGroup for fallible work

Raw WaitGroup can't propagate errors or cancel siblings. errgroup.WithContext gives you both: the first error cancels the shared context, the rest see ctx.Done() and bail, and Wait() returns that error. SetLimit(n) turns it into a bounded worker pool in one line. This is the default pattern for "do these N things concurrently and fail fast."

Internals · the race detector is non-negotiable in CI

go test -race ./... instruments memory accesses to detect data races at runtime (two goroutines touching the same memory, one writing, with no synchronisation). It has ~5–10× CPU/memory overhead so it's not for production, but it catches bugs that are otherwise invisible until they corrupt data in prod at 3am. Run your full test suite with -race in CI. It only catches races on code paths your tests actually exercise — so coverage of concurrent paths matters.

14Errors, panic & recover

Errors are values. This one design choice shapes how every Go program is written. Master the wrapping/inspection idioms and your services become debuggable.

The error interface is tiny

errors.gogo
type error interface {        // the entire definition
    Error() string
}

// create errors
errors.New("not found")
fmt.Errorf("user %d: %w", id, err)   // %w WRAPS err, preserving the chain

// sentinel errors — comparable package-level values
var ErrNotFound = errors.New("not found")

// custom error types carry structured data
type ValidationError struct {
    Field string
    Msg   string
}
func (e *ValidationError) Error() string {
    return fmt.Sprintf("%s: %s", e.Field, e.Msg)
}
Why %w matters

%w (wrap) embeds the original error inside a new one, building a chain you can later unwrap and inspect — while %v just flattens it to text and loses the structure. Wrap with context at each layer ("querying user: scanning row: connection reset") so the final message reads like a stack trace of what you were doing, not just where it failed.

Inspecting wrapped errors

inspect.gogo
// errors.Is — does the chain contain this sentinel?
if errors.Is(err, sql.ErrNoRows) {
    return http.StatusNotFound
}

// errors.As — extract a specific error TYPE from the chain
var ve *ValidationError
if errors.As(err, &ve) {
    fmt.Println("bad field:", ve.Field)
}

// errors.Join — combine multiple errors (Go 1.20+)
err := errors.Join(err1, err2)   // Is/As see both
Gotcha · stop comparing errors with ==

if err == ErrNotFound breaks the moment someone wraps the error with %w upstream — the wrapped error isn't == the sentinel. Always use errors.Is(err, ErrNotFound), which walks the chain. Same for type checks: use errors.As, not a type assertion. Linters (errorlint) flag direct comparisons.

panic & recover — for the truly exceptional

panic.gogo
// panic unwinds the stack, running deferred funcs, then crashes the program
panic("unrecoverable: corrupt invariant")

// recover stops a panic — ONLY works inside a deferred function
func safeHandler(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                log.Printf("panic: %v\n%s", rec, debug.Stack())
                http.Error(w, "internal error", 500)
            }
        }()
        next.ServeHTTP(w, r)
    })
}
Convention · panic is not exceptions

Use panic only for programmer errors and truly impossible states (a corrupt invariant, a nil that "can't" be nil). Normal failures — bad input, missing record, network blip — are errors you return, not panics. The one legitimate recover in a typical service is a top-level middleware that turns an unexpected panic in one handler into a 500 instead of crashing the whole process. A panicking goroutine that nobody recovers takes down the entire program.

16net/http — a production server in the stdlib

No framework required. Go's net/http is a fully capable, production-grade HTTP server and client. Frameworks add ergonomics, not capability.

The smallest real server

main.gogo
func main() {
    mux := http.NewServeMux()                 // a request router (multiplexer)
    mux.HandleFunc("GET /health", health)     // 1.22: method + path patterns

    srv := &http.Server{
        Addr:              ":8080",
        Handler:           mux,
        ReadHeaderTimeout: 5 * time.Second,    // mitigate Slowloris attacks
        ReadTimeout:       10 * time.Second,
        WriteTimeout:      15 * time.Second,
        IdleTimeout:       60 * time.Second,
    }
    log.Fatal(srv.ListenAndServe())
}

func health(w http.ResponseWriter, r *http.Request) {
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("ok"))
}
TypeRole
http.HandlerThe core interface: one method, ServeHTTP(w, r). Everything routable is a Handler.
http.HandlerFuncAn adapter so a plain func(w, r) satisfies Handler. This is the "func as interface" trick from §9.
http.ResponseWriterWhere you write the response: set headers, status, body. Not safe for concurrent use within one request.
*http.RequestThe incoming request: method, URL, headers, body, and crucially r.Context().
http.ServeMuxThe stdlib router. Greatly upgraded in 1.22 (methods + path wildcards).
Gotcha · always set server timeouts

http.ListenAndServe(":8080", mux) (the one-liner) has no timeouts — a slow or malicious client can hold a connection open forever and exhaust your server. Always build an explicit http.Server with ReadHeaderTimeout at minimum. This is the single most common production omission in Go services.

Why a "ResponseWriter" interface and not return a response?

Streaming. Because you write to w rather than returning a response object, you can stream gigabytes, flush partial responses (SSE, chunked), and hijack the connection (WebSockets) — all without buffering the whole body in memory. The trade-off: once you call w.WriteHeader or write a body, the status is locked in; you can't change it later. Order matters: set headers → WriteHeader(status) → write body.

Graceful shutdown

shutdown.gogo
// listen in a goroutine so main can wait for a signal
go func() {
    if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
        log.Fatal(err)
    }
}()

// block until SIGINT/SIGTERM (k8s sends SIGTERM on pod stop)
stop := make(chan os.Signal, 1)
signal.Notify(stop, syscall.SIGINT, syscall.SIGTERM)

Convention · graceful shutdown is mandatory in k8s

When Kubernetes rolls a deployment it sends SIGTERM and waits terminationGracePeriodSeconds before SIGKILL. Without srv.Shutdown, in-flight requests get cut off mid-response. Drain time should be less than the grace period. Pair this with a readiness probe that starts failing on shutdown so the load balancer stops sending new traffic first.

json:"-"Skip this field entirely (great for passwords, internal flags).
json:",omitempty"Omit the key when the value is the zero value.
json:"id,string"Encode a number as a JSON string (for JS bigint safety).
Gotcha · unexported fields are invisible to JSON

encoding/json uses reflection and can only see exported (capitalised) fields. A lowercase field is silently skipped in both directions — no error, just missing data. If your JSON output is missing a field, check its capitalisation first. Also: decoding into a field that's missing from the JSON leaves it at its zero value, so you can't distinguish "absent" from "explicitly zero" without a pointer or *T/sql.Null* type.

Middleware: http.Handler wrapping http.Handler

middleware.gogo
// middleware is a function: Handler in, Handler out
func Logging(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        // wrap w to capture the status code
        rec := &statusRecorder{ResponseWriter: w, status: 200}
        next.ServeHTTP(rec, r)              // call the next handler in the chain
        slog.Info("http",
            "method", r.Method, "path", r.URL.Path,
            "status", rec.status, "dur", time.Since(start))
    })
}

type statusRecorder struct {
    http.ResponseWriter
    status int
}
func (r *statusRecorder) WriteHeader(c int) {
    r.status = c
    r.ResponseWriter.WriteHeader(c)
}

// compose: outermost wraps innermost
handler := Logging(Auth(mux))
Internals · why wrapping ResponseWriter is fiddly

To log the status code you must intercept WriteHeader, because the status isn't stored anywhere readable after the fact. The embedding trick (statusRecorder embeds http.ResponseWriter) forwards every method except the one you override. But beware: if the underlying writer implements http.Flusher or http.Hijacker, your wrapper hides those interfaces unless you forward them too — which breaks SSE/WebSockets. Production wrappers (chi's middleware.WrapResponseWriter) handle this for you; reach for those rather than hand-rolling.

Why methods on a Server struct?

Handlers need access to the database, cache, logger, config. This "handler-as-method + explicit deps" pattern is the backbone of idiomatic Go web services — no DI framework needed.

JSON helpers (write these once, reuse everywhere)

respond.gogo
func writeJSON(w http.ResponseWriter, status int, v any) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    json.NewEncoder(w).Encode(v)
}

func writeError(w http.ResponseWriter, status int, msg string) {
    writeJSON(w, status, map[string]string{"error": msg})
}

func (s *Server) handleGetUser(w http.ResponseWriter, r *http.Request) {
    id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
    if err != nil {
        writeError(w, http.StatusBadRequest, "invalid id")
        return
    }

    // try cache first, fall through to db (cache-aside, §21)
    user, err := s.getUserCached(r.Context(), id)
    if errors.Is(err, sql.ErrNoRows) {
        writeError(w, http.StatusNotFound, "user not found")
        return
    }
    if err != nil {
        s.logger.Error("get user", "id", id, "err", err)
        writeError(w, http.StatusInternalServerError, "internal error")
        return
    }
    writeJSON(w, http.StatusOK, user)
}
Convention · map errors to status codes in one place

Notice how sql.ErrNoRows becomes 404 and everything else becomes 500 — and the real error is logged server-side but never leaked to the client (no DB error strings in responses; they reveal schema and aid attackers). For larger APIs, centralise this mapping in a single error-rendering helper so every handler responds consistently and you never accidentally echo an internal error to the wire.

Gotcha · check the Encode error in real handlers

json.NewEncoder(w).Encode(v) can fail (e.g. client disconnected mid-write). For brevity it's ignored above, but in production wrap it and log — a silently dropped encode error hides client-disconnect storms and broken-pipe issues.

The standard library: database/sql

database/sql is a thin, driver-agnostic abstraction over SQL databases. It manages a connection pool for you; you bring a driver (Postgres, MySQL, SQLite).

sql.gogo
import (
    "database/sql"
    _ "github.com/jackc/pgx/v5/stdlib"   // blank import registers the driver

Gotcha · the blank import and sql.Open lies

The _ "driver" import looks unused but runs the driver's init() which registers it — remove it and sql.Open("pgx", …) fails at runtime with "unknown driver." And sql.Open doesn't connect; it just validates arguments and returns a pool handle. Always follow it with db.PingContext to fail fast on a bad DSN at startup rather than on the first query.

Gotcha · you MUST close rows or leak connections

Every Query that returns *sql.Rows holds a connection until you rows.Close() and fully drain it. Forgetting defer rows.Close() leaks pool connections until the pool is exhausted and every request hangs. Also always check rows.Err() after the loop — iteration can stop early on a network error that rows.Next() swallows.

Querying by hand (what generators automate)

tx.gogo
tx, err := db.BeginTx(ctx, nil)
if err != nil { return err }

if _, err := tx.ExecContext(ctx, `UPDATE accounts SET bal = bal - $1 WHERE id=$2`, amt, from); err != nil {
    return err                      // defer rollback fires
}
if _, err := tx.ExecContext(ctx, `UPDATE accounts SET bal = bal + $1 WHERE id=$2`, amt, to); err != nil {

Convention · defer Rollback, return Commit

defer tx.Rollback() immediately after BeginTx guarantees the transaction is cleaned up on any early return or panic. After a successful Commit, the rollback is a harmless no-op. This pairing means you never leak an open transaction — which otherwise holds locks and pool connections until it times out.

Redis is the default cache, rate-limiter, and ephemeral store for Go services. The canonical client is redis/go-redis.

redis.gogo
import "github.com/redis/go-redis/v9"

rdb := redis.NewClient(&redis.Options{

Gotcha · redis.Nil is not an error condition

A cache miss returns the sentinel redis.Nil as the error. That's the normal "key absent" signal — check errors.Is(err, redis.Nil) and treat it as a miss, not a failure. Logging it as an error will flood your logs with noise on every cache miss.

Cache-aside: the workhorse pattern

cache_aside.gogo
func (s *Server) getUserCached(ctx context.Context, id int64) (User, error) {
    key := fmt.Sprintf("user:%d", id)

    // 1. try cache
    if data, err := s.cache.Get(ctx, key).Bytes(); err == nil {
        var u User
        if json.Unmarshal(data, &u) == nil {
            return u, nil                        // HIT
        }
    }

    // 2. miss → read source of truth
    u, err := s.store.GetUser(ctx, id)
    if err != nil {
        return User{}, err                       // includes sql.ErrNoRows
    }

    // 3. populate cache (best-effort; a cache write failure shouldn't fail the request)
    if data, err := json.Marshal(u); err == nil {
        s.cache.Set(ctx, key, data, 5*time.Minute)
    }
    return u, nil
}

// invalidate on write
func (s *Server) updateUser(ctx context.Context, u User) error {
    if err := s.store.UpdateUser(ctx, u); err != nil { return err }
    s.cache.Del(ctx, fmt.Sprintf("user:%d", u.ID))   // bust the cache
    return nil
}
Why cache-aside and not write-through?

Cache-aside (lazy loading) keeps the cache and DB decoupled: the cache only holds what's actually been read, a cache outage degrades to "slower" not "broken," and invalidation is a simple delete. The cost is the first read after a write/expiry is a miss. For most read-heavy services this is the right default — and it's exactly the pattern behind sub-100ms p95s when paired with a fast source of truth.

Internals · the three cache stampede problems
  • Thundering herd / stampede: a hot key expires and 10k requests all miss and hit the DB simultaneously. Fix: singleflight (golang.org/x/sync/singleflight) collapses concurrent identical loads into one DB call; the rest wait and share the result.
  • Cache penetration: requests for keys that don't exist bypass the cache every time. Fix: cache the negative result (a "not found" marker) with a short TTL.
  • Cache avalanche: many keys expire at the same instant. Fix: add jitter to TTLs (5*time.Minute + rand jitter).
Convention · Redis as rate limiter & lock

Beyond caching, Redis powers distributed rate limiting (INCR + EXPIRE, or the token-bucket via redis_rate) and distributed locks (SET key val NX PX ttl, or Redlock for stricter needs). Keep lock TTLs short and always set them — a lock without a TTL is a deadlock waiting for a crashed holder.

22Protocol Buffers — the complete proto3 syntax

Protobuf is a language-neutral, binary serialization format plus an IDL (interface definition language). You write .proto files describing your data and services once, then generate type-safe code for Go, TypeScript, Python, and a dozen other languages. It's the wire format behind gRPC. This section is the full reference — every keyword, every rule.

Anatomy of a .proto file

user/v1/user.protoprotobuf
// Every proto3 file starts by declaring the syntax. Without this line,
// protoc assumes proto2 — a different, older dialect.
syntax = "proto3";

// The logical namespace for this file's symbols. Prevents name clashes
// when many protos are compiled together. Convention: company.product.version
package user.v1;

// Language-specific code-gen options. go_package tells protoc-gen-go the
// import path AND the package name (after the semicolon) for generated Go.
option go_package = "github.com/acme/api/gen/user/v1;userv1";

// Pull in definitions from other proto files. Paths are relative to the
// import roots passed to protoc (-I / buf's roots).
import "google/protobuf/timestamp.proto";
import "google/protobuf/field_mask.proto";

// A message is a structured record — the core building block.
message User {
  // Each field has: type, name, and a UNIQUE field number.
  // Field numbers (not names) are what's encoded on the wire.
  uint64 id        = 1;
  string email     = 2;
  string full_name = 3;
  bool   is_active = 4;

  // Enums are fully-qualified within the message when nested.
  Role role = 5;

  // A nested enum. Proto3 enums MUST have a zero value (the default).
  enum Role {
    ROLE_UNSPECIFIED = 0;   // always define 0 = UNSPECIFIED
    ROLE_MEMBER      = 1;
    ROLE_ADMIN       = 2;
  }

  // Well-known type for timestamps — maps to time.Time in Go.
  google.protobuf.Timestamp created_at = 6;

  repeated string tags = 7;            // a list/slice of strings
  map<string, string> metadata = 8;    // a hash map
}
Why field numbers, not names?

The binary wire format encodes each field as a (field_number, wire_type) tag followed by the value — the field name never travels. That's why renaming a field is a safe, backward-compatible change, but changing or reusing a field number breaks every old client. Field numbers are the contract.

Internals · the wire format (varint & ZigZag)
  • Varint: integers are encoded 7 bits per byte, with the high bit signaling "more bytes follow." Small numbers take 1 byte; that's why you assign field numbers 1–15 to your hottest fields — their tag fits in a single byte (numbers 16–2047 take two).
  • ZigZag (sint): maps signed ints to unsigned so small magnitudes stay small: 0→0, -1→1, 1→2, -2→3. Without it, -1 as an int64 varint is the maximum 10 bytes.
  • Wire types: 0=varint, 1=64-bit, 2=length-delimited (strings, bytes, embedded messages, packed repeated), 5=32-bit. The tag byte is (field_number << 3) | wire_type.

Field numbers — the rules that bite you

Gotcha · reserved ranges & the 19000–19999 hole
  • Valid range is 1 to 536,870,911 (2²⁹−1).
  • 19000–19999 are reserved by the protobuf implementation — you can't use them.
  • When you delete a field, reserve its number and name so nobody reuses them and silently misreads old data.
reserved.protoprotobuf
message Account {
  reserved 2, 5, 9 to 11;            // numbers no one may reuse
  reserved "old_field", "legacy_id"; // names no one may reuse
  uint64 id = 1;
  string name = 3;
}

repeated, map, oneof & optional

composite.protoprotobuf
message Order {
  // repeated → a slice. Scalar numeric repeateds are "packed" by default
  // in proto3 (encoded contiguously, no per-element tag) → compact.
  repeated string item_ids = 1;
  repeated LineItem line_items = 2;   // repeated message

  // map<K,V> → Go map. K must be an integral or string type; V can be
  // anything except another map. Order is NOT preserved on the wire.
  map<string, int32> quantities = 3;

  // oneof → at most ONE of these fields is set at a time (a tagged union).
  // Setting one clears the others. Great for "A or B" payloads.
  oneof payment {
    CardPayment card   = 4;
    BankPayment bank   = 5;
    string      coupon = 6;
  }

  // proto3 'optional' re-introduces field presence: you can tell apart
  // "set to zero/empty" from "never set" (generates a *type pointer / Has()).
  optional string note = 7;
}
Why optional matters in proto3

By default proto3 scalar fields have no presence: a field set to 0, "", or false is indistinguishable from "unset" — both simply aren't serialized. That breaks PATCH semantics ("did the client mean to clear this, or omit it?"). Marking a field optional brings back explicit presence: in Go you get a pointer (*string) and a nil means truly unset. Use it whenever the difference between "zero" and "absent" is meaningful.

Internals · how each maps to Go
  • oneof payment → a Go interface field Payment isOrder_Payment with wrapper structs Order_Card, Order_Bank, Order_Coupon; you type-switch on it.
  • optional string note → *string plus generated GetNote() returning the deref or zero value.
  • map<string,int32> → map[string]int32.
  • repeated LineItem → []*LineItem (messages are always pointers).

Enums, nested types & reserved enum values

enums.protoprotobuf
enum Status {
  // proto3 requires the first enum value to be 0 — it's the default.
  STATUS_UNSPECIFIED = 0;
  STATUS_PENDING     = 1;
  STATUS_SHIPPED     = 2;
  STATUS_DELIVERED   = 3;

  // Two names sharing a number requires allow_alias.
  option allow_alias = true;
  STATUS_DONE        = 3;   // alias of DELIVERED

  reserved 4, 5;            // reserve numbers
  reserved "STATUS_OLD";    // and names
}
Convention · enum naming

Prefix every value with the enum name (STATUS_) because proto enum values live in the enclosing scope, not the enum's — two enums in one file with a bare PENDING would collide. And always make 0 the _UNSPECIFIED sentinel so an unset enum is detectably "not chosen" rather than accidentally meaning your first real state.

Services & the four RPC kinds

service.protoprotobuf
service UserService {

  rpc ImportUsers(stream User) returns (ImportSummary);

  rpc Chat(stream ChatMessage) returns (stream ChatMessage);
}

Internals · proto3 ↔ JSON & the proto2 differences
  • Canonical JSON: protobuf has a defined JSON mapping (field names become lowerCamelCase unless you set json_name). This is how gRPC-Gateway and Connect expose JSON.
  • vs proto2: proto3 dropped required (everything is optional), dropped custom field defaults, and made every field have an implicit zero default. required was removed because it makes schema evolution dangerous — you can never safely remove a required field.

Convention · file & package layout

Put protos under a versioned path: proto/user/v1/user.proto with package user.v1. Version in the package (v1, v2) so breaking changes become a new package rather than a silent break. One top-level message/service concern per file. This is exactly the layout buf expects.

Implementing the server

Codegen produces a UserServiceServer interface and an UnimplementedUserServiceServer you embed for forward-compatibility. You implement only the methods you need.

server.gogo
type userServer struct {
    userv1.UnimplementedUserServiceServer   // embed → future-proof
    store *Store
}

// Unary handler: signature is dictated by the generated interface.
func (s *userServer) GetUser(ctx context.Context, req *userv1.GetUserRequest) (*userv1.User, error) {
    u, err := s.store.User(ctx, req.GetId())
    if errors.Is(err, ErrNotFound) {
        // Return a gRPC status code, NOT a bare error.
        return nil, status.Errorf(codes.NotFound, "user %d not found", req.GetId())
    }
    if err != nil {
        return nil, status.Error(codes.Internal, "lookup failed")
    }
    return &userv1.User{Id: u.ID, Email: u.Email, FullName: u.Name}, nil
}

// Server-streaming handler: push messages via stream.Send.
func (s *userServer) ListUsers(req *userv1.ListUsersRequest, stream userv1.UserService_ListUsersServer) error {
    for _, u := range s.store.All(stream.Context()) {
        if err := stream.Send(&userv1.User{Id: u.ID, Email: u.Email}); err != nil {
            return err   // client went away
        }
    }
    return nil
}

Why embed UnimplementedUserServiceServer?

When you add a new RPC to the .proto and regenerate, your server struct suddenly doesn't satisfy the bigger interface — a compile error. By embedding the generated Unimplemented… stub (which returns codes.Unimplemented for everything), new methods get a safe default and your code keeps compiling. It turns "forgot to implement" from a build break into a clean runtime Unimplemented status you can roll out gradually.

24Integrating a React frontend

There are two common topologies for a Go + React app: serve them separately (React on a CDN/Vite dev server, Go as a pure JSON API) or embed the built SPA into the Go binary and ship one artifact. We'll cover both, plus the CORS and type-sharing details that trip people up.

Topology A — separate origins (dev) with CORS

During development Vite runs on :5173 and your API on :8080. Different origin → the browser enforces CORS. Handle it explicitly:

cors.gogo
func cors(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("Access-Control-Allow-Origin", "http://localhost:5173")
        w.Header().Set("Access-Control-Allow-Methods", "GET,POST,PUT,DELETE,OPTIONS")
        w.Header().Set("Access-Control-Allow-Headers", "Content-Type,Authorization")
        w.Header().Set("Access-Control-Allow-Credentials", "true")
        // Preflight: the browser sends OPTIONS first for non-simple requests.
        if r.Method == http.MethodOptions {
            w.WriteHeader(http.StatusNoContent)
            return
        }
        next.ServeHTTP(w, r)
    })
}
Why the preflight OPTIONS?

For any "non-simple" request (custom headers like Authorization, or methods like PUT/DELETE), the browser first sends an OPTIONS "preflight" asking the server what's allowed. If you don't answer it with the right Allow-* headers and a 2xx, the real request never fires and you get the classic "blocked by CORS policy" console error. In production prefer the github.com/rs/cors package over hand-rolling — it handles edge cases (Vary headers, wildcards) correctly.

Topology B — embed the SPA in the Go binary

For production simplicity, build the React app and bake the static files into the binary with embed.FS. One binary, one deploy, no separate web server for assets.

embed.gogo
import (
    "embed"
    "io/fs"
    "net/http"
)

//go:embed all:dist
var dist embed.FS   // the //go:embed directive bakes ./dist into the binary

func spaHandler() http.Handler {
    sub, _ := fs.Sub(dist, "dist")        // treat dist/ as the FS root
    fileServer := http.FileServer(http.FS(sub))
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // Serve the asset if it exists; otherwise fall back to index.html
        // so client-side routes (e.g. /users/42) work on hard refresh.
        if _, err := fs.Stat(sub, strings.TrimPrefix(r.URL.Path, "/")); err != nil {
            r.URL.Path = "/"
        }
        fileServer.ServeHTTP(w, r)
    })
}

func main() {
    mux := http.NewServeMux()
    mux.Handle("/api/", apiRouter())   // JSON API
    mux.Handle("/", spaHandler())      // everything else → the SPA
    http.ListenAndServe(":8080", mux)
}
Internals · what //go:embed actually does

//go:embed is a compiler directive (note: no space after // — it must be a contiguous comment touching the var). At build time the toolchain reads the named files and stores their bytes in the binary's read-only data segment, exposed as an embed.FS implementing fs.FS. The all: prefix includes files that start with _ or . (which Vite emits). Zero runtime I/O, no missing-file-in-prod surprises.

25Docker — tiny, secure multi-stage images

Go's superpower for ops: it compiles to a single static binary. That means your production image can be almost nothing — no interpreter, no OS packages, just your binary. A naive image is ~900MB; a good one is ~10MB.

Dockerfiledockerfile
# ---------- Stage 1: build ----------
FROM golang:1.23 AS build
WORKDIR /src

# Copy go.mod/go.sum FIRST and download deps. This layer is cached as long
# as your dependencies don't change → fast rebuilds when only code changes.
COPY go.mod go.sum ./
RUN go mod download

COPY . .
# CGO_ENABLED=0 → a fully static binary with no libc dependency, so it runs
# in 'scratch'. -ldflags "-s -w" strips debug info → smaller binary.
RUN CGO_ENABLED=0 GOOS=linux go build -ldflags="-s -w" -o /app ./cmd/server

# ---------- Stage 2: runtime ----------
# 'scratch' is the empty image — literally nothing. Or use distroless for
# CA certs + tzdata + a non-root user already set up.
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /app /app
USER nonroot:nonroot       # never run as root
EXPOSE 8080
ENTRYPOINT ["/app"]
Why multi-stage + distroless?

The golang:1.23 image (~800MB) has the whole compiler toolchain — you need it to build but not to run. Multi-stage lets you build in the fat image and copy only the binary into a near-empty final image. distroless/static adds just what a static Go binary actually needs at runtime: CA certificates (for outbound TLS), timezone data, and /etc/passwd with a non-root user. Smaller image = faster pulls, smaller attack surface, fewer CVEs to patch.

Gotcha · scratch & the three things it's missing
  • CA certs: outbound HTTPS fails with x509 errors. Fix: COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/, or use distroless.
  • tzdata: time.LoadLocation fails. Embed via the time/tzdata import or copy the zoneinfo.
  • CGO: if you forget CGO_ENABLED=0, the binary dynamically links libc and crashes in scratch with "no such file or directory" (a confusing error — the file is the missing loader).

26nginx as a reverse proxy & TLS terminator

A Go server can serve HTTP directly, but in front of it you usually want a reverse proxy for TLS termination, compression, static caching, and load-balancing across replicas. nginx is the workhorse.

/etc/nginx/conf.d/app.confnginx
# Define a pool of backend instances → nginx load-balances across them.
upstream go_app {
    least_conn;                 # send to the backend with fewest active conns
    server 127.0.0.1:8080;
    server 127.0.0.1:8081;
    keepalive 32;               # reuse upstream connections (perf)
}

server {
    listen 443 ssl http2;       # HTTP/2 on, TLS terminated here
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    gzip on;
    gzip_types application/json text/plain application/javascript text/css;

    location /api/ {
        proxy_pass http://go_app;
        proxy_http_version 1.1;             # required for keepalive to upstream
        # Pass the REAL client info — without this your Go app sees nginx's IP.
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    # WebSocket / SSE upgrade support (needed for streaming endpoints).
    location /ws/ {
        proxy_pass http://go_app;
        proxy_http_version 1.1;
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}

# Redirect plain HTTP → HTTPS.
server {
    listen 80;
    server_name api.example.com;
    return 301 https://$host$request_uri;
}
Why X-Forwarded-For matters in Go

Once nginx fronts your app, r.RemoteAddr is always nginx's address — useless for rate-limiting or audit logs. nginx injects the real client IP into X-Forwarded-For; your Go middleware must read it (validating that the immediate peer is your trusted proxy, so clients can't spoof the header). The stdlib doesn't trust these headers automatically by design — you opt in deliberately. Many use the realip middleware from chi for this.

Convention · what terminates TLS

Common setups: nginx (shown), Caddy (automatic Let's Encrypt, simplest config), or a cloud load balancer (ALB/GCLB) that terminates TLS and forwards plain HTTP inside the VPC. In Kubernetes this job usually moves to an Ingress controller (ingress-nginx) or the newer Gateway API — same idea, declarative. Pick one place to own certs and HTTP/2.

Why three different probes?

They answer different questions and have different consequences. Readiness = "route traffic to me?" — failing it pulls you out of the load balancer without a restart, perfect for "my DB connection is down, hold traffic." Liveness = "am I wedged?" — failing it restarts the container, for unrecoverable deadlocks. Mixing them up is a classic outage: if your liveness probe checks the database and the DB blips, K8s restart-loops every replica simultaneously and turns a brief dependency hiccup into a full outage. Keep liveness dumb (process responds at all); put dependency checks in readiness.

health.gogo
// Liveness: trivially returns 200 if the process can serve HTTP at all.

    w.WriteHeader(http.StatusOK)
})

// Readiness: checks real dependencies. Returns 503 when not ready.

    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)

    if err := db.PingContext(ctx); err != nil {
        http.Error(w, "db down", http.StatusServiceUnavailable)

Gotcha · graceful shutdown & SIGTERM

On a rolling update, K8s sends SIGTERM, waits terminationGracePeriodSeconds (default 30), then SIGKILLs. If your Go server ignores SIGTERM it gets killed mid-request → 502s for users. Catch it and call srv.Shutdown(ctx) to drain in-flight requests. Also: K8s removes the pod from endpoints and sends SIGTERM concurrently, so sleep briefly (or fail readiness first) before shutting down to avoid a race where traffic still arrives.

Convention · set GOMAXPROCS to your CPU limit

Go defaults GOMAXPROCS to the node's core count, not your pod's CPU limit. On a 64-core node with a 500m limit, Go spins up 64 scheduler threads and gets throttled hard. Averages lie. A 50ms average latency can hide a p99 of 3 seconds that's wrecking a fraction of users. The classics that bite everyone

Gotcha · the pre-1.22 loop variable (know the history)

Before Go 1.22, the loop variable was shared across all iterations, so for _, v := range xs { go func(){ use(v) }() } captured the same v — every goroutine saw the last value. Go 1.22 made the loop variable per-iteration, fixing it. You'll still see the old v := v shadow trick in pre-1.22 code; know why it existed. (Reviewers love asking this.)

Gotcha · defer in a loop

defer runs at function return, not loop-iteration end. for ... { f, _ := os.Open(x); defer f.Close() } holds every file open until the function exits → fd exhaustion. Move the work into a helper function, or close explicitly inside the loop.

Gotcha · time.After in a hot select

time.After allocates a new timer each call and doesn't get GC'd until it fires. In a tight select loop that's a slow leak. Use a single time.NewTimer you Reset, or context.WithTimeout.

Gotcha · forgetting resp.Body.Close()

Every http.Get/Do response body must be closed or you leak connections (the pool can't reuse them) and eventually file descriptors. defer resp.Body.Close() — and read the body to EOF (or io.Copy(io.Discard, body)) so the connection can be reused, not dropped.

  • Context everywhere: every blocking call (DB, HTTP, gRPC) takes a ctx with a deadline, propagated from the request.
  • Graceful shutdown: SIGTERM → srv.Shutdown, drain in-flight, close pools.
  • Timeouts on the server: set ReadHeaderTimeout (and ideally Read/Write/Idle) — the zero-value http.Server has none and is Slowloris-vulnerable.
  • Resource limits: connection pool caps (SetMaxOpenConns), GOMAXPROCS + GOMEMLIMIT matched to container limits.
  • Observability: structured logs, /metrics, traces, /healthz + /readyz.
  • Tested with -race and real dependencies (testcontainers).
  • Static, non-root container with pinned base images and a .dockerignore.

The Go ethos is consistency over cleverness: a small language, a great standard library, and tools (go vet, -race, pprof, gofmt) that make the right thing the easy thing. Build something, run it under load, read the profiles, and the rest becomes muscle memory.
