01

Orientation

Two technologies that ship together but are not the same thing. Get this separation right and the rest is mechanical.

Protocol Buffers (protobuf) is two things in one: a schema language (an IDL) for describing structured data, and a compact binary serialization format for that data. gRPC is a remote-procedure-call framework that runs over HTTP/2 and uses protobuf as its default payload format and its service-definition language. You can use protobuf without gRPC (config files, Kafka payloads, on-disk records). You rarely use gRPC without protobuf.

◆ mental model

REST: you act on resources at URLs with verbs (GET /users/42), payloads are self-describing text. gRPC: you call methods on a service (GetUser(GetUserRequest)), payloads are opaque binary whose meaning lives entirely in a shared .proto contract. The contract is compiled into typed client and server stubs in each language. You program against generated function signatures, not HTTP.

Why it exists / what it buys you

  • Contract-first. The .proto file is the single source of truth. Clients and servers in different languages generate code from the same file, so the interface cannot drift.
  • Binary & small. No field names on the wire, integers are varint-packed. Typically 3–10× smaller than equivalent JSON, and far cheaper to parse (no string scanning).
  • HTTP/2 transport. One TCP connection multiplexes many concurrent calls, supports flow control, header compression, and full-duplex streaming.
  • Streaming is native. Server-, client-, and bidirectional-streaming are first-class, not bolted on with SSE or WebSockets.
  • Schema evolution. Field numbers (not names) identify data, so you can add and remove fields without breaking old peers — if you follow the rules in §04.

When not to reach for it

  • Browser-to-server directly. Browsers cannot speak raw gRPC frames. You need grpc-web + a proxy (Envoy) or a framework like Connect. Native gRPC shines server-to-server.
  • Public, human-debuggable APIs. JSON/REST wins when third parties poke at it with curl and read it by eye. Binary is opaque without the schema.
  • Trivial CRUD with no polyglot or perf pressure. The codegen toolchain is overhead you may not need.

02

Protobuf: the schema

A .proto file is a typed contract. Here is one with every line annotated.

📄 user.protoprotobuf
syntax = "proto3";

package acme.user.v1;

import "google/protobuf/timestamp.proto";

option go_package = "github.com/acme/gen/user/v1;userv1";

// A registered user of the system.
message User {
  string id        = 1;
  string email     = 2;
  string full_name = 3;
  Role   role      = 4;
  repeated string tags = 5;
  google.protobuf.Timestamp created_at = 6;
  optional string nickname = 7;
}

enum Role {
  ROLE_UNSPECIFIED = 0;
  ROLE_MEMBER      = 1;
  ROLE_ADMIN       = 2;
}
line by line — what each token does
syntax = "proto3";Declares the dialect. Must be the first non-comment line. proto3 is the modern default; proto2 still exists; editions (below) is the future. Without it the compiler assumes proto2.
package acme.user.v1;Logical namespace. Prevents name collisions across files and maps to a package/module prefix in generated code. Convention: reverse-domain-ish, version-suffixed (.v1) so v1 and v2 can coexist.
import "...timestamp.proto";Pulls in another .proto so you can reference its types. Here, a Google "well-known type". Imports are resolved against the compiler's include paths, not the filesystem directly.
option go_package = ...;A file-level option: per-language codegen knobs that do not change the wire format. go_package sets the Go import path; the part after ; is the package name. Other languages have their own (java_package, etc).
message User { }Defines a composite type — a struct. Compiles to a class/struct with typed accessors in every target language.
string id = 1;A field: type string, name id, field number 1. The number — not the name — is what goes on the wire. §03 is entirely about this.
repeated string tags = 5;repeated = a list/array of zero or more values. Order is preserved.
optional string nickname = 7;optional re-enables explicit field presence (can distinguish "" from unset). See the presence gotcha in §03.
enum Role { }A closed set of named integer constants. The = 0 member is mandatory and is the default. Convention: prefix members with the enum name and reserve 0 for _UNSPECIFIED.

◆ why sint over int for signed values

Plain int32/int64 store negative numbers as their two's-complement, which a varint sees as a huge unsigned number — so -1 costs the full 10 bytes. sint32/sint64 apply ZigZag first (§04), mapping small-magnitude negatives to small varints. Rule: if a field is frequently negative, reach for sint*.

◆ editions — where this is heading

Protobuf editions (e.g. edition = "2023";) replace the proto2/proto3 split with per-feature features you opt into individually (field presence, enum openness, packed encoding), set with option features.* = .... The wire format is unchanged. As of 2026 proto3 is still the default most teams write; editions is what new Google-internal and buf-managed schemas migrate toward. Learn proto3 first — editions is a superset of the same ideas.

03

Fields, tags & rules

Field numbers are the load-bearing wall of the whole system. Everything about compatibility flows from them.

Field numbers (tags)

Every field carries an integer field number (often called its tag). It is the identity of the field on the wire — the name is compile-time only and never transmitted. This is why you can rename a field freely but must never reuse or change a number.

  • Range: 1 to 536,870,911 (2²⁹−1).
  • 19000–19999 are reserved by the implementation — you cannot use them.
  • Numbers 1–15 encode their tag in a single byte; 16–2047 take two bytes. Spend the low numbers on your hottest, most-frequent fields.
▲ gotcha — the cardinal rule

Once a field number is in production, it is forever bound to that field's type and meaning. Changing the type, or reusing the number for a different field after deleting the old one, silently corrupts data for any peer still on the old schema. To retire a field, delete the field and reserved its number (below) so no one reuses it by accident.

Field presence — the proto3 trap

In proto3, a singular scalar field has no presence tracking by default: if you set count = 0 it is indistinguishable from never setting it, and zero values are not serialized at all. Add the optional keyword to get explicit presence back (a has_count() accessor).

presence.protoprotobuf
message Settings {
  int32 retries = 1;            // no presence: 0 == "unset". Not sent on wire if 0.
  optional int32 timeout = 2;   // presence: can tell "set to 0" from "absent".
}
◆ why this matters

Partial updates (PATCH-style) and "use server default if absent" semantics break without presence. If a client genuinely needs to send 0 / false / "" as a deliberate value distinct from "I didn't set this", mark the field optional. Message-typed fields always have presence; scalars are the trap.

Aggregates: repeated, map, oneof

aggregates.protoprotobuf
message Order {
  repeated string item_ids = 1;          // list, order preserved

  map<string, int32> quantities = 2;     // key -> value. keys: integral or string only

  oneof payment {                        // at most ONE of these is set at a time
    CreditCard card   = 3;
    BankTransfer bank = 4;
  }
}
what each construct does
repeatedZero-or-more values. Numeric/enum/bool repeated fields are packed by default in proto3 (all values in one length-delimited block — fewer tag bytes).
map<K,V>Associative array. Sugar for repeated of a hidden key/value message — so map order is undefined and duplicate keys keep the last. Keys must be integral or string; values can be anything except another map.
oneofA union: setting any member clears the others. Saves space and expresses "exactly one of" in the type system. You cannot make a oneof member repeated.

Enums — the zero-value rule

enum.protoprotobuf
enum Status {
  STATUS_UNSPECIFIED = 0;   // REQUIRED: first member must be 0
  STATUS_ACTIVE      = 1;
  STATUS_SUSPENDED   = 2;
}
▲ gotcha — always reserve 0 for UNSPECIFIED

Because proto3 scalars default to their zero value, an unset enum field reads as the 0 member. If 0 means ACTIVE, every message that forgot to set the field silently becomes "active". Make 0 a neutral _UNSPECIFIED sentinel. Proto3 enums are also open: an unknown number deserializes intact and round-trips, so you can add members without breaking old readers.

reserved — tombstoning removed fields

reserved.protoprotobuf
message User {
  reserved 4, 7, 10 to 15;          // these numbers can never be reused
  reserved "legacy_token", "ssn";   // these names can never be reused
  string id = 1;
}
◆ why reserve names too

Reserving the number stops wire-level corruption. Reserving the name stops a future developer re-introducing a field with the old name (and a new number) that revives a deprecated concept and confuses readers. Cheap insurance — do both whenever you delete a field.

Nested, imported & well-known types

Messages nest, import across files, and reuse Google's standard library of "well-known types" (WKTs) for things you should never hand-roll.

Well-known typeUse for
TimestampA point in time (UTC, nanosecond precision). Not a Unix int.
DurationA span of time (signed seconds + nanos).
FieldMaskA set of field paths — the standard way to express "update only these fields" in PATCH-style RPCs.
AnyA type-erased message packed with its type URL. Escape hatch; avoid unless you truly need dynamic typing.
Struct / Value / ListValueArbitrary JSON-like data when the shape is genuinely unknown.
EmptyA message with no fields, for RPCs that take or return nothing.
wrappers (Int32Value…)Legacy way to get presence on scalars before optional existed. Prefer optional in new code.

Naming conventions (the standard style)

  • Messages & enums: PascalCase — UserAccount, OrderStatus.
  • Fields: snake_case — full_name, created_at. Codegen converts to each language's idiom (fullName in Go/JS).
  • Enum members: SCREAMING_SNAKE_CASE, prefixed with the enum name, 0 = *_UNSPECIFIED.
  • Services: PascalCase ending in Service; RPCs are PascalCase verbs.
  • Packages: lowercase, dotted, version-suffixed — acme.user.v1.
04

The wire format

This is the section that separates "I use gRPC" from "I understand gRPC". A serialized message is just a flat sequence of key-value pairs.

Each field on the wire is a tag byte (or bytes) followed by a value. The tag packs the field number and a 3-bit wire type that tells the parser how to read the value that follows:

tag constructionformula
tag = (field_number << 3) | wire_type

# field 1, wire_type 2 (LEN):  (1 << 3) | 2 = 0x0A
# field 2, wire_type 0 (VARINT): (2 << 3) | 0 = 0x10
Wire typeIDUsed byHow the value is read
VARINT0int32/64, uint32/64, sint*, bool, enumRead varint bytes until high bit clears
I641fixed64, sfixed64, doubleExactly 8 bytes, little-endian
LEN2string, bytes, embedded messages, packed repeatedA varint length, then that many bytes
I325fixed32, sfixed32, floatExactly 4 bytes, little-endian
SGROUP/EGROUP3,4deprecated groupsDo not use

Varints — variable-length integers

A varint stores an integer in as few bytes as possible. Each byte uses its low 7 bits for data; the high bit (the continuation bit) is 1 if more bytes follow, 0 on the last. Bytes are little-endian (least-significant group first).

encoding 300 as a varintwalk-through
300 decimal           = 1 0010 1100  (binary)
split into 7-bit groups: 0000010  0101100
reverse to little-endian: 0101100  0000010
add continuation bits:  1 0101100   0 0000010
                        = 0xAC       0x02

So 300 on the wire = AC 02   (two bytes, not four)

ZigZag — making signed varints small

Varints are inefficient for negatives because two's-complement makes -1 look enormous. sint32/sint64 first apply ZigZag, which interleaves positive and negative numbers so small magnitudes stay small:

zigzagmapping
encode: (n << 1) ^ (n >> 31)     # 64-bit: >> 63

  0 -> 0      -1 -> 1      1 -> 2     -2 -> 3     2 -> 4
small negatives map to small varints, so -1 costs 1 byte, not 10.

Decoding a real message

Take message M { string name = 1; int32 age = 2; } holding name="Al", age=30:

bytes on the wirehex
0A 02 41 6C 10 1E

0A          tag: field 1, wire_type 2 (LEN)   ← (1<<3)|2
02          length: 2 bytes follow
41 6C       "Al"  (ASCII A=0x41, l=0x6C)
10          tag: field 2, wire_type 0 (VARINT) ← (2<<3)|0
1E          value: 30
◆ what the parser knows — and doesn't

The wire bytes carry numbers and wire types only. There is no "name", no "age", no type beyond the 3-bit wire type. The decoder needs the .proto to know field 1 is a string and field 2 is an int32. This is exactly why protobuf is compact — and why you cannot read a payload without its schema.

The payoff: schema-evolution rules

Because fields are keyed by number and unknown fields are skipped (and, by default, preserved on re-serialization), you can evolve schemas without coordinated deploys — within these rules:

ChangeSafe?Why
Add a new field (new number)✓ yesOld peers skip the unknown number; new peers read it
Rename a field✓ yesNames aren't on the wire
Delete a field✓ yes**Must reserved the number so it's never reused
Change field number✗ noIt's a different field now; data mismatches
Change a field's type✗ usuallyOnly a few wire-compatible swaps are safe (e.g. int32/int64/bool share VARINT but truncate)
Move a field in/out of a oneof✗ noChanges presence semantics
◆ let a tool enforce this

Don't police these by code review. buf breaking (§07) diffs your schema against a baseline (git ref or the Buf registry) and fails CI on any wire-incompatible change. This is the single highest-leverage thing you can add to a protobuf workflow.

05

The service definition

Where protobuf stops being just serialization and gRPC begins. A service declares callable methods; each method names a request type and a response type.

user_service.protoprotobuf
syntax = "proto3";
package acme.user.v1;
option go_package = "github.com/acme/gen/user/v1;userv1";

service UserService {
  rpc GetUser     (GetUserRequest)    returns (User);                 // unary
  rpc ListUsers   (ListUsersRequest)  returns (stream User);          // server-stream
  rpc ImportUsers (stream User)       returns (ImportSummary);        // client-stream
  rpc Chat        (stream ChatMessage) returns (stream ChatMessage);  // bidi
}

message GetUserRequest  { string id = 1; }
message ListUsersRequest { int32 page_size = 1; string page_token = 2; }
message ImportSummary    { int32 imported = 1; int32 skipped = 2; }
message ChatMessage      { string from = 1; string body = 2; }
message User             { string id = 1; string email = 2; }
anatomy of an rpc line
rpcKeyword introducing one callable method.
GetUserMethod name → becomes a function on the generated client stub and a handler you implement on the server.
(GetUserRequest)The single request message type. gRPC methods take exactly one message in and one out — bundle parameters into a request message.
returns (User)The single response message type.
streamPrefix on the request and/or response type. Its presence on each side is what selects the RPC kind (next section).
◆ why one-message-in, one-message-out

Wrapping every call's inputs in a dedicated ...Request message (rather than a bare scalar) is the convention even for single-argument calls. It lets you add fields later without changing the method signature — the same evolution story as §04, applied to APIs. Returning a dedicated ...Response/...Summary message (not a bare User) is similarly future-proof when you later need pagination tokens or metadata alongside the payload.

06

The four RPC types

Where stream appears decides everything about the call's shape. All four ride the same HTTP/2 connection.

KindSignature shapeUse for
Unary(Req) returns (Res)Ordinary request/response — most calls
Server streaming(Req) returns (stream Res)One request, many responses: feeds, large list pagination, progress
Client streaming(stream Req) returns (Res)Many requests, one response: uploads, batched ingest
Bidirectional(stream Req) returns (stream Res)Independent full-duplex: chat, live sync, multiplexed control
◆ what "bidirectional" actually means

Both streams are independent — the server is not forced to reply once per request. It can read three messages then send one, or send continuously while reading. Ordering is guaranteed within each direction, not across them. That independence is what makes bidi suitable for protocols, not just RPC.

▲ gotcha — streaming isn't free

A stream pins a long-lived HTTP/2 stream and server goroutine/thread/coroutine for its whole lifetime. Unbounded server-streams without flow-control awareness or client cancellation handling leak resources. Always honor the call's context/deadline and stop producing when the peer goes away (§11). For "just return a big list", prefer paginated unary over an open-ended server stream unless you genuinely need push.

07

Codegen: protoc & buf

A .proto does nothing until you compile it into a target language. The raw tool is protoc; the modern workflow is buf.

The raw way — protoc + plugins

protoc is the reference compiler. It parses .proto files and hands the parsed schema to plugins (protoc-gen-*), one per language/feature, which emit code. You assemble the toolchain by hand:

protoc invocation (Go)bash
# one plugin emits message types, another emits the gRPC service stubs
protoc \
  --proto_path=proto \
  --go_out=gen --go_opt=paths=source_relative \
  --go-grpc_out=gen --go-grpc_opt=paths=source_relative \
  proto/acme/user/v1/user_service.proto
▲ gotcha — why protoc-by-hand hurts at scale

Every developer needs the exact same protoc version and the exact same plugin versions, the include paths sprawl, and there's nothing stopping a breaking schema change. The flags become a fragile shell script no one wants to touch. This is the problem buf exists to solve.

The modern way — buf

buf wraps the whole Protobuf lifecycle: a fast built-in compiler, linting, breaking-change detection, formatting, and code generation driven by version-controlled YAML instead of CLI flags. Two config files do the work.

buf.yamlyaml
version: v2
modules:
  - path: proto
lint:
  use:
    - STANDARD          # the standard lint ruleset (naming, package versioning, …)
breaking:
  use:
    - FILE              # detect wire-breaking changes at file granularity
deps:
  - buf.build/googleapis/googleapis   # pull shared types from the registry, no vendoring
buf.gen.yamlyaml
version: v2
managed:
  enabled: true        # auto-manage file options (go_package etc.) so you don't hand-write them
plugins:
  # remote plugins run on Buf's infra — no local protoc/plugin installs needed
  - remote: buf.build/protocolbuffers/go
    out: gen
    opt: paths=source_relative
  - remote: buf.build/grpc/go
    out: gen
    opt: paths=source_relative
  - remote: buf.build/protocolbuffers/python
    out: gen/py
  - remote: buf.build/grpc/python
    out: gen/py
daily commandsbash
buf lint                                   # catch API-shape problems while editing
buf format -w                              # auto-format in place
buf breaking --against '.git#branch=main'  # fail if this diverges from main incompatibly
buf generate                               # emit code for every plugin in buf.gen.yaml
buf build                                  # compile the workspace to a binary image
◆ why buf is the standard answer in 2026

Three things you cannot get from protoc alone: breaking-change CI (the §04 rules enforced automatically), remote plugins (pin a plugin by URL, no "works on my machine" version skew), and managed mode (stop hand-writing per-language file options). If you're starting fresh, start with buf. If you inherit raw protoc scripts, buf reads the same .proto and is the upgrade path.

Testing without writing a client

Two tools let you hit a running server by hand — invaluable while developing:

  • grpcurl — curl for gRPC. With server reflection enabled, it discovers the schema live: grpcurl -plaintext -d '{"id":"42"}' localhost:50051 acme.user.v1.UserService/GetUser.
  • buf curl — buf's built-in equivalent, handles gRPC and Connect protocols.
  • grpcui / evans — interactive REPL/UI clients for exploratory testing.

Python

install + generatebash
pip install grpcio grpcio-tools          # runtime + protoc wrapper

# generate messages (_pb2), stubs (_pb2_grpc), and type stubs (.pyi)
python -m grpc_tools.protoc \
  -I proto \
  --python_out=gen --grpc_python_out=gen --pyi_out=gen \
  proto/acme/user/v1/user_service.proto
what each flag emits
--python_outuser_service_pb2.py — the message classes (serialization).
--grpc_python_outuser_service_pb2_grpc.py — the UserServiceStub (client) and UserServiceServicer (server base) plus the registration helper.
--pyi_out.pyi type stubs so editors and mypy understand the generated classes.

Server (sync)

server.pypython
from concurrent import futures
import grpc
from acme.user.v1 import user_service_pb2 as pb
from acme.user.v1 import user_service_pb2_grpc as pb_grpc

class UserService(pb_grpc.UserServiceServicer):
    def GetUser(self, request, context):                 # unary handler
        if not request.id:
            context.abort(grpc.StatusCode.INVALID_ARGUMENT, "id required")
        return pb.User(id=request.id, email=f"{request.id}@acme.dev")

    def ListUsers(self, request, context):               # server-streaming: yield
        for i in range(request.page_size or 3):
            yield pb.User(id=str(i), email=f"u{i}@acme.dev")

def serve():
    server = grpc.server(futures.ThreadPoolExecutor(max_workers=10))
    pb_grpc.add_UserServiceServicer_to_server(UserService(), server)
    server.add_insecure_port("[::]:50051")               # plaintext; use TLS in prod
    server.start()
    server.wait_for_termination()

if __name__ == "__main__":
    serve()
◆ context — the second parameter on every handler

context is your handle on the live call: context.abort(code, msg) ends with a gRPC status, context.invocation_metadata() reads request headers, context.set_trailing_metadata(...) attaches response headers, and context.is_active() / context.add_callback(...) detect client cancellation. Returning normally is OK; raising or aborting maps to an error status.

Client (sync)

client.pypython
import grpc
from acme.user.v1 import user_service_pb2 as pb
from acme.user.v1 import user_service_pb2_grpc as pb_grpc

with grpc.insecure_channel("localhost:50051") as channel:
    stub = pb_grpc.UserServiceStub(channel)

    user = stub.GetUser(pb.GetUserRequest(id="42"), timeout=2.0)   # deadline = 2s
    print(user.email)

    for u in stub.ListUsers(pb.ListUsersRequest(page_size=3)):     # iterate the stream
        print(u.id)

Async (grpc.aio)

async_server.pypython
import asyncio, grpc
from acme.user.v1 import user_service_pb2 as pb
from acme.user.v1 import user_service_pb2_grpc as pb_grpc

class UserService(pb_grpc.UserServiceServicer):
    async def GetUser(self, request, context):
        return pb.User(id=request.id, email=f"{request.id}@acme.dev")

async def serve():
    server = grpc.aio.server()                  # no thread pool: asyncio drives it
    pb_grpc.add_UserServiceServicer_to_server(UserService(), server)
    server.add_insecure_port("[::]:50051")
    await server.start()
    await server.wait_for_termination()

asyncio.run(serve())
▲ gotcha — sync gRPC and forking

The sync server uses a thread pool sized by max_workers; a slow handler starves it. Under heavy concurrency prefer grpc.aio. Also: gRPC's C-core does not survive os.fork() cleanly — create channels and servers after forking (relevant under Gunicorn/uWSGI with pre-fork workers).

Server

server.gogo
package main

import (
    "context"
    "log"
    "net"

    "google.golang.org/grpc"
    "google.golang.org/grpc/codes"
    "google.golang.org/grpc/status"
    userv1 "github.com/acme/gen/user/v1"
)

type server struct {
    userv1.UnimplementedUserServiceServer // MUST embed — forward compatibility
}

func (s *server) GetUser(ctx context.Context, req *userv1.GetUserRequest) (*userv1.User, error) {
    if req.GetId() == "" {
        return nil, status.Error(codes.InvalidArgument, "id required")
    }
    return &userv1.User{Id: req.GetId(), Email: req.GetId() + "@acme.dev"}, nil
}

// server-streaming: push via the stream, return nil to close
func (s *server) ListUsers(req *userv1.ListUsersRequest, stream userv1.UserService_ListUsersServer) error {
    for i := 0; i < 3; i++ {
        if err := stream.Send(&userv1.User{Id: "u" + string(rune('0'+i))}); err != nil {
            return err
        }
    }
    return nil
}

func main() {
    lis, err := net.Listen("tcp", ":50051")
    if err != nil {
        log.Fatal(err)
    }
    s := grpc.NewServer()
    userv1.RegisterUserServiceServer(s, &server{})
    log.Println("listening :50051")
    log.Fatal(s.Serve(lis))
}
▲ gotcha — embed UnimplementedUserServiceServer

The generated base struct gives default Unimplemented handlers for every method. Embedding it means adding a new RPC to the .proto won't break compilation of existing servers — they inherit a "not implemented" stub until you write the real one. Omitting it (or the older require_unimplemented_servers=false escape hatch) makes every schema addition a build break. Embed it by value, not as a pointer.

Client

client.gogo
package main

import (
    "context"
    "log"
    "time"

    "google.golang.org/grpc"
    "google.golang.org/grpc/credentials/insecure"
    userv1 "github.com/acme/gen/user/v1"
)

func main() {
    // NewClient is the current constructor. grpc.Dial / DialContext are deprecated.
    // It does NOT connect eagerly — the first RPC triggers the connection.
    conn, err := grpc.NewClient(
        "localhost:50051",
        grpc.WithTransportCredentials(insecure.NewCredentials()), // plaintext; TLS in prod
    )
    if err != nil {
        log.Fatal(err)
    }
    defer conn.Close()

    client := userv1.NewUserServiceClient(conn)

    ctx, cancel := context.WithTimeout(context.Background(), 2*time.Second) // deadline
    defer cancel()

    user, err := client.GetUser(ctx, &userv1.GetUserRequest{Id: "42"})
    if err != nil {
        log.Fatal(err)
    }
    log.Println(user.GetEmail())
}
◆ NewClient vs the old Dial

Older tutorials show grpc.Dial/DialContext, which eagerly connected and made WithBlock a common footgun. grpc.NewClient (the recommended API since the 1.6x line) is lazy and uses the standard dns resolver by default, so "host:port" targets behave predictably. Always pass a per-call context with a deadline — it's how cancellation and timeouts propagate across the whole call chain.

Node.js

Pure-JS runtime @grpc/grpc-js. Two codegen styles: dynamic (load .proto at runtime) or static (pre-generate). Dynamic is the common default.

installbash
npm install @grpc/grpc-js @grpc/proto-loader
# dynamic loading needs no build step. For static/TS codegen, add grpc-tools or ts-proto.

Server (dynamic codegen)

server.jsjavascript
const grpc = require("@grpc/grpc-js");
const protoLoader = require("@grpc/proto-loader");

// parse the .proto at runtime into a package definition
const def = protoLoader.loadSync("proto/acme/user/v1/user_service.proto", {
  keepCase: true,   // keep snake_case field names as written in the .proto
  longs: String,    // 64-bit ints -> strings (JS number can't hold them safely)
  enums: String,    // enums -> their string names
  defaults: true,
});
const proto = grpc.loadPackageDefinition(def).acme.user.v1;

function GetUser(call, callback) {            // unary: (call, callback) signature
  const { id } = call.request;
  if (!id) {
    return callback({ code: grpc.status.INVALID_ARGUMENT, message: "id required" });
  }
  callback(null, { id, email: `${id}@acme.dev` });
}

function ListUsers(call) {                     // server-streaming: write + end
  for (let i = 0; i < 3; i++) call.write({ id: String(i), email: `u${i}@acme.dev` });
  call.end();
}

const server = new grpc.Server();
server.addService(proto.UserService.service, { GetUser, ListUsers });
server.bindAsync("0.0.0.0:50051", grpc.ServerCredentials.createInsecure(), () => {
  console.log("listening :50051");            // server starts automatically after bind
});
▲ gotcha — bindAsync, not bind; and loader options

server.bind() is removed — use server.bindAsync(), and note modern grpc-js no longer needs an explicit server.start() after it. The proto-loader options are easy to get wrong: without keepCase your field names get camelCased; without longs: String, 64-bit integers lose precision silently. Set them deliberately and consistently between client and server.

Client (dynamic codegen)

client.jsjavascript
const grpc = require("@grpc/grpc-js");
const protoLoader = require("@grpc/proto-loader");

const def = protoLoader.loadSync("proto/acme/user/v1/user_service.proto", {
  keepCase: true, longs: String, enums: String, defaults: true,
});
const proto = grpc.loadPackageDefinition(def).acme.user.v1;

const client = new proto.UserService(
  "localhost:50051",
  grpc.credentials.createInsecure(),
);

// unary calls are callback-style; set a deadline via a call options object
const deadline = new Date(Date.now() + 2000);
client.GetUser({ id: "42" }, { deadline }, (err, user) => {
  if (err) return console.error(err.code, err.details);
  console.log(user.email);
});

// server-streaming returns an event emitter
const stream = client.ListUsers({ page_size: 3 });
stream.on("data", (u) => console.log(u.id));
stream.on("end", () => console.log("done"));
stream.on("error", (e) => console.error(e));
◆ dynamic vs static codegen — which to pick

Dynamic (proto-loader) is fastest to start: no build step, the .proto is the only artifact. Static (via grpc-tools or ts-proto) pre-generates .js/.d.ts, giving you real TypeScript types, autocomplete, and compile-time checking — worth it for any TS codebase. Both interoperate on the wire; the choice is purely developer ergonomics. For a typed Node service in 2026, most teams reach for ts-proto or Connect-ES.

gRPC mechanics

The runtime concepts every gRPC service touches: channels, metadata, deadlines, status, interceptors. This is the interview surface area.

Channels & stubs

A channel is a long-lived, reusable connection to a server (really a managed pool of HTTP/2 connections with its own state machine: IDLE → CONNECTING → READY → TRANSIENT_FAILURE). A stub (client) is a thin typed wrapper over a channel. Create one channel and share it — channels are expensive; stubs are cheap. Never open a channel per request.

Metadata

Metadata is key–value headers attached to a call — gRPC's equivalent of HTTP headers, used for auth tokens, request IDs, tracing context. Keys are lowercase ASCII; a -bin suffix marks binary values.

metadata (Python client / Go server)text
# client attaches:
stub.GetUser(req, metadata=(("authorization", "Bearer …"), ("x-request-id", "abc")))

// server reads (Go):
md, _ := metadata.FromIncomingContext(ctx)
token := md.Get("authorization")

Deadlines & cancellation

gRPC uses deadlines (an absolute point in time), not bare timeouts. The deadline propagates: it travels in call metadata, so a downstream service inherits the remaining budget. When it passes, the call fails with DEADLINE_EXCEEDED on both ends and the server's context is cancelled, letting handlers stop work.

◆ always set a deadline

A client with no deadline can hang forever on a stuck server, and threads/goroutines pile up until the process dies. Set one on every call. On the server, check for cancellation in long handlers (ctx.Err() in Go, context.is_active() in Python) and abandon work the client no longer wants — otherwise you do expensive work for a caller who already gave up.

Status codes

Every call ends with a status code. Returning the right one is how clients decide whether to retry, fail, or surface an error. The canonical set:

#CodeMeaning / when to return it
0OKSuccess
1CANCELLEDCaller cancelled the call
2UNKNOWNUnexpected error / unmapped exception
3INVALID_ARGUMENTBad input regardless of system state (client bug)
4DEADLINE_EXCEEDEDRan out of time
5NOT_FOUNDResource doesn't exist
6ALREADY_EXISTSCreate conflicts with existing resource
7PERMISSION_DENIEDAuthenticated but not authorized
8RESOURCE_EXHAUSTEDQuota / rate limit hit
9FAILED_PRECONDITIONSystem state forbids it (don't retry without fixing state)
10ABORTEDConcurrency conflict, e.g. txn abort (retry may help)
11OUT_OF_RANGEPast valid range (e.g. seek beyond EOF)
12UNIMPLEMENTEDMethod not implemented
13INTERNALSerious internal invariant broken
14UNAVAILABLETransient — server down/overloaded. The standard retryable code
15DATA_LOSSUnrecoverable data corruption
16UNAUTHENTICATEDMissing/invalid credentials
▲ gotcha — INVALID_ARGUMENT vs FAILED_PRECONDITION

Both mean "request rejected", but they signal different retry behavior. INVALID_ARGUMENT means the request is malformed no matter what — the client must change the request. FAILED_PRECONDITION means the request is fine but the system isn't in a state to accept it — the client should fix state first, not blindly retry. ABORTED and UNAVAILABLE are the retryable ones. Picking the right code is what makes a gRPC API usable by automated clients.

Rich error details

Beyond code + message, attach structured details with the google.rpc.Status model (grpcio-status in Python, status package in Go): BadRequest.FieldViolation, RetryInfo, QuotaFailure, etc. Clients parse these for machine-readable error handling instead of regexing message strings.

Interceptors

Interceptors are gRPC's middleware: one place to wrap every call for logging, auth, metrics, tracing, retries, panic recovery. Client-side and server-side, unary and streaming variants exist.

server interceptor (Go) — auth + timinggo
func authUnary(
    ctx context.Context, req any,
    info *grpc.UnaryServerInfo, handler grpc.UnaryHandler,
) (any, error) {
    md, _ := metadata.FromIncomingContext(ctx)
    if len(md.Get("authorization")) == 0 {
        return nil, status.Error(codes.Unauthenticated, "missing token")
    }
    start := time.Now()
    resp, err := handler(ctx, req)                 // call the actual handler
    log.Printf("%s took %s", info.FullMethod, time.Since(start))
    return resp, err
}

s := grpc.NewServer(grpc.ChainUnaryInterceptor(authUnary, otherInterceptor))

Built-in services you should turn on

  • Health checking — the standard grpc.health.v1.Health service. Load balancers and orchestrators (k8s gRPC probes) call Check/Watch to route only to healthy backends.
  • Server reflection — exposes your schema at runtime so grpcurl/grpcui can call the server without the .proto. Enable in dev; gate it in prod.

Keepalive & retries

Keepalive pings detect dead connections behind load balancers and idle NAT timeouts; tune ping interval and timeout, but don't ping so aggressively that the server rejects you with ENHANCE_YOUR_CALM. Transparent retries can be configured declaratively via a service config (retry policy: which codes, max attempts, backoff) — let the framework retry UNAVAILABLE rather than hand-rolling loops.

Production concerns

What the toy examples skip. Plaintext and a single backend get you to a demo, not to prod.

Transport security: TLS & mTLS

Every example above used insecure/plaintext credentials — fine for localhost, never for real traffic. Production uses TLS (server proves identity to client) or mTLS (both sides present certs — common for service-to-service zero-trust). You swap the credential object, not your handlers:

TLS credentialstext
# Go server:
creds, _ := credentials.NewServerTLSFromFile("server.crt", "server.key")
s := grpc.NewServer(grpc.Creds(creds))

# Go client:
creds := credentials.NewClientTLSFromCert(certPool, "")
conn, _ := grpc.NewClient(addr, grpc.WithTransportCredentials(creds))

# Python client:
creds = grpc.ssl_channel_credentials(root_certs)
channel = grpc.secure_channel(addr, creds)
◆ in 2026, assume TLS 1.3 + mTLS for east-west traffic

Service meshes (Istio, Linkerd) often terminate mTLS for you transparently. If you're not in a mesh, wire it yourself — and rotate certs. Plaintext gRPC should exist only inside a single trusted boundary, if at all.

Load balancing

gRPC's HTTP/2 multiplexing breaks naive L4 load balancers: one long-lived connection pins all calls to one backend. Two correct approaches:

  • Client-side LB — the client resolves multiple backend addresses (via a dns:/// or custom resolver) and a policy (round_robin, pick_first) spreads calls across them. No proxy hop.
  • Look-aside / proxy LB — an L7 proxy that understands gRPC (Envoy) balances per-request, not per-connection. This is what a mesh gives you.
▲ gotcha — a plain TCP/round-robin DNS LB is wrong for gRPC

Because all requests share one connection, an L4 balancer sends every call to whichever backend won the connection. Use an L7/gRPC-aware proxy or client-side balancing, or one hot backend takes all the load.

Observability

The 2026 default is OpenTelemetry: gRPC has built-in OTel instrumentation for traces and metrics across every language. Trace context propagates in metadata automatically, so a single request stitches across services. Export metrics (latency, status-code rates, in-flight calls) to Prometheus; export traces to your backend of choice. Add a logging/recovery interceptor (§11) so a panicking handler returns INTERNAL instead of killing the process.

Browsers: gRPC-Web

Browsers can't open raw HTTP/2 gRPC streams, so direct browser→gRPC doesn't work. Options: gRPC-Web (a browser-compatible variant; needs an Envoy proxy or in-process translator, and supports unary + server-streaming only), or Connect (buf's protocol — speaks gRPC, gRPC-Web, and a plain HTTP/JSON mode from the same handlers, callable with curl). For new browser-facing work, Connect is often the smoother path.

The five things people get wrong

  1. Reusing or renumbering a field number → silent data corruption.
  2. Letting enum 0 mean something real instead of _UNSPECIFIED.
  3. Forgetting optional when "0 vs unset" matters.
  4. No deadline on the client → hangs and resource leaks.
  5. An L4 load balancer in front of gRPC → one backend takes all traffic.
